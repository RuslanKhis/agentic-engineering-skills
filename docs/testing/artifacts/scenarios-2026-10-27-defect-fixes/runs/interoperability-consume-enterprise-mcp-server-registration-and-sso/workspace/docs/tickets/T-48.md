# T-48 Connect the support assistant to Loyalty Cloud

Agents need balances and history for signed-in customers, and staff-initiated
points adjustments. Record how we register, how credentials are bound, and what
the tool contract must survive. Owner: Jonas.

### 1. Registration: Client ID Metadata Document, never DCR

The vendor's authorization server (`https://auth.loyaltycloud.example`) advertises
both `client_id_metadata_document_supported: true` and a `registration_endpoint`.
The specification's order is pre-registered id, then metadata document, then DCR
as a deprecated fallback. Security forbids DCR, so:

1. Host one JSON document at an HTTPS URL with a path. The URL is our `client_id`
   and the document's `client_id` must equal it exactly. Placeholder:
   `https://support.harbour-outfitters.example/oauth/clients/loyalty-cloud.json`
   (real host: question Q1).
2. Contents: `client_id`, `client_name`, `redirect_uris` (one HTTPS URI on our host;
   the flow is headless so it is never used, record that), `grant_types`
   (`urn:ietf:params:oauth:grant-type:jwt-bearer`), `token_endpoint_auth_method:
   private_key_jwt`, and `jwks_uri` (public keys only). Check the vendor's accepted
   field set; they may also require `application_type`.
3. The document must be fetchable by the vendor's server without sign-in. The
   service is behind IAP, so serve it from a path excluded from IAP, or from a
   static bucket behind the load balancer. Serve only the document and the JWKS there.
4. Signing key: prefer a Cloud KMS asymmetric key so the private key is never
   exported; otherwise Secret Manager. Rotation: publish the new `kid` in the JWKS
   before signing with it.
5. Never call `registration_endpoint`. The client has no DCR code path, and a test
   fails if the fake authorization server's registration endpoint receives a request.
   Egress allowlist: `mcp.loyaltycloud.example`, `auth.loyaltycloud.example`, the
   Entra token endpoint.
6. Ask the vendor to allow-list our client id. A metadata-document client can still
   be refused by their policy, and they should confirm JWT-bearer grants are enabled
   for it with scopes `loyalty.read` and `loyalty.adjust` only.

### 2. Credential binding: Enterprise-Managed Authorization, no consent screens

Staff path (stable profile):

1. Entra (`northwind.example`) token exchange: `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`,
   `requested_token_type=urn:ietf:params:oauth:token-type:id-jag`, `subject_token` the
   staff member's Entra ID token with its `subject_token_type`, `audience`
   `https://auth.loyaltycloud.example` (the issuer), `resource`
   `https://mcp.loyaltycloud.example/v2/mcp`. Result: an ID-JAG (`oauth-id-jag+jwt`).
2. At the vendor token endpoint: `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`,
   `assertion` the ID-JAG, client authentication `private_key_jwt` with our
   metadata-document client id, `scope` as below. Result: a short-lived access token.
3. The token reaches MCP only through `McpToolset(header_provider=...)` (or the
   wrapper's HTTP client, see section 3). It is never put in `connection_params.headers`,
   session state, events, logs, or tool results. The provider reads the verified
   `Principal`, not anything the model supplied. A provider that raises fails the
   call closed.
4. Lifecycle: no vendor refresh token is stored (the profile defines none); re-exchange
   instead. Cache in memory only, for the shorter of (token lifetime minus a margin) and
   a fixed ceiling, keyed by principal + issuer + client id + scope. One exchange in
   flight per principal. `invalid_grant` is a denial (tell the user, do not retry);
   transport errors are transient (one retry per step).
5. Issuer binding: the credential index records issuer `https://auth.loyaltycloud.example`,
   client id URL, registration mechanism `client-id-metadata-document`, scopes and
   key id. Never reuse for another issuer. If the authorization response carries `iss`,
   it must match before redemption (not applicable to the JWT-bearer step, which has no
   redirect, but keep the check in the token-response handling).
6. Scopes: staff sessions without the adjuster role get `loyalty.read` only. Request
   `loyalty.adjust` only for a principal holding the adjuster role (question Q3).
   Different tokens give different pooled MCP sessions (the pool is keyed on headers).

### 3. Identity gaps this design depends on (answer before building)

- The existing `Principal` is an IAP `sub`, and an IAP assertion is not an Entra
  ID token, so it cannot be the `subject_token`. The agent needs a server-side Entra
  sign-in (or Workforce Identity Federation that exposes the upstream ID token) that
  stores the ID/refresh token against the `Principal` outside ADK state (Q2).
- Customers have no Entra identity, so the enterprise grant cannot cover "balances for
  signed-in customers". Proposed: customer reads use the vendor's headless client
  credentials profile (a draft extension; confirm with the vendor), with `loyalty.read`
  only, and the member id resolved server-side from the customer's profile (Q4). Until
  confirmed, ship the staff path only.
- `app/store.py` has no loyalty member id and no staff role. Both must come from our
  store or the IdP, never from the model or the request body.

### 4. What the tool contract must survive

Findings from the recorded `tools/list`:

| Finding | Consequence |
| --- | --- |
| `list points history` contains spaces | Not a valid function name for the model API; ADK cannot rename MCP tools |
| `confirm_points_adjustment_for_member_after_customer_service_review_and_supervisor_sign_off` is 90 characters | Over the 64-character function-name limit before any `tool_name_prefix` |
| `member_id` is a model argument on every tool | The model could read or adjust any member: breaks "user id comes from the verified principal" |
| `pattern`, `minimum/maximum`, `additionalProperties` constraints | ADK keeps only the Gemini-supported schema subset; dropped keywords mean the server rejects arguments the model could not know were invalid. Record which survive |
| No `outputSchema`, no annotations | Nothing to validate results against; tiers come from our review |
| Staging list only | Production may differ; re-record when credentialed |

Therefore:

1. Expose four app-owned tools with clean names, not the raw server tools:
   `loyalty_get_balance(tool_context)`, `loyalty_list_history(limit, tool_context)`,
   `loyalty_start_adjustment(delta, reason, tool_context)`, and a confirm step. They
   call the vendor's tools through an MCP client in `app/clients/` (imports `mcp`, not
   `google.adk`; tests use a fake server in `tests/fakes.py`). `member_id` is not a
   parameter: resolve it from the principal (balances, history) or from the staff-selected
   case record (adjustments), then check `^LC[0-9]{8}$` locally. If the team prefers
   `McpToolset`, it needs a `tool_filter` and still cannot fix the two names, so
   it cannot be used for those tools.
2. Adjustments: `start` is a write intent and records `(handle, staff principal, member,
   delta, reason, created_at)` in our store. `confirm` accepts a handle only when it
   belongs to the same principal or, if sign-off by a different supervisor is required,
   to a supervisor with the approver role. Bound `delta` in code (limit: Q5). The model
   never supplies a handle it did not receive from `start` in this session.
3. Confirmation: a model-requested adjustment needs human approval, as a strict-`True`
   `require_confirmation` at minimum. The name says supervisor sign-off, which may take
   hours and another person, so prefer a durable review record approved through an
   authenticated API route (not chat text), because ADK's in-session confirmation does
   not survive restarts or a persistent session store. Record an operation key per handle
   so a duplicate approval converges on one effect; test duplicate approval, since
   whether the vendor treats a repeated `confirm` as idempotent is unknown (ask them).
4. Results are vendor-controlled text. Project only the expected fields (balance, ISO
   date, integer delta, reason code), cap history at the vendor's 50, and drop free text
   before it reaches the model. Points are integers; money elsewhere stays in cents.
5. Failures return actionable errors, not raw exceptions: 401 or token mint failure
   ("sign-in with Loyalty Cloud unavailable"), 403 / `insufficient_scope`
   ("not permitted to adjust points"), unknown member, timeout, `input_required`
   (2026-07-28 multi-round-trip result: report it, never answer it automatically). Set no
   `sampling_callback` or `elicitation_callback`. Writes are never retried automatically.
6. Drift: commit the manifest from `mcp_tool_inventory.py --out`; a later `--diff` reporting
   `rug_pull_signal` is a change request. If `tool_list_cache_ttl_seconds` is used, write
   down the value. Call `close()` on the toolset or client at shutdown (`server.py`
   currently builds a Runner and never closes).
7. Tests (all with fakes; never the real vendor or Entra): customer A's session never
   reaches member B's id; token never appears in events, state, logs; header provider
   raising fails closed; fake AS registration endpoint never hit; staff without adjuster
   role gets a `loyalty.read` token and a refusal on adjust; confirm with a foreign or
   reused handle refused; duplicate approval gives one vendor call; vendor timeout,
   `isError`, server restart; the recorded definitions declare no name over 64 characters
   or with spaces.
