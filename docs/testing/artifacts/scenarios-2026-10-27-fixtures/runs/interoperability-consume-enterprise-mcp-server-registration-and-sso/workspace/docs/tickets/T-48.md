Agents need balances and history for signed-in customers, and staff-initiated
points adjustments. Record how we register, how credentials are bound, and what

### 1. Registration (no DCR)

The vendor AS advertises both `client_id_metadata_document_supported` and a
`registration_endpoint`. Our client never calls `registration_endpoint`
(requirement 1). Order: pre-registered id, else Client ID Metadata Document.

1. Host a JSON document at a stable HTTPS URL on our domain, e.g.
   `https://support.northwind.example/oauth/client.json`. `client_id` must equal
   that URL exactly. Fields: `client_name`, `redirect_uris` (required even though
   we use no browser flow: list one HTTPS URI on our host and mark it unused),
   `grant_types: ["urn:ietf:params:oauth:grant-type:jwt-bearer"]`,
   `token_endpoint_auth_method: "private_key_jwt"` plus `jwks_uri`. No client
   secret exists. The signing key lives in Secret Manager, not the repo.
2. Vendor must confirm in writing, before any live test: (a) their AS fetches
   and accepts our document, (b) it accepts the JWT-bearer grant from a
   CIMD client, (c) it trusts our IdP's ID-JAG issuer and audience, (d) scopes
   per grant (below). Ask for a pre-registered client id as fallback if (a) or
   (b) is "no". Do not fall back to DCR.
3. Key the stored client state by issuer `https://auth.loyaltycloud.example`
   (SEP-2352); if the issuer changes, re-register, never reuse.
4. Hosting the document is an outward-facing publication; needs Ahmed's sign-off.

### 2. Credential binding (no consent screens)

Enterprise-managed authorization, per call, with no vendor refresh token stored:

1. Subject token: the signed-in user's Northwind ID token.
2. At the Entra/IdP token endpoint: RFC 8693 token exchange,
   `requested_token_type=urn:ietf:params:oauth:token-type:id-jag`,
   `audience=https://auth.loyaltycloud.example`,
   `resource=https://mcp.loyaltycloud.example/v2/mcp`, scope as needed.
3. Present the ID-JAG at the vendor token endpoint as an RFC 7523 jwt-bearer
   grant, client authenticating with private_key_jwt. Check `iss` matches the
   recorded issuer (RFC 9207) where an authorization response exists.
4. The access token is minted for the MCP server's audience only. Never forward
   our own IAP assertion or the user's ID token to the vendor.
5. Attach it with `McpToolset(header_provider=...)`: reads the verified
   `Principal` (`app/auth.py`), never a model argument or request body; cache
   short, single flight per principal, re-exchange on expiry; a raising provider
   fails closed (test it). Nothing in `connection_params.headers`; the pool key
   is the header hash, so a shared header would share a session across users.
   Tokens never enter state, events, logs or the browser (requirement 3).
6. Two toolsets, two scopes: read tools get a `loyalty.read` token; adjustment
   tools a separate toolset whose provider requests `loyalty.adjust` and only
   for staff principals. A customer principal can never obtain it.

Open questions and assumptions I proceed on (nobody was available to answer):

- Q1: `app/auth.py` verifies the Google IAP assertion, not an Entra ID token.
  Token exchange needs the IdP's ID token. Assumption: IAP is federated to
  Northwind SSO and the original ID token can be obtained server-side at the
  request boundary (a new field on `Principal`, kept out of state). If not,
  the exchange cannot happen and this design is blocked.
- Q2: Balances/history are for signed-in customers, who are not in the Northwind
  tenant, so EMA cannot cover them. Assumption: customer reads use a
  vendor-supported service grant (the client-credentials profile is a draft;
  confirm) or the staff user's EMA token with the customer's `member_id`
  resolved server-side. Owner: Jonas + Ahmed. EMA applies to staff for sure.
- Q3: Does Entra issue ID-JAG today? Assumption yes, as security states; verify
  with the IdP admin.
- Q4: Mapping from customer principal to `member_id`: assumed to be a lookup in
  our store, not yet present in `app/store.py`.

### 3. What the tool contract must survive

Reviewed from `docs/vendor/tools-list-2026-10-20.json` (staging, not production).

| Issue | Consequence | Handling |
| --- | --- | --- |
| `list points history` has spaces | Not a valid function name for the model API; ADK may reject or mangle | Do not expose via McpToolset; wrap |
| `confirm_points_adjustment_for_member_after_customer_service_review_and_supervisor_sign_off` is about 90 chars | Exceeds the usual 64-char function-name limit; the name also promises a review the server may not enforce | Wrap under our own name |
| No `outputSchema`, no annotations | Results unvalidated; hints would be untrusted anyway | Validate results ourselves; tier from our review |
| `member_id` pattern only on balance; history/start have none | Model can pass any member | Validate `^LC[0-9]{8}$` on every call, in code |
| `member_id` is a model argument | Cross-customer read or adjustment | Drop it from the model-facing schema; fill it from the verified principal's mapping (customers) or require staff to pick it, checked against the staff's case |
| `delta` unbounded, `reason` free text | Large or negative adjustments, injection into audit text | Cap `abs(delta)` in settings, require non-empty bounded reason |
| Two-step start/confirm with `adjustment_handle` | Handle is a bearer capability; replay or cross-user confirm | See below |
| Tool descriptions are one line | Model misuse | Our wrapper docstrings carry the contract |
| `tools/list` is staging | Prod may differ | Run `mcp_tool_inventory.py --allow-remote` against prod (needs owner approval) and commit the manifest; later `--diff` with `rug_pull_signal` is a change request |

Shape: `McpToolset` is not used for the four tools as listed. Instead thin
`FunctionTool` wrappers in `app/tools/loyalty.py` with clean names
(`get_loyalty_balance`, `list_loyalty_history`, `start_points_adjustment`,
`confirm_points_adjustment`) call an MCP client in `app/clients/loyalty.py`
(no `google.adk` imports, per AGENTS.md; fake in `tests/fakes.py`). If an
`McpToolset` is preferred, it needs `tool_filter` by exact name, `tool_name_prefix="loyalty"` and
the two renamed tools cannot pass through it, so the wrapper route is the
recommendation.

Adjustment flow:
- `start_points_adjustment` is staff-only (principal check in the tool body, not
  the prompt). Record `{handle, staff user_id, member_id, delta, reason, state}`
  in our store when the vendor returns the handle.
- `confirm_points_adjustment` looks the handle up, refuses if it was issued to a
  different principal, is unknown, or already confirmed (converge on one effect
  with an operation record; duplicate approval must not double-apply).
- Confirmation is human: `require_confirmation` as a callable returning a strict
  `bool`, answered by the authenticated staff user via the app API, never by the
  model or A2A. The supervisor sign-off the vendor's name implies is a
  business rule we enforce ourselves (second principal), not assumed.
- Do not retry `confirm` blindly; a timeout leaves an unknown outcome. Report it
  as such and reconcile through `history`.
- Results: return small dicts `{"status": ..., ...}` like `issue_refund`; points
  are integers, not cents; map vendor errors to actionable messages without
  leaking tokens or raw bodies.
