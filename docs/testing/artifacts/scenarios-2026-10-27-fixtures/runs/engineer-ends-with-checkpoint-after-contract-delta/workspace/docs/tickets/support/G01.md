# G01 Save and forget a reply language

## Outcome

A signed-in customer can save the language the assistant replies in, and forget it; later
conversations use it (D1).

## Scope

- In: a `preferences` table in the SQLite store, `GET/PUT/DELETE /api/preferences/language` keyed
  on the verified principal, loading the value into session state as `user:language` when a
  session starts, and the instruction reading `{user:language?}`.
- Out: streaming (G02), group or household preferences (out of scope for this release).
- Depth: proof of concept; floor kept (identity from IAP only, no secrets in code).

## Constraints

Identity comes from `app/auth.py` only (AGENTS.md); keep the existing tool interfaces.

## Resources created

none

## Acceptance

- [ ] A1 WHEN a customer saves a language THE app SHALL use it in their next session (C1)
- [ ] A2 IF another customer requests or deletes it THEN THE app SHALL return 404 (C1, SB01)
- [ ] A3 WHEN the customer forgets it THE app SHALL NOT use it in their next session (C2)

Rulings (left to the designer's checkpoint):
- R-a: soft delete keeps the language value for 30 days. Why: the person decided it. Cost if wrong: if "forget" is a privacy erasure request, a retained value may breach it; the alternative is a tombstone with no value. Assumed: keep the value as decided, restorable only by saving again (no restore route), never read while deleted.
- R-b: the 30-day purge has no caller. Why: no scheduler exists and a new cloud resource is out of scope. Cost if wrong: rows live past 30 days. Assumed: run `purge_expired` from a job later.
- R-c: a blank string, not a removed key, clears the cached value. Why: unverified that a removed `user:` key can be deleted through ADK state. Cost if wrong: `{user:language?}` renders something other than blank. Assumed: blank renders empty.
- R-d: language accepts 2-40 letters, spaces, hyphens and apostrophes, so free text cannot be injected into the instruction. Cost if wrong: a valid name such as one with a digit is refused (422).

Questions that nobody could answer in this non-interactive run: (1) Does "forget" need a true erasure after a request? (2) Who runs the purge? Proceeded on the assumptions above.
