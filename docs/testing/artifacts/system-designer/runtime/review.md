# Draft architecture review

Keep React, existing OIDC and PostgreSQL. The main gaps are durable execution ownership, honest completion, artifact delivery and safe mixed-version operation. A customer must be able to request a report, disconnect, reconnect through another replica and see the same authorized work, its actual outcome and any completed download.

These are recommendations; the design is not ready for implementation until the contracts below are settled.

## Most important choices and checks

1. **Separate context selection from deletion.** Sending the last 20 events does not delete PostgreSQL history and can split a tool call from its result. Keep durable conversation history separate from bounded model context; retain required facts and complete tool exchanges. Bound query work before materializing results and bound the complete outgoing model payload, including tool responses. Define retention and erasure for events, summaries, caches, artifacts and backups separately. This adds lifecycle handling but makes the privacy promise enforceable. **Check:** inspect the actual model request after a large tool result, and prove deletion/expiry prevents later retrieval or resurrection by pending work.

2. **Make privacy a backend contract.** The API verifies OIDC and derives tenant/user scope before history reads, model exposure and execution. Enforce ownership again on send, reconnect, cancel, download and delete; knowing a conversation or artifact ID grants no authority. Keep workload credentials separate from customer identity. This adds authorization checks at each entry point. **Check:** another customer cannot access any route, including a reconnect or download routed to a different replica; revoked access is denied.

3. **Store full results durably.** Use an object store such as GCS, with owner, result version, completeness, expiry and object reference recorded in PostgreSQL. Return an application artifact ID and authorize download through the backend or a scoped, short-lived link. Temporary disk may stage a file but cannot be its durable home. This adds object lifecycle and storage costs. **Check:** after replacing the producing replica, the owner can download the complete result; another customer and an expired link cannot. Distinguish complete, truncated, empty and unavailable results, and validate report meaning/freshness separately from schema validity.

4. **Own the browser event contract.** The gateway emits sanitized application events carrying invocation, message and exact tool-call IDs, plus replay ordering/deduplication information. Pair results by call ID, including simultaneous calls to the same tool. Treat streamed text as provisional; publish application success only after all required steps and durable result/state recording succeed. Preserve completed stages and downloads when a later stage fails, showing partial/failed/uncertain status accurately. This requires a client state machine. **Check:** duplicate/out-of-order events, same-name calls, an early final-response event followed by failure, and real incremental delivery through the gateway and browser. Bound event sizes, retained client state and slow-consumer buffering.

5. **Reconnect to existing work.** Persist accepted invocation identity, request fingerprint, status and dispatch intent before acknowledging acceptance. A retried submission with the same key loads the same work; changed payloads are rejected. Reconnect subscribes from a cursor or reads durable status instead of creating another invocation. Conversation persistence alone cannot resume execution: assign a recoverable worker/job owner and recovery policy. This costs durable orchestration. **Check:** lose the acceptance response, reconnect repeatedly and kill the worker; only one logical report exists and recovery reaches a truthful outcome.

6. **Coordinate all three replicas.** Recommend queued, serialized turns per conversation, enforced through PostgreSQL ownership/version checks. If using leases, fence stale owners from protected commits after takeover. Admission, deadlines, usage and reservations must also be shared. Disconnecting the browser is not cancellation or proof that remote work stopped; retain its reservation until completion, confirmed cancellation or reconciliation. This trades some throughput for consistency. **Check:** concurrent submissions across replicas, lease expiry with the old worker still active, disconnect during a remote call and control-store failure; no conflicting commits or premature capacity release occur.

7. **Make storage changes compatible with rolling releases.** Version the stored contracts and use an expand/migrate/contract sequence with an explicit old/new read/write compatibility matrix. Drain accepted work before closing dependencies. If compatibility cannot be provided, gate the migration behind a controlled cutover. Added migration work preserves rollback options. **Check:** old and new replicas read/write the same sessions, reconnect to queued/running work, and roll back against migrated data without loss or corruption.

## Remaining decisions and first slice

Confirm retention/download expiry, queue/deadline limits, cancellation behavior and whether accepted reports must continue after disconnect; the recommendation above assumes they must. Verify the pinned ADK versions' session serialization, event identity/finality and cancellation behavior, plus the selected GCP artifact and execution contracts against current official documentation. These are verification tasks, not established provider guarantees. No additional memory service or multi-agent design is needed for the stated requirements.

Start with one read-only report journey: authenticated request → durable acceptance → progress → durable artifact → reconnect → verified terminal status. Its acceptance cases should include cross-tenant denial, worker replacement, duplicate submission and a late failure after a completed stage. Relevant implementation specialists are `adk-frontend-integration`, `adk-memory-architecture` and `adk-agent-evaluation`. All checks above are planned; no implementation, deployment or tests have been performed.
