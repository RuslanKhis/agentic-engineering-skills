# T-203 Make Gmail connection usable by the 30 pilot customers

Remainder of T-202. The broker and the tool exist (`support_agent/gmail_connect.py`, `gmail_tools.py`).

Acceptance:
- Customer sign-in is verified by the gateway, and ADK sessions are created with `user_id` set to that verified principal.
  Bob cannot load Alice's session.
- Authenticated `POST /gmail/connect`, `GET /gmail/callback` and `POST /gmail/disconnect` routes use a Secure HttpOnly
  SameSite=Lax cookie for the browser secret and CSRF protection on POSTs.
  Callback query strings are kept out of access logs.
- The connection index and consent transactions live in a shared durable store (for example Firestore).
  Refresh tokens are in Secret Manager or a KMS-encrypted store. The OAuth client secret comes from Secret Manager.
  Disconnect and refresh hold across a restart and two Cloud Run instances.
- A real ADK Runner test with only the model substituted calls `find_order_confirmations` for the session owner.
- Google OAuth consent screen: either Testing mode with the 30 pilot customers as test users
  (refresh tokens expire after 7 days in Testing, so customers reconnect weekly), or start
  restricted-scope verification and the security assessment.
- T-104 security review covers root_agent holding mailbox data together with send_email.

Decisions needed: how customers sign in; Testing mode vs verification; durable store choice.
