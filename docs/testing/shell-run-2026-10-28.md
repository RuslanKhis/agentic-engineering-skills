# The first shell-enabled scenario run · 28 October 2026

**This run was unconfined.** Every earlier scenario run gave the agent Read,
Write, Edit, Glob, Grep and Skill, each confined to its workspace by path
rules, and no shell. Here the agent also had Bash. A shell cannot be confined
by path rules, so it could reach any file the user can read and the network.
The runner instead made the run harmless through its environment: no cloud,
container, git-hosting or SSH credential was visible to it, and every
command it ran was recorded and audited afterwards. Branch
`phase-13-shell-run`, from `main` at `151ee23`. Live GCP testing was out of
scope: no agent reached a cloud.

## How the environment was scrubbed

When `--agent-tools` includes Bash, `run_scenarios.py` builds the agent's
environment as follows. The code is `SHELL_TOOLS` to `HOME_NOTE` and
`shell_environment()` in [the runner](../../scripts/run_scenarios.py).

- **Removed.** Every variable starting `GOOGLE_`, `GCLOUD_`, `CLOUDSDK_`,
  `AWS_`, `AZURE_` or `ARM_` is removed. So are `SSH_AUTH_SOCK`,
  `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITLAB_TOKEN`,
  `NPM_TOKEN`, `HF_TOKEN`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `VAULT_TOKEN`,
  `KUBECONFIG`, `DOCKER_CONFIG`, `DOCKER_HOST`, `GIT_CONFIG_GLOBAL`,
  `GIT_ASKPASS`, `SSH_ASKPASS`, and the parent Claude Code session's
  `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN`. On this
  machine the scrub actually removed `SSH_AUTH_SOCK` and the two messaging
  variables; no cloud variable was set.
- **Redirected** to empty paths under `<case>/shell-env/`, outside the
  workspace: `CLOUDSDK_CONFIG` (gcloud, and google-auth's application-default
  lookup, which follows it), `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`,
  `AZURE_CONFIG_DIR`, `DOCKER_CONFIG`, `KUBECONFIG`, `GIT_CONFIG_GLOBAL`,
  `GH_CONFIG_DIR` and `NPM_CONFIG_USERCONFIG`.
- **Set:**
  - `GIT_CONFIG_NOSYSTEM=1`;
  - `BROWSER=true`, so a login flow opens nothing;
  - `CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1`, explained under "A runner
    defect found mid-run" below.
- **HOME mode: real home, configuration redirected
  (`real-home-redirected-config`).** With HOME pointed at an empty
  directory, the claude CLI (Claude Code 2.1.306, macOS keychain login)
  answered "Not logged in · Please run /login" and exited 1. With the real
  HOME it authenticated. So HOME stays real, and the fallback the brief
  allowed (redirect each tool's configuration) is what ran.

**What this leaves exposed.** Files under the real home directory stay
readable to a shell. That includes `~/.config/gcloud` (which holds
application-default credentials on this machine), `~/.aws`, `~/.ssh` and
`~/.claude`. No tool finds them, because their configuration points
elsewhere, but `cat` would. The network is open.

**What the run records.** `confinement()` now carries:
- `"unconfined": true`;
- `shell_environment` with the HOME mode and its reason, the variables
  scrubbed (names only, never values), the prefixes and names scrubbed, the
  redirects and the fixed settings.

Each `agent.json` also has `variables_scrubbed` and `shell_commands`, which
holds every Bash command with its clipped output and error flag. Unit tests
in `tests/test_run_scenarios.py` (`ShellRunTests`) check:
- the removal, including that no credential value survives under any name;
- that the redirect targets are empty;
- that HOME and PATH are kept;
- that a run without Bash keeps its environment;
- the confinement record;
- the evidence given to the judge.

### A runner defect found mid-run

A `cd` in the Bash tool moves Claude Code's working directory, and the
relative allow rules (`Write(./**)`) move with it. After an agent changed
into `.claude/skills/adk-governance-pack/references`, every write under
`docs/` was refused. The first Auckland-Singapore and Quebec-Ontario runs
(batches s3 and s4) lost their packs to it: 0 of 6 and 3 of 6, judged on
nothing or on files written around the refusal.

A probe agent that changed directory and then wrote under `docs/` was
allowed once the variable was set. Both packs were then re-run (batches r3
and r4). The spoiled runs are kept under
[runs-void/](artifacts/shell-run-2026-10-28/runs-void/), counted in the
cost and left out of the results.

## Smoke test

Before any scenario ran, a Bash-enabled agent, set up through the runner's
own `prepare` and `run_agent` in the `governance-pack-nsw-agency-chatbot`
workspace, ran exactly two commands:

```text
$ gcloud config list
[core]
disable_usage_reporting = False

Your active configuration is: [default]

$ env | grep -i -E 'google|cloudsdk'
__CFBundleIdentifier=com.googlecode.iterm2
PATH=...:/Users/<user>/Downloads/google-cloud-sdk/bin:...
CLOUDSDK_CONFIG=<run dir>/governance-pack-nsw-agency-chatbot/shell-env/gcloud
```

No account, no project and no credentials variable were visible. The two
other matches are unrelated: the terminal's bundle identifier, and PATH
holding the SDK binary. gcloud wrote a fresh `default` configuration into the
empty directory. It also cached `gce=False`, which means it ran its own
metadata-server check (a local network probe that carries no credentials).

Evidence: [smoke/](artifacts/shell-run-2026-10-28/smoke/) and the
working-directory probe [cd-probe/](artifacts/shell-run-2026-10-28/cd-probe/).

## Method

- `run_scenarios.py run`, agent and judge `claude-sonnet-5-5` through
  `claude-cli` (Claude Code 2.1.306), three judge repeats with majority
  verdicts.
- `--agent-tools Read,Write,Edit,Glob,Grep,Skill,Bash`, `--max-turns 40`,
  `--timeout 1200`, `--max-budget-usd 3`, project skill install.
- Skills at `151ee23`; the task text and run conditions are unchanged, so
  agents were still told not to install packages, make network requests or
  touch cloud resources.
- Batches ran in parallel: s1 to s4 one governance pack each, s5 and s6 four
  scenarios each, t1 three, r3 and r4 the re-runs.
- `engineer-ticket-with-missing-companion` was re-judged (rj1) on its
  unchanged evidence after the parser fix.
- Evidence per scenario (task, `agent.json` with every shell command, final
  answer, judge replies, files written), plus each batch's manifest and
  results, is under
  [artifacts/shell-run-2026-10-28/](artifacts/shell-run-2026-10-28/).
- [summary.md](artifacts/shell-run-2026-10-28/summary.md) has every vote
  beside the last no-shell votes.

## Bash commands of concern

195 shell commands over the 17 scenario runs (valid and spoiled) were
audited, with heredoc bodies (file contents) set aside. The audit looked for
paths outside the run directory, network commands and cloud CLIs.

| Scenario | Command | What it reached |
| --- | --- | --- |
| governance-pack-nsw-agency-chatbot | `ls ~/.agentic-engineering` | Outside the workspace, read-only. The directory does not exist on this machine. The agent skipped the skill's `${AGENTIC_ENGINEERING_HOME:-...}` form; the variable pointed at the run's own empty home |
| engineer-google-skills-supporting-missing | `ls ~/.claude/skills .claude/skills` | Listed the names of the user's own installed skills; read none |
| engineer-ticket-with-missing-companion | `ls ~/.claude/skills` | Same, names only |
| interoperability-expose-mcp-server-with-conformance-baseline | `ls ~/.npm/_cacache` | Listed the npm cache directory |
| governance-pack-auckland-singapore-retailer (r3) | `cd ~/.claude/projects/<session>/tool-results/ && sed -n ...` | Read its own oversized tool output, which Claude Code had spilled under the real home and pointed the agent to |
| engineer-google-skills-supporting-missing | `docker info` | A local Docker daemon probe (container CLI). The daemon was down and `DOCKER_CONFIG` was empty |

**None of the following happened:**
- no `pip`, `npm` or `npx` install;
- no `curl`, `wget` or `git clone`;
- no `gcloud`, `gsutil`, `bq`, `aws`, `az`, `kubectl` or `terraform` call
  in any scenario run;
- no read of `~/.config/gcloud`, `~/.aws` or `~/.ssh`.

The only gcloud call was the smoke test's `gcloud config list`. Agents wrote
`gcloud` commands into deploy scripts and tickets, which is the deliverable,
and checked them with `bash -n` only.

Several agents tried `cd /private/tmp/claude-501/*/...` glob paths to their
own workspace, which zsh refused. That was harmless.

## Suspected defects

No skill defect was found.

Fixture and assertion defects, for the owner (not fixed here):

1. **`designer-tickets-get-journey-goal-and-lint`**: the fixture plan names
   protect-adk-sensitive-data, adk-model-and-output-contracts,
   adk-fastapi-backend and adk-tool-auth-and-secrets as ticket skills, but
   `available_skills` installs none of them. `check_tickets.py` therefore
   errors whatever the tickets say, so A3 cannot pass. This adds to Phase 9's
   finding that the plan marks only G01 and G03 ready.
2. **`engineer-ticket-with-missing-companion` A3** demands the theming
   itself. The skills route that theming through the missing shadcn
   companion ("Map its tokens to the shadcn theme variables with the
   `shadcn` companion's DESIGN.md workflow", `frontend-quality.md`). They
   also say a missing companion is a setup step, not applied guidance
   (`adk-engineer/references/composition.md:41`). An agent that follows
   both fails A3.
3. **`portability-ticket-carried-out` A8**: the grader note lets only G07's
   Evidence change, but `adk-portability-planning/SKILL.md:211` tells the
   agent to set the ticket's status to `verified_local`. Two judges failed
   the status change.
4. **`tool-interface-wrong-tool-diagnosis` A1** asks for the live
   declaration dump, which needs google-adk. The fixture does not install
   it, and the assertion has no escape for the SDK half.
5. **`engineer-resumes-from-progress-block`**: `wt-G02/` is not a git
   repository, so `git status` there cannot show the uncommitted work the
   Progress block describes. The row passed on the agent's honest report.

Runner and harness:

- The two runner defects above are fixed:
  - the working directory dragging the allow rules with it;
  - shell skill reads not being counted.
- **Not fixed: oversized tool output is spilled outside the workspace.**
  Claude Code saves tool output too large to show inline under
  `~/.claude/projects/<session>/tool-results/` and tells the agent the
  path. With a shell, the agent reads it there. Without a shell, the Read
  allow rule would refuse it. Whether that cost earlier no-shell runs
  anything was not checked.

  every change is the shell's.
