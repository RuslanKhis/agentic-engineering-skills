# Held-out activation · 27 October 2026

Every activation case before this change was written by someone who had read
the skill descriptions. Forty of them were written alongside the routing fixes
they test ([skill boundaries](skill-boundaries-2026-10-27.md)). A pass on those
cases shows that a description covers the requests its authors had in mind. It
does not show that the description reaches requests nobody wrote it for. This
change adds a held-out split of 78 cases, generated by a model that saw
neither the descriptions nor the repository. It also measures the split
without changing any description.

## What changed

- **A `split` field on every case.** All 154 existing cases are `dev`. The
  field was added as text after each `rationale` line; no other byte of an
  existing case changed. The 78 new cases are `heldout`.
- **`scripts/check_repo.py`** now requires `split` to be `dev` or `heldout`
  on every case. It also requires every skill to have at least one held-out
  positive and one held-out near-miss. This replaces the optional
  `train`/`held-out` field, which no case used.
- **`scripts/run_activation.py --split dev|heldout|all`** (default `all`)
  selects cases. The corpus hash still covers the whole file. Each result row
  records its split, `summary.by_split` counts grades per split, and the
  printed summary has a table row per split. Batches exported with one split
  will not import under another.
- **Tests:** `tests/test_check_repo.py` covers a required split, a value
  outside the two allowed, and a missing held-out positive or near-miss.
  `tests/test_run_activation.py` covers filtering, the unchanged hash, the
  per-split summary and the import mismatch.
- **Rules** in [checking skill quality](skill-quality.md#keep-a-held-out-split)
  and `CONTRIBUTING.md`: the held-out split is never used while editing a
  description. It is re-run once the change is final. When its cases leak into
  description work, it is refreshed with a new generation.

## How the held-out cases were made

**Briefs.** I wrote one brief per skill (26), describing what kind of engineer
comes with what problem. I wrote them from each skill's purpose and avoided
the description's phrasing and key nouns where I could. Product names a
developer would type stayed in, such as FastAPI, BigQuery, Gemini, AWS and
Kubernetes. The briefs are in
[briefs.json](artifacts/heldout-activation-2026-10-27/briefs.json).

**Generator.** Each brief went to its own fresh session of
`claude-opus-5-5`, through the repository's claude-cli backend
(`call_claude_cli` in `scripts/model_backends.py`). The selector uses the same
backend, so the generator was isolated the same way. The session ran in a new
empty temporary directory, with the prompt on stdin:

```bash
claude -p --model claude-opus-5-5 --output-format json \
  --system-prompt "You write realistic test requests that software developers type to an AI coding assistant. Answer with JSON only." \
  --tools "" --safe-mode --disable-slash-commands --no-session-persistence \
  --strict-mcp-config --setting-sources ""
```

The prompt is in
[generate.py](artifacts/heldout-activation-2026-10-27/generate.py). It holds
one brief and a one-line note that the users build Python agents with Google's
Agent Development Kit on Google Cloud. It asks for two requests that fit and
one that sounds related but belongs elsewhere, with the other help named in
plain words. It asks for varied tone, some vague requests and some with
irrelevant detail. The session never saw a skill name, SKILL.md, a
description, an existing case or the repository.

Before generating, I ran an isolation check with the same flags and system
prompt and asked the session to list every tool, skill, instruction and file
it had. It answered empty lists, and the whole call used 690 input tokens
([isolation-check.json](artifacts/heldout-activation-2026-10-27/isolation-check.json)).
The raw replies, each with its exact prompt, command, model and usage, are in
[raw/](artifacts/heldout-activation-2026-10-27/raw/). Generation cost
$0.54.

**Labels.** A "fits" request became a positive for its brief's skill. An
"elsewhere" request became a near-miss for its brief's skill, but only when
every plausible destination lay outside that skill. If the brief's own skill
was one plausible destination, I dropped the request rather than guess.
[labels.json](artifacts/heldout-activation-2026-10-27/labels.json) records
each label, its source request and where each near-miss belongs.
[build_cases.py](artifacts/heldout-activation-2026-10-27/build_cases.py)
copied the kept requests verbatim into `evals/activation.json` with ids
`<skill-short>-heldout-<n>`. Each rationale begins "held-out, generated from a
neutral brief".

**Kept and dropped.** Round 1 produced 78 requests, and 77 were kept. One was
dropped: frontend's near-miss about streamed replies buffered behind a load
balancer. The generator sent it to infrastructure, but streaming to the
browser is plausibly the frontend skill's own concern. Frontend then had no
near-miss, so its brief went unchanged to a second fresh session. Only that
session's near-miss was used; its two positives were not needed. In total, 81
requests were generated, 78 were kept (52 positives and 26 near-misses, three
per skill), one was dropped as ambiguous and two were unused.

## Results

Runs used `scripts/run_activation.py --backend claude-cli --split heldout`.
Sonnet 5.5 ran with `--repeat 2` and Haiku 5.5 with `--repeat 1`, at the
default seed and batch size. The dev split was re-run the same way for a
like-for-like comparison. All four runs used catalogue `3295a5a6cc395a72` and
corpus `e57980b8cbe62338`, and no description changed. The runs were made
from the uncommitted working tree on top of `c938155`, which is the commit
the results files record.

### Held-out cases that did not pass

No description was changed for any of these. Each entry names the skill's
owner as the one to decide.

- **api-heldout-3** (safe-api-tool-calls, near-miss). The request: Gemini
  returns 429 RESOURCE_EXHAUSTED under load, so should I add retries and
  backoff with the Runner? Results: Sonnet FAIL then PASS, Haiku FAIL. Sonnet
  gave primary safe-api with supporting guardrails: "Handling 429 errors from
  Gemini with retries and backoff is selective retry policy." Haiku gave
  primary safe-api with supporting model-and-output: "Retry and backoff policy
  for failing API calls belongs to safe-api-tool-calls, and model failover for
  Gemini 429s falls under the model-and-output skill."
- **engineer-heldout-1** (adk-engineer, positive). The request: a "saved
  conversations" feature across the React UI, FastAPI endpoints, a persistent
  session service and Cloud Run, asking to "map out what's involved". Sonnet
  gave FAIL then PASS; its failing answer had primary adk-system-designer,
  with frontend and memory supporting: "a cross-cutting design task".
- **guardrails-heldout-3** (adk-operational-guardrails, near-miss). The
  request: break down Vertex AI spend per agent and set a billing budget
  alert. Sonnet gave PARTIAL then PASS, with primary observability and
  guardrails supporting: "enforcing staged cost controls is only secondary".
- **model-output-heldout-3** (adk-model-and-output-contracts, near-miss). The
  request: the agent returns valid JSON, but Agent Runtime wraps it in an
  event structure that the frontend cannot read. Sonnet gave PASS then
  PARTIAL, and Haiku PARTIAL. Both chose primary frontend-integration with
  model-and-output supporting, "with output schema handling as secondary".
- **frontend-heldout-3** (adk-frontend-integration, near-miss). The request:
  the agent forgets earlier turns in a long VertexAiSessionService session;
  "is this a frontend thing?" Haiku gave PARTIAL, with primary memory and
  frontend supporting, "a supporting check on session continuation". The
  prompt itself asks about the frontend.
- **workflow-heldout-1** (adk-workflow-design, positive). The request: a
  SequentialAgent's `output_key` value arrives as a literal `{research_notes}`
  or a state KeyError in the next sub-agent. Haiku gave PARTIAL, with primary
  adk-agent-instructions and workflow supporting: "templating ... KeyError
  [is] session-state templating ... the output_key handoff timing ... is a
  workflow concern."

## What this suggests

- **Retries on the model's own API look unowned.** api-heldout-3 failed on
  both models. safe-api-tool-calls claims "selective retries" for
  "unreliable API calls", and its exclusion "model-only tuning
  (adk-model-and-output-contracts owns model settings)" does not clearly
  cover retry and backoff on the model endpoint's 429s.
  adk-model-and-output-contracts names "model failover" but not retries or
  quota. The label could be argued the other way too, so the owners of the
  two skills should decide which one owns this request. That decision should
  then be written into one description or the other, and tested with a new
  dev case.
- **Planning a cross-cutting feature sits between adk-engineer and
  adk-system-designer.** engineer-heldout-1 failed once. adk-engineer says
  "when a change spans several ADK concerns". adk-system-designer says
  "cross-cutting architecture review". A request to scope one feature across
  several areas matches both. This is one miss in two repeats: worth
  watching, not yet a gap.
- **The `{key}` KeyError between sequential agents is claimed twice.**
  adk-agent-instructions names "templating KeyErrors" and adk-workflow-design
  names "session-state handoffs". Haiku chose the instructions skill. The
  ownership map may want a line for this case.
- The model-output, guardrails and frontend PARTIALs put the right skill
  first and the brief's skill as support for a detail the prompt mentions.
  Neither suggests a gap.

## Limits

- **The near-misses are easier than the dev ones.** The generator's
  "elsewhere" requests tend to sit far from the boundary. Six of the 26 are
  IAM or permission errors on a deployed agent, and three more are runtime
  timeouts or secrets. The dev near-misses were written on the contested
  boundaries. The held-out positives are the stronger evidence of
  generalisation.
- **Only one generator model.** All requests came from Opus 5.5. Its idiom,
  such as demo deadlines, "ugh" openers and Agent Engine phrasing, shapes the
  whole set. A refresh could alternate generator models.
- **I wrote the briefs and labelled the cases, and I had read the
  descriptions.** Product names in the briefs leak some vocabulary. The
  labels mostly follow the generator's own "fits" or "elsewhere" judgement,
  and the one judgement call (a drop) is recorded.
- **The sample is small.** It has 78 cases and three runs. One flip moves a
  skill's rate a lot. A description-only selector says nothing about a
  host's own loader.
