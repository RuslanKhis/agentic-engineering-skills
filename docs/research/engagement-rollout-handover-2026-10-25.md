# Engagement scoping, rollout and operations handover

Research date: 25 October 2026. Sources were read on that date; downloaded
files were treated as data only.

The toolkit takes an agency or consultancy from discovery to a measured
production result, but three business documents sat outside it: the
statement of work that turns the design and plan into a contract, the
rollout pack that gets the people in the workflow to use the agent, and the
handover that lets the client's own IT team run it. Each was being written
by hand from the same artefacts the skills already produce (the discovery
brief, the contracts table, the plan's schedule block and cost ledger), so
the figures drifted from the plan and the promises drifted from the
contracts. This note records the sources read, the decisions taken and what
was left out.

## Where each capability lives, and why

| Capability | Home | Reason |
| --- | --- | --- |
| Proposal, statement of work, change request, data-request letter | `adk-system-designer` (reference, three assets, `check_sow.py`) | Every input is a designer artefact: objectives from the brief's outcome measure, deliverables from goals, out-of-scope from the Later list, client dependencies from calendar waits, effort from `check_schedule.py`. The checker imports the schedule parser from the same `scripts/` directory, so hours cannot disagree with the plan. A new skill would duplicate the plan's reading rules. |
| Rollout and adoption pack | `adk-presenter` (rollout mode: reference, template, `check_rollout.py`) | Considered: a new skill, a designer reference, a presenter mode. The pack is documents for people, written from recorded evidence and the contracts, with the same discipline the presenter already enforces (no claim without a record; measured, estimated and hypothesised voices kept apart; separate versions per audience). The presenter never changes code, and its readers (sponsor, managers, frontline users) are audiences it already distinguishes. A new skill would add a 24th package, a router row, a description competing with the presenter's for "write the materials for the launch", and count changes across the README, for a set of documents produced once per go-live. The designer is the wrong home because rollout happens after the build, from evidence the designer does not hold. The cost of the choice: the presenter's description grows (744 to about 980 characters) and its job is no longer only "win a decision"; the description names the rollout pack explicitly so routing does not depend on that phrase. |
| Operations handover and agent postmortem | `adk-agent-observability` (reference, two assets) | The incident note, the debugging runbook, alert design and feedback capture already live here; the postmortem extends the incident note rather than restating it, and support tiers are routed by the alerts this skill defines. `deploy-adk-on-google-cloud` was the alternative because access transfer touches IAM, secrets and billing; it is named as the supporting skill for those commands, since the handover decides who owns what, not how a role is granted. |

## What the toolkit already says, so the new material links instead

- The incident note (observability `debugging-runbook.md` §5): alert, trace id, invocation id, root-cause category, fix, regression case id. The postmortem template opens with exactly those fields and adds what the note lacks.
- Incident regressions (evaluation skill, `deterministic-tests.md` and `evaluation-design.md`): `fail_to_pass` and `pass_to_pass` lists, a base-commit run and a reference-fix run. The postmortem's regression section asks for those, by name.
- Feedback capture (observability `feedback-capture.md`): the record keyed by `session_id` and `invocation_id`, categories `wrong_answer`, `tool_failed`, `too_slow`, `unsafe`, `other`, a sink to BigQuery. The rollout pack's "report a problem" control maps user-facing labels onto these categories instead of inventing a second channel.
- Model lifecycle (`adk-model-and-output-contracts`, `assets/model-lifecycle-*.json`): the handover's model-retirement calendar reads it by reference and copies the dates of the pinned model and judge only.
- Production-sample refresh of evaluation sets (`adk-release-engineering`, `production-feedback.md`): the handover names its owner and cadence.
- Plan measurement and incident records (`M<n>`, `I<n>`): the hypercare exit test and the postmortem write into them, so `adk-presenter` can cite them at the results review.

## Decisions on content

- **Acceptance criteria for probabilistic output.** A criterion names a pass threshold, the number of cases, who agreed the cases, the method and the date, and the contracts it proves, e.g. "≥ 85% of 40 gold cases agreed with the client's claims leads pass the grounded-answer rubric, measured by `adk eval` on the release build by 4 December 2026". "The agent answers correctly" fails the checker. A small case set makes the threshold coarse (one case is 2.5 points on 40), so the reference says to agree the sample size with the threshold, not after it. This follows the MCC-AI-Light's own structure: accuracy metrics are an annex the parties fill, not a promise in the body.
- **Rates.** The SOW multiplies the schedule check's hours by a rate the user supplies; without one, fee cells stay `rate to be supplied` and the checker reports it. Run cost comes from the plan's cost ledger and resource rows, labelled as an estimate with its pricing date.
- **Client dependencies.** Every calendar wait and outside prerequisite in the plan (SME hours, data access, IAM grants, a security review) becomes a dated, owned dependency with what it blocks; a slip past its date is a change-request trigger, so the agency's schedule risk is visible in the contract.
- **AI disclosure.** Article 50 has applied since 2 August 2026, verified on the consolidated text. Whether the client is the provider (puts the system into service under its own name) is a contract question the SOW checklist raises; the disclosure text itself is written for any EU-facing interaction unless the user records why it is obvious. Outside the EU the text is still recommended and marked as not legally required.
- **Adoption metrics.** "Active user" is defined against the assigned population and a window, from completed invocations, not log-ins; a counter-metric comes from the discovery brief. A rollout without a counter-metric rewards forcing use.
- **Postmortem harm assessment.** Agent incidents differ from service outages: the service can be up while the agent gives wrong, unsafe or unauthorised answers. The template asks for affected users and invocations by query, harm category and severity, whether any effect reached the outside world, and the notification decision with the person who made it.

## Left out

- The 2025 MCC-AI commentary was not read in full; the reference cites the clauses themselves.
- No legal advice: the SOW reference says to have counsel review the AI terms and to treat the checklist as questions, not clauses.
- Prosci's percentages and the secondary-source BCG figures that the press release does not carry.
- GitHub-hosted sources: none of these sources is a repository, so `docs/research/source-register.json` (which tracks repositories only) gains no rows; the dated table above is the record.
