# External sources to integrate — research report, 21 October 2026

*Author's research memo. Input to [the integration prompt](../testing/external-sources-integration-prompt.md). Its claims are dated 21 October 2026, were gathered from documentation and source without execution, and are to be verified against the primary source on the day they are acted on; the report's own "What this research could not verify" section lists the known gaps.*

# Conformance suites and Google recipes lead integration

The repositories most worth integrating fall into three groups, and the first is mostly Google's own. It is **google/adk-recipes** (renamed from adk-samples), **googleapis/mcp-toolbox** (renamed from genai-toolbox), the **BigQuery Agent Analytics SDK**, the **`agents/` subtree of GoogleCloudPlatform/generative-ai**, the **ADK 2.12 source tree**, and **kubernetes-sigs/agent-sandbox**, which backs GKE Agent Sandbox. Between them they hold ADK-native content the 22 skills have not yet absorbed: an ambient quality agent, event-driven human-in-the-loop (HITL) workflows, managed RAG, a three-layer read-only SQL defence, evaluation over production traces, and a new sandbox and execution-environment layer. The second group is the **protocol conformance tools**: the official MCP conformance suite, the A2A TCK, AG-UI 1.0's `verifyEvents`, and the OpenTelemetry GenAI reference scenario for google-adk. These let adk-system-designer write acceptance checks as pinned commands with exit codes instead of prose. The third group fills gaps that ADK's own stack leaves. tau2-bench and Inspect AI cover pass^k, grading on end state, and agreement between judges. promptfoo asserts trajectories on ADK's native spans and gives CI exit codes. AgentDojo, Snyk Agent Scan, MITRE ATLAS and the CoSAI Risk Map supply security fixtures and finding IDs. Temporal and DBOS cover crash recovery. Before integrating any of this, fix fourteen facts in the current skills that have already drifted, led by ADK 2.12.0's security fixes, an `adk eval` exit code whose behaviour now depends on the build, and the ADK 2.9.0 rule that failed workflow nodes re-run on resume. For the designer, the main changes are a `reference_patterns` ticket field, `parallel_safe`/`touches`/`constraints`/`docs` lines, and named companion skills. Almost everything found is MIT or Apache-2.0. The traps are share-alike, non-commercial and Elastic licences, plus the rule that Apache notices must travel inside each skill folder.

Rows 4 through 6 matter most because they change behaviour the skills assert. Row 5 is the subtle one. A CI gate that trusts `adk eval`'s exit code is wrong on every released version. A gate that wraps it in pytest because "it always exits 0" becomes redundant once a team builds from a commit containing `c2ff634`. The safe wording is version-conditional: run a deliberately failing case on the pinned version, and keep the pytest gate as primary, because `adk eval` still has no repetition and no pass threshold below 100% ([cli_tools_click.py](https://github.com/google/adk-python/blob/main/src/google/adk/cli/cli_tools_click.py)). Row 4 also argues for raising the version floors in adk-agent-security and adk-tool-auth-and-secrets above the 2.12 fixes for OAuth secret leakage and principal-only user ids.

## Google's own repos hold most of the missing ADK-native content

### adk-recipes adds an ambient quality agent, event-driven HITL and managed RAG

**adk-recipes** is organised in three layers. `core/` holds canonical patterns curated by the agents-cli team. `contrib/` holds deployable vertical agents in Python, Go, Java, Kotlin and TypeScript. `plugins/` holds installable skills that ship a `SKILL.md` with an `EVAL.yaml`; the retail skill halts below an 80% pass target. Nine maintainer skills live in `.agents/skills` ([README](https://github.com/google/adk-recipes/blob/main/README.md)). The agents-cli catalog says "Study and adapt — don't scaffold from a recipe" ([samples.md](https://github.com/google/agents-cli/blob/main/skills/google-agents-cli-adk-code/references/samples.md)). The repo itself warns that recipes are "not production use" ([README](https://github.com/google/adk-recipes/blob/main/README.md)), so any ticket that copies a recipe pattern should repeat that disclaimer. The user has already mined four core recipes: long-horizon-harness, cross-session-memory, safety-plugins and oauth-user-consent-flow. **Eight have zero citations**: rag-vector-search, rag-agent-search, ambient-expense-agent, deep-search, staged-ui-widgets, multiformat-hybrid-rag, high-volume-document-analyzer and llm-auditor ([core/python](https://github.com/google/adk-recipes/tree/main/core/python), [contrib/python](https://github.com/google/adk-recipes/tree/main/contrib/python)).

**AQuA, the Ambient Quality Agent** (v0.1.0, 8 Oct), is the most consequential of these. It runs beside a production ADK agent and reads conversations from three possible sources: the BigQuery Agent Analytics plugin, a Cloud Trace `_AllSpans` dataset, or agents-cli default logging. It evaluates them on a schedule, after a deploy, or on demand, using an LLM review, published deterministic Python checks, or Gemini-platform eval metrics. It deduplicates failures into insights marked `NEW`/`RECURRING`/`RESOLVED` and runs root-cause analysis against a snapshot of the agent's source. It installs as an agents-cli extension (`--apply-aqua`, `--deploy-aqua`, `agents-cli aqua attach`) and ships an IAP-protected Cloud Run dashboard ([AQuA README](https://github.com/google/adk-recipes/blob/main/core/python/ambient-quality-agent/README.md)). The toolkit should not rebuild it. adk-agent-evaluation and adk-release-engineering should own two things instead: the decision on whether AQuA insights gate a release, and the rule that missing or failed AQuA evaluations count as incomplete evidence.

**ambient-expense-agent** shows the "deterministic first, LLM for ambiguity" shape adk-workflow-design teaches. Pub/Sub events drive a graph-based ADK 2.0 `Workflow`. Low-value expenses are approved in code, and only high-value cases reach an LLM, which pauses for human approval. The Pub/Sub wiring is Terraform ([recipe README](https://github.com/google/adk-recipes/blob/main/core/python/ambient-expense-agent/README.md)).

For adk-memory-architecture there are three managed-RAG recipes:

- **rag-vector-search** pairs Vector Search 2.0 with a KFP ingestion pipeline that handles chunking, BigQuery staging and server-side embeddings.
- **rag-agent-search** uses managed Discovery Engine with a GCS connector and Terraform ([samples.md](https://github.com/google/agents-cli/blob/main/skills/google-agents-cli-adk-code/references/samples.md)).
- **multiformat-hybrid-rag** is the managed twin of the skill's local RRF. It converts PDFs (through Gemini multimodal) and Office files (through LibreOffice) to markdown. It prepends "Gemini-generated per-chunk context" before embedding, fuses BM25 and semantic results by Reciprocal Rank Fusion on Vector Search 2.0, and serves an ADK agent, a REST API and an MCP server from one Cloud Run service, with evalsets included ([README](https://github.com/google/adk-recipes/tree/main/contrib/python/multiformat-hybrid-rag)).

### Horizon's evalsets, guard plugins and memory loop are still unabsorbed

The toolkit cites long-horizon-harness ("Horizon") for its context window, instruction tiers, guard chain and tool-result pruning. Four other parts of it are still unused:

1. **Eighteen evalsets** in `tests/eval/evalsets/`, among them `clarify_gate`, `compression_quality`, `exfil_injection`, `guardrail_halt`, `memory_recall` and `tool_selection_core`. They are scored with `rubric_based_final_response_quality_v1` at threshold 0.8, using a pinned `gemini-3.7-flash` judge ([evalsets](https://github.com/google/adk-recipes/tree/main/core/python/long-horizon-harness/tests/eval/evalsets)). These are ready fixture templates for adk-agent-evaluation and adk-agent-security.

2. **The guard modules** under `horizon/guardrails/`, which are ADK `BasePlugin` code rather than prose:

   - `GuardrailsPlugin` wraps three halt guards "so they share a turn boundary".
   - `RepeatedFailureGuard` halts after N tool failures with an identical signature.
   - `NoProgressGuard` halts after N identical model texts.
   - `exfil_guard` uses per-session grants.
   - `default_policies.jsonl` lists destructive commands and protected paths, including `*/.config/gcloud/*` and `*/.kube/*` ([Horizon tree](https://github.com/google/adk-recipes/tree/main/core/python/long-horizon-harness)).

   adk-operational-guardrails should compare these with its own repeated-tool protection and adopt the identical-signature hash if it counts differently.

3. **The memory write-back loop** in `docs/memory.md`:

   - a throttled after-turn flush;
   - a per-turn background judge fork that decides what is worth saving without blocking the response;
   - a pre-compaction flush "so facts aren't lost when old turns are summarized away";
   - a nightly "dream" pass that consolidates a structured profile.

   It also sets user and agent write scopes (`USER_CHAR_LIMIT = 1375`) and has a "Honesty callouts" section listing what is gated or best-effort ([memory.md](https://github.com/google/adk-recipes/blob/main/core/python/long-horizon-harness/docs/memory.md)). A grep of the toolkit finds no "pre-compaction", "consolidat" or "dream".

4. **`AGENTS.md`**, which has a "Transferable vs Horizon-specific" column, the per-stage callback chain, an `ask_is_deny=True` rule for headless children, and a note on "Why `pool_pre_ping` is not enough" ([AGENTS.md](https://github.com/google/adk-recipes/blob/main/core/python/long-horizon-harness/AGENTS.md)).

`docs/security-model.md` adds a "layered adoption ladder": hard deny versus soft ask, argv classification for command safety, and resurfacing of child permissions ([security-model.md](https://github.com/google/adk-recipes/blob/main/core/python/long-horizon-harness/docs/security-model.md)). For adk-frontend-integration, the contrib **staged-ui-widgets** agent answers "with real interface — product cards, a comparison table, a delivery timeline, a spend chart — rendered as A2UI" ([README](https://github.com/google/adk-recipes/blob/main/contrib/python/staged-ui-widgets/README.md)).

The largest content gap is execution environments. ADK Python now has:

- `src/google/adk/environment/`;
- an `EnvironmentToolset` with execute, read_file and edit_file tools;
- an Agent Engine sandbox environment under `integrations/vmaas/`, including `sandbox_computer.py`;
- a Cloud Run sandbox code executor;
- integrations for Daytona, E2B and OpenSandbox;
- samples under `contributing/samples/environment_and_skills/` ([src tree](https://github.com/google/adk-python/tree/main/src/google/adk), [samples](https://github.com/google/adk-python/tree/main/contributing/samples/environment_and_skills)).

The security skill tabulates only the six classic code executors ([agency-and-output.md](https://github.com/RuslanKhis/agentic-engineering-skills/blob/main/skills/adk-agent-security/references/agency-and-output.md)). Selection guidance needs two caveats. Daytona's public repo says "no longer maintained… core development has moved to a private codebase" as of June 2026 ([daytonaio/daytona](https://github.com/daytonaio/daytona)). E2B and Daytona also move execution off GCP. `GkeCodeExecutor(executor_type="sandbox")` imports `k8s_agent_sandbox.SandboxClient`, which ties the GKE option to kubernetes-sigs/agent-sandbox ([adk-python](https://github.com/google/adk-python)).

The same tree has more that the skills can use directly:

- **Maintainer skills.** `adk-agent-builder/references/testing.md` states concrete flake rules ("One `InMemoryRunner` and one session per test", "A unique `app_name` per test", "Any LLM agent feeding a `JoinNode` needs `output_schema=`"), checked against 2.6.2 ([adk-agent-builder](https://github.com/google/adk-python/tree/main/.agents/skills/adk-agent-builder)). These are deterministic Runner-test rules adk-agent-evaluation should cite.
- **Fixture-grade samples.** `contributing/samples` has `evaluation/`, `hitl/` (classifier_tool_gate, tool_confirmation, request_input_tool), 27 `workflows/` (retry, dynamic_fan_out_fan_in, request_input_rerun), `a2a/`, `mcp/` (mTLS, service-account auth) and `plugins/plugin_reflect_tool_retry` ([samples](https://github.com/google/adk-python/tree/main/contributing/samples)).
- **BigQuery skills bundled in the SDK.** `bigquery-ai-ml` and `bigquery-graph` ship as `SKILL.md` folders ([BigQuery skills](https://github.com/google/adk-python/tree/main/src/google/adk/integrations/bigquery/skills)). BigQuery vector or AI-function tickets should cite them as operating references.
- **Primitives the skills never name.** `Runner.rewind_async` is ADK's time-travel and regenerate primitive ([runners.py](https://github.com/google/adk-python/blob/main/src/google/adk/runners.py)). `_tool_call_integrity_plugin` "stamps function calls and verifies them" ([plugins](https://github.com/google/adk-python/tree/main/src/google/adk/plugins)). `google.adk.platform.time`/`uuid` exist so Temporal can map them to deterministic replay ([platform](https://github.com/google/adk-python/tree/main/src/google/adk/platform), [Temporal blog](https://temporal.io/blog/google-adk-temporal-integration-bts)). 2.11.0 added a SQLite memory service ([CHANGELOG](https://github.com/google/adk-python/blob/main/CHANGELOG.md)).

Create, update and delete appear only with `enable_data_agent_modification=True`, `max_query_result_rows` defaults to 50, and its credentials config is "experimental" ([adk.dev data-agent](https://adk.dev/integrations/data-agent/)).

### mcp-toolbox and the BigQuery Analytics SDK fill the SQL and telemetry read paths

**mcp-toolbox's "Read-Only Tools" document** is the strongest single external artefact for adk-sql-agent-engineering. It describes three layers of defence: a session lock at protocol and engine level, tool suppression, and dynamic MCP manifest annotations. It also explains why soft locks fail, with bypasses that translate directly into deterministic test fixtures: `WITH d AS (DELETE FROM users RETURNING *) SELECT * FROM d;`, UDF calls with side effects, `SET default_transaction_read_only` escaped by `COMMIT;` chaining, and connection-pool poisoning under PgBouncer ([read-only.md](https://github.com/googleapis/mcp-toolbox/blob/main/docs/en/documentation/configuration/security/read-only.md)).

Configuration enforces what the skill currently enforces in code:

- With `readOnly: true` and `writeMode: blocked`, `bigquery-execute-sql` allows only `SELECT`. It supports `allowedDatasets` and `dry_run`, and "conflicting configurations… are rejected during server startup" ([bigquery-execute-sql](https://github.com/googleapis/mcp-toolbox/blob/main/docs/en/integrations/bigquery/tools/bigquery-execute-sql.md)).
- `templateParameters` are flagged "more vulnerable to SQL injections" ([postgres-sql](https://github.com/googleapis/mcp-toolbox/blob/main/docs/en/integrations/postgres/tools/postgres-sql.md)).
- The new **`secure` parameters** are supplied out of band and "isolated from LLM context". A model that tries to supply one through standard arguments gets a tool execution error. They require MCP protocol 2026-07-28 ([tools configuration](https://github.com/googleapis/mcp-toolbox/blob/main/docs/en/documentation/configuration/tools/_index.md)).

The SQL skill never names Toolbox ([SKILL.md](https://github.com/RuslanKhis/agentic-engineering-skills/blob/main/skills/adk-sql-agent-engineering/SKILL.md)). It needs a Toolbox branch checklist:

- read-only source plus `allowedDatasets`;
- `parameters` only, with `templateParameters` used only behind `allowedValues`, `escape` and a reviewer sign-off;
- tenant ids as `secure` params;
- the prebuilt free-form `bigquery-execute-sql` excluded unless the ticket justifies it.

The Toolbox Model Armor doc also screens tool results flowing back to the model ([model-armor.md](https://github.com/googleapis/mcp-toolbox/blob/main/docs/en/documentation/configuration/security/model-armor.md)). That fills the gap the ADK Model Armor plugin leaves when it skips `function_response` parts ([ADK Model Armor docs](https://adk.dev/integrations/model-armor/index.md)).

**BigQuery-Agent-Analytics-SDK** (v0.6.1) is the read side of the `agent_events` table that ADK's `BigQueryAgentAnalyticsPlugin` writes ([README](https://github.com/GoogleCloudPlatform/BigQuery-Agent-Analytics-SDK/blob/main/README.md)). It provides:

- trace reconstruction;
- system metrics (latency, tool error rate, TTFT, cost);
- grader composition;
- "eval suite lifecycle management with graduation and saturation detection";
- "drift detection for golden vs production question distributions";
- job labels for spend attribution;
- deployable artefacts: continuous-query SQL for Pub/Sub alerting and session scoring, `examples/evalbench_score_gate.sh`, and a Claude Code tracing plugin ([repo tree](https://github.com/GoogleCloudPlatform/BigQuery-Agent-Analytics-SDK)).

The observability skill says only that the SDK exists ([bigquery-analytics.md](https://github.com/RuslanKhis/agentic-engineering-skills/blob/main/skills/adk-agent-observability/references/bigquery-analytics.md)). The toolkit covers writing analytics. It does not cover alerting on them, gating releases on them, or detecting drift from them.

### generative-ai, agent-sandbox and CoSAI supply blueprints, clusters and vocabulary

The `agents/` subtree of GoogleCloudPlatform/generative-ai holds four security and quality blueprints:

- **`zero-trust-agents`**: KMS-signed database writes, a gVisor sandbox, and a deterministic input/output regex gateway backed by CI tests ([README](https://github.com/GoogleCloudPlatform/generative-ai/blob/main/agents/adk/zero-trust-agents/README.md)).
- **`zero-trust-agents-2`**: a four-act attack on a refund agent, countered by Model Armor, an intent-aware judge ("Semantic Governance Policies") and behavioural "Agent Anomaly Detection" that catches "micro-refund smurfing" ([README](https://github.com/GoogleCloudPlatform/generative-ai/blob/main/agents/adk/zero-trust-agents-2/README.md)).
- **`agent-quality-flywheel`**: pairs an LLM rubric metric with a deterministic regex metric through `agents-cli eval run`, going "from 0 of 6 to 6 of 6" ([README](https://github.com/GoogleCloudPlatform/generative-ai/blob/main/agents/adk/agent-quality-flywheel/README.md)).
- **`contract-compliance-pipeline`**: hands off over `RemoteA2aAgent` to a deterministic Go policy agent on the principle "LLMs are useful for ambiguity. Deterministic agents should enforce hard policy" ([README](https://github.com/GoogleCloudPlatform/generative-ai/blob/main/agents/adk/contract-compliance-pipeline/README.md)). This is a clean adk-system-designer pattern for A2A topologies.

## Conformance suites turn protocol acceptance into pinned commands

### MCP's conformance suite needs a baseline for business servers

MCP's current revision, **2026-07-28**, retires `initialize` and `Mcp-Session-Id`. It replaces server-initiated sampling and elicitation with Multi Round-Trip Requests (`input_required`), and it deprecates Dynamic Client Registration in favour of Client ID Metadata Documents ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)). Google's blog notes that the stateless core enables Cloud Run scale-to-zero with no Redis session store ([Google Developers Blog](https://developers.googleblog.com/scaling-ai-agent-infrastructure-with-the-mcp-stateless-updates/)).

**`@modelcontextprotocol/conformance`** (0.2.0-alpha.12) has a server mode that runs against a URL, and `--requirements <rev>` runs exactly what a frozen revision requires ([README](https://github.com/modelcontextprotocol/conformance/blob/HEAD/README.md)). Its expected-failures YAML exits 1 on a new regression *and* on a stale baseline entry, every scenario validates every JSON-RPC message against the spec schema, and it ships a GitHub Action ([action.yml](https://github.com/modelcontextprotocol/conformance/blob/HEAD/action.yml)).

The catch is that the `tools`, `stateless` and `prompts` scenarios call fixture tools from the reference "everything" server ([tools.ts](https://github.com/modelcontextprotocol/conformance/blob/HEAD/src/scenarios/server/tools.ts)). A business ADK server fails them by design, and those failures must be recorded per check in a reviewed baseline. The protocol-level scenarios need no fixtures and are the real test: `dns-rebinding`, `http-standard-headers`, `caching` and `json-schema-2020-12`. The python-sdk's own CI keeps one baseline file per revision, which is the layout to copy ([python-sdk conformance](https://github.com/modelcontextprotocol/python-sdk/tree/HEAD/.github/actions/conformance)).

The Inspector v2 CLI (`--method initialize`, `--method tools/list`) gives an independent cross-check of the skill's pinned tool manifest. It stores OAuth tokens in the OS keychain by default, which matters on shared CI runners ([Inspector README](https://github.com/modelcontextprotocol/inspector/blob/HEAD/README.md)).

The spec itself also supplies tool-design facts for adk-tool-interface-design:

- `readOnlyHint`, `destructiveHint`, `idempotentHint` and `openWorldHint` annotations ([schema.ts](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/HEAD/schema/2026-07-28/schema.ts));
- deterministic `tools/list` order and any JSON Schema 2020-12 keyword ([2026-07-28 changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/HEAD/docs/specification/2026-07-28/changelog.mdx));
- tool-name guidance (SEP-986), and input-validation failures returned as tool execution errors "to enable model self-correction" (SEP-1303) ([2025-11-25 changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/HEAD/docs/specification/2025-11-25/changelog.mdx)).

For adk-tool-auth-and-secrets, `ext-auth` adds Enterprise-Managed Authorization (ID-JAG) and OAuth client credentials ([ext-auth](https://github.com/modelcontextprotocol/ext-auth/tree/HEAD/specification)). FastMCP 4 is "era-gated": `ctx.elicit()` raises on 2026-07-28 connections ([FastMCP upgrade guide](https://github.com/PrefectHQ/fastmcp/blob/HEAD/docs/getting-started/upgrading/from-fastmcp-3.mdx)), so any ADK pattern that relies on server-initiated elicitation has to move to MRTR.

### The A2A TCK only fits a scoped, local, unauthenticated run

A2A 1.0.0 shipped on 12 March and 1.0.1 on 26 May ([CHANGELOG](https://github.com/a2aproject/A2A/blob/HEAD/CHANGELOG.md)). a2a-python 1.2.3 implements 1.0 with a 0.3 compatibility mode on all three bindings ([README](https://github.com/a2aproject/a2a-python/blob/HEAD/README.md)). The **a2a-tck** runs `./run_tck.py --sut-host … --level must|should|may` and writes JSON, HTML and JUnit reports ([TCK README](https://github.com/a2aproject/a2a-tck/blob/HEAD/README.md)). Its requirement IDs cover several areas:

- auth: `AUTH-SERVER-002` ("Server must authenticate every incoming request");
- versioning: `VER-SERVER-003` (an empty version header means 0.3) ([auth.py](https://github.com/a2aproject/a2a-tck/blob/HEAD/tck/requirements/auth.py));
- agent cards: JCS canonicalisation before signing, `Cache-Control`/`ETag`, and authentication for the extended card ([agent_card.py](https://github.com/a2aproject/a2a-tck/blob/HEAD/tck/requirements/agent_card.py)).

Most core-operation tests, however, drive a scripted system under test through `messageId` prefixes such as `tck-complete-task` ([core_operations.feature](https://github.com/a2aproject/a2a-tck/blob/HEAD/scenarios/core_operations.feature)). The transport clients also send only the `A2A-Version` and `Content-Type` headers ([jsonrpc_client.py](https://github.com/a2aproject/a2a-tck/blob/HEAD/tck/transport/jsonrpc_client.py)). The right citation is therefore a **scoped run**: `--level must -- -k 'agent_card or versioning'` against a local `to_a2a` instance, never Agent Runtime directly. The requirement IDs can also seed new rules in the skill's `agent_card_check.py`, which does not yet check signing, caching headers or extended-card auth. The TCK ships `run-tck` and `learn-requirement` skills that a ticket can name as companions ([AGENTS.md](https://github.com/a2aproject/a2a-tck/blob/HEAD/AGENTS.md)).

Two smaller items belong in a2a-contracts.md. agents-cli's `_a2a_pinning.py` notes that the a2a-sdk "never compares that host against the URL the card came from", which matters for raw SDK clients calling an ADK agent ([_a2a_pinning.py](https://github.com/google/agents-cli/blob/HEAD/src/google/agents/cli/run/_a2a_pinning.py)). a2a-samples has `sign_and_verify_agent_card`, `headless_agent_auth` (CIBA) and `multitenancy` as patterns to pin by commit ([a2a-samples](https://github.com/a2aproject/a2a-samples/tree/HEAD/samples/python/agents)).

### AG-UI 1.0 splits approvals into two incompatible client contracts

AG-UI's 1.0 spec is now normative, with 31 event types and a `schema.json` ([spec 1.0](https://github.com/ag-ui-protocol/ag-ui/tree/HEAD/docs/spec/1.0)), and the TypeScript client exports `verifyEvents` for stream validation ([verify](https://github.com/ag-ui-protocol/ag-ui/blob/HEAD/sdks/typescript/packages/client/src/verify/index.ts)). The detail with the most design weight is in the unreleased ag-ui-adk changes:

- `emit_interrupt_outcome` maps ADK tool confirmation to `RUN_FINISHED` interrupt outcomes.
- Server-side codes (`INTERRUPT_RESUME_REQUIRED`, `INTERRUPT_RESUME_INCOMPLETE`, `UNKNOWN_INTERRUPT`) are enforced from session state "so every instance enforces them".
- The flag is **off by default**, because `@ag-ui/client` rejects the next run unless interrupts are answered through `RunAgentInput.resume`, "which breaks frontends that answer with a plain tool message (CopilotKit `useHumanInTheLoop` …)" ([CHANGELOG](https://github.com/ag-ui-protocol/ag-ui/blob/HEAD/integrations/adk-middleware/python/CHANGELOG.md)).

adk-frontend-integration and adk-operational-guardrails must therefore document **two approval contracts**: plain tool-message answers, or interrupt outcomes with resume. Each ticket must declare which one it uses. The CopilotKit monorepo's `examples/integrations/adk` replaces the archived with-adk ([example](https://github.com/CopilotKit/CopilotKit/tree/HEAD/examples/integrations/adk)). Even there the stack is mixed: the Python agent pins `ag-ui-adk==0.7.0` and `ag-ui-protocol==0.1.18` against a 1.0.2 JS client ([agent pyproject](https://github.com/CopilotKit/CopilotKit/blob/HEAD/examples/integrations/adk/agent/pyproject.toml)).

**MCP Apps now reach ADK end to end.** On main, `UiWidget(provider="mcp")` carries the `ui://` resource that `McpTool` reads from `meta.ui.resourceUri` ([ui_widget.py](https://github.com/google/adk-python/blob/HEAD/src/google/adk/events/ui_widget.py)). A custom frontend has to render it with the MCP Apps AppBridge, which makes that a ticket of its own. ext-apps ships four companion skills, including `add-app-to-server` ([ext-apps](https://github.com/modelcontextprotocol/ext-apps/blob/HEAD/README.md)). assistant-ui's ADK adapter targets ADK JS, not Python, but its warning that "a client-sent session ID is not proof that the caller owns the session" independently corroborates the skill's session-ownership rule ([react-google-adk](https://github.com/assistant-ui/assistant-ui/blob/HEAD/packages/react-google-adk/README.md)).

### OpenTelemetry already lists ADK's known semconv violations

The GenAI semantic conventions are entirely at **Development** status and live in `semantic-conventions-genai` ([agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)). That repo's reference suite has a **google-adk scenario pinned to `google-adk==2.11.0`**. It marks `invoke_agent` (internal), `invoke_workflow`, `execute_tool`, memory spans and `SkillToolset` spans as implemented ([scenario README](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/reference/scenarios/google-adk/README.md)). It also lists expected violations: proprietary `gcp.vertex.agent.*` attributes, the removed `gen_ai.system` attribute, and unit `1` instead of `{inference_call}` ([conformance.yaml](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/reference/scenarios/google-adk/conformance.yaml)).

adk-agent-observability can turn this into a reproducible check. Run one scripted invocation under Weaver live-check, using the conformance runner's mock LLM server ([conformance runner](https://github.com/open-telemetry/semantic-conventions-conformance/blob/main/README.md)), and diff the result against the upstream list, so that a new violation reads as drift. The skill should also warn that dashboards must not key on `gen_ai.system`. Eval and online-judge scores should be emitted as **`gen_ai.evaluation.result`** events parented to the evaluated span, which lets them join traces in any OTel backend, not only BigQuery ([gen-ai-events.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-events.md)).

## Outside methods fill ADK's reliability, state and judge-agreement gaps

ADK's eval stack on main has fifteen prebuilt metrics, including `tool_call_count_v1`, `token_usage_v1` and `invocation_duration_v1` ([eval_metrics.py](https://github.com/google/adk-python/blob/main/src/google/adk/evaluation/eval_metrics.py)). Its only control for judge flakiness is `num_samples` majority voting ([criteria.md](https://github.com/google/adk-docs/blob/main/docs/evaluate/criteria.md)). Four things are missing: repeated trials, a pass^k estimator, grading on end state, and a statistic for agreement between judges.

**tau2-bench** (MIT) is the methodology to copy. Its `pass_hat_k` is `math.comb(success_count, k) / math.comb(num_trials, k)` and raises when trials < k ([agent_metrics.py](https://github.com/sierra-research/tau2-bench/blob/main/src/tau2/metrics/agent_metrics.py)). Its evaluator rules are explicit ([evaluator AGENTS.md](https://github.com/sierra-research/tau2-bench/blob/main/src/tau2/evaluator/AGENTS.md)):

- "Reward is multiplicative … A 0 in any component zeroes the total."
- "Premature termination = 0 reward."
- "Missing criteria means 'not evaluated', not 'failed'."
- Gold actions are "one reference trajectory": any path that reaches an equivalent end state also passes.

Version 2.0 refuses comparison with 1.x after a judge change to `gpt-5.4-mini-2026-03-17` ([README](https://github.com/sierra-research/tau2-bench/blob/main/README.md)). That is a public precedent for the toolkit's pinned-judge rule. For adk-agent-evaluation, adopt the method, not the benchmark:

- a `pass_hat_k` helper next to `check_eval_results.py`, which today defines observed pass^k and deliberately computes nothing ([result-auditing.md](https://github.com/RuslanKhis/agentic-engineering-skills/blob/main/skills/adk-agent-evaluation/references/result-auditing.md));
- a state grader that replays gold actions into a second fresh backend and compares end states, which closes the skill's own flagged gap that relaxed ordering "does not classify extra mutations as safe";
- premature stops scored as failures;
- multiplied component scores.

AppWorld's database-state unit tests "without causing any collateral damage" supply the extra-mutation half ([AppWorld](https://github.com/StonyBrookNLP/appworld/blob/main/README.md)).

**Inspect AI** (MIT) contributes three things:

- the `pass_k` and `at_least` reducers;
- `pass_at`, which returns **NaN rather than a spurious 1.0** when fewer than k scored epochs remain, an explicit "incomplete" signal for gates ([reducer.py](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/src/inspect_ai/scorer/_reducer/reducer.py));
- a built-in `krippendorff_alpha` for calibrating judges against human labels ([krippendorff.py](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/src/inspect_ai/scorer/_metrics/krippendorff.py)).

Its `agent_bridge()` supports Google APIs but ships no ADK example, so whether it intercepts ADK's google-genai calls needs a spike first ([agent-bridge.qmd](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/docs/agent-bridge.qmd)).

**promptfoo** (MIT, owned by OpenAI since 9 March 2026 per [TechCrunch](https://www.techcrunch.com/2026/03/09/openai-acquires-promptfoo-to-secure-its-ai-agents/)) is the only external harness whose official ADK 2.x guide asserts directly on ADK's native spans. It wraps the app as an in-process Python provider and normalises `gen_ai.tool.name` and tool arguments "without a custom span translator". That sidesteps the duplicate-span problem the toolkit documents for OpenInference ([ADK guide](https://github.com/promptfoo/promptfoo/blob/main/site/docs/guides/evaluate-google-adk.md)). The guide maps ADK features to assertions (paired session-id cases for `MemoryService`, session-state snapshots for resumable apps) and advises "state and artifact assertions first". For CI it gives exit code **100** on a failed case or a pass rate below `PROMPTFOO_PASS_RATE_THRESHOLD` and exit **1** on other errors, plus `--repeat` ([command-line.md](https://github.com/promptfoo/promptfoo/blob/main/site/docs/usage/command-line.md)). That split matches the toolkit's existing 0/1/2 exit-code design. Pin the version and keep the deterministic Runner suite as the source of truth, given the change in ownership.

Two other harnesses carry conditions. deepeval's ADK tracing hook raises without a `CONFIDENT_API_KEY`, so it routes through SaaS ([otel.py](https://github.com/confident-ai/deepeval/blob/main/deepeval/integrations/google_adk/otel.py)). MLflow wraps ADK's own evaluators as scorers over a self-hosted store ([MLflow ADK scorers](https://github.com/mlflow/mlflow/blob/main/docs/docs/genai/eval-monitor/scorers/third-party/google-adk.mdx)).

Several narrower sources supply single patterns:

- **MCPMark** ships a `verify.py` per task, pinned MCP server versions, and pass^k reporting ([MCPMark](https://github.com/eval-sys/mcpmark/blob/main/README.md)), which suits ADK agents that use MCP toolsets.
- **Harbor's task layout** (instruction, `task.toml` timeouts, Dockerfile, verifier writing `reward.json`, reference solution) and **SWE-bench's `FAIL_TO_PASS`/`PASS_TO_PASS`** lists are templates for regression tickets ([Harbor task](https://github.com/harbor-framework/harbor/tree/main/examples/tasks/computer-1-click-calibration), [SWE-bench](https://github.com/SWE-bench/SWE-bench/blob/main/swebench/harness/constants/__init__.py)).
- **For SQL**, BIRD Mini-Dev supplies the published names EX, Soft-F1 and R-VES. Its licence badge is CC BY-SA 4.0, so link it and never vendor it ([BIRD](https://github.com/bird-bench/mini_dev/blob/main/README.md)). Spider 2.0-Lite's 214 BigQuery tasks are the only benchmark examined that targets BigQuery ([Spider2](https://github.com/xlang-ai/Spider2/blob/main/README.md)).
- **For memory**, LongMemEval's ability taxonomy (information extraction, multi-session and temporal reasoning, knowledge updates, abstention) is the right structure for `retrieval-gold.json` ([LongMemEval](https://github.com/xiaowu0162/LongMemEval)). LongMemEval-V2 covers memory that agents build from experience ([V2](https://github.com/xiaowu0162/LongMemEval-V2)).
- **Pydantic Evals** grades the path from the OTel span tree and runs sampled online judges on production calls ([span-based](https://github.com/pydantic/pydantic-ai/blob/main/docs/evals/evaluators/span-based.md), [online](https://github.com/pydantic/pydantic-ai/blob/main/docs/evals/online-evaluation.md)). The eval skill has no online mode at all.
- **Strands chaos testing** adds three resilience metrics (failure communication, partial completion, recovery strategy) and cases with corrupted responses ([chaos_testing](https://github.com/strands-agents/harness-sdk/blob/main/site/src/content/docs/user-guide/evals-sdk/chaos_testing.mdx)).
- **OpenAI's scripted `ModelStep` tests** raise `UnexpectedModelCall` and leave `UnconsumedModelSteps` to "detect workflow drift" ([testing.md](https://github.com/openai/openai-agents-python/blob/main/docs/testing.md)). That is a small addition to the toolkit's fake-model tests.
- **Anthropic's eval guide** stresses that each trial starts from a clean environment, after one agent gained an advantage from git history left by earlier trials, and that "20-50 simple tasks drawn from real failures is a great start" ([Anthropic](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)).

## Security sources supply fixtures, finding IDs and sandbox checks

**AgentDojo** (MIT, v0.1.35, last commit June 2026) is the one injection benchmark worth integrating. Its four v1 suites hold banking (16 user / 9 injection tasks), slack (17/5), travel (20/7) and workspace (33/6). Its `BasePipelineElement.query(...)` API means an ADK `Runner` can be wrapped as one element. Its Gemini list ends at `gemini-2.5-pro-preview-05-06`, and the README warns that the API "might change" ([agentdojo](https://github.com/ethz-spylab/agentdojo)). There are two routes:

- **Offline, deterministic first (do now):** port the injection *goals* as attributed fixtures into `adversarial-cases.json`, then assert with the existing scripted-model Runner harness.
- **Live, authorised ticket (later):** an `AdkRunnerElement` adapter that reports attack success rate against the bare model.

inspect_evals carries a ready AgentDojo port and Lakera's `b3` ([inspect_evals agentdojo](https://github.com/UKGovernmentBEIS/inspect_evals/tree/main/src/inspect_evals/agentdojo)). Three further sources give reusable shapes rather than dependencies:

- **CaMeL** offers the clearest copyable shape for a `before_tool_callback` policy table: a set of tools with no side effects, plus one policy function per side-effect tool that checks where its argument values came from. The authors are "not planning to… maintain this codebase", so cite the pattern and do not depend on it ([camel](https://github.com/google-research/camel-prompt-injection)).
- **LlamaFirewall** scanners (PromptGuard, AlignmentCheck) can run in `after_tool_callback` to screen tool results locally. The scanner code is MIT, but the Prompt Guard 2 weights carry the Llama 4 Community License ([LlamaFirewall](https://github.com/meta-llama/PurpleLlama/tree/main/LlamaFirewall)).
- **NeMo Guardrails** has YARA rules for SQL, Jinja, code and XSS injection in model output, which suit LLM05 output-handling checks ([NeMo-Guardrails](https://github.com/NVIDIA/NeMo-Guardrails)).

Presidio (MIT) is the offline PII oracle for CI without GCP credentials, while SDP stays the production control ([presidio](https://github.com/microsoft/presidio)).

For red-teaming ADK targets, each tool connects differently:

- **promptfoo** runs in-process with plugins for `mcp` (eight vectors, including tool-metadata injection and privilege escalation), `tool-discovery`, `memory-poisoning`, `data-exfil` and `excessive-agency` ([mcp plugin](https://github.com/promptfoo/promptfoo/blob/main/site/docs/red-team/plugins/mcp.md)).
- **PyRIT's `A2ATarget`** speaks A2A 0.3 and 1.0, discovers cards and continues `input-required` tasks, so it can red-team an ADK agent over A2A with no adapter. That makes it the natural ASI07 tool ([PyRIT](https://github.com/microsoft/PyRIT)).
- **deepteam** ships an OWASP Agentic preset whose categories carry IDs `ASI01:2026` through `ASI10`, so findings arrive pre-labelled ([deepteam](https://github.com/confident-ai/deepteam)).
- **garak's** `function` generator wraps a Runner, and its new `agent_breaker` probe attacks tools ([garak](https://github.com/NVIDIA/garak)).

**Snyk Agent Scan** (formerly mcp-scan, Apache-2.0) scans MCP configs *and* `SKILL.md` folders for 14 risk types and has a `--ci` flag. It needs a `SNYK_TOKEN`, it sends tool descriptions and skill content to Snyk, and its output schema is "experimental… We do not recommend building production workflows that depend on specific CLI output fields" ([agent-scan](https://github.com/snyk/agent-scan)). It belongs in adk-agent-security as an optional scan before adopting a server, run in a sandbox at a pinned version, alongside the existing hash-pinning. The same `--ci` scan over the toolkit's own `skills/` directory treats the 22 distributed skills as the supply-chain surface they are.

For finding IDs, keep **ASI01–ASI10 (2026)** and **LLM01–LLM10 (2025)** as primary. The user's `sources.md` flags the ASI titles as coming from secondary summaries ([sources.md](https://github.com/RuslanKhis/agentic-engineering-skills/blob/main/skills/adk-agent-security/references/sources.md)); deepteam's code carries the same titles. Add two versioned, Apache-licensed YAML cross-references that a script can validate in CI:

- **MITRE ATLAS 2026.09**: 16 tactics, 120 techniques and 88 sub-techniques, including AML.T0086 "Exfiltration via AI Agent Tool Invocation" and AML.T0110 "AI Agent Tool Poisoning" ([atlas-data](https://github.com/mitre-atlas/atlas-data)).
- **CoSAI Risk Map** IDs such as `riskRunawayAgentToolLoops` and `controlAgentExecutionBounds` ([secure-ai-tooling](https://github.com/cosai-oasis/secure-ai-tooling)).

The OWASP MCP Top 10 (beta, CC BY-SA) supplies MCP01–MCP10 for findings on MCP servers, citing IDs only ([OWASP MCP Top 10](https://github.com/OWASP/www-project-mcp-top-10)). CoSAI WS4's "MCP Runtime Isolation" and "Tool Design" runbooks (CC BY 4.0) are vendor-neutral companions ([WS4](https://github.com/cosai-oasis/ws4-secure-design-agentic-systems)).

## Approvals, resume and memory need rules other frameworks already wrote

**Guardrail placement and approval semantics** are documented more explicitly outside ADK. OpenAI's Agents SDK sets four rules ([guardrails.md](https://github.com/openai/openai-agents-python/blob/main/docs/guardrails.md), [human_in_the_loop.md](https://github.com/openai/openai-agents-python/blob/main/docs/human_in_the_loop.md)):

- Placement: input guardrails run only for the first agent, output guardrails only for the agent that produces the final output, and tool guardrails on every guarded call, including inside delegated specialists.
- Parallel screening has a cost: "the agent may have already consumed tokens and executed tools before being cancelled".
- An output tripwire keeps completed tool events, drops the rejected output, and substitutes a static, data-free message.
- Approvals fail closed: malformed, empty or NaN arguments force manual approval.

Microsoft Agent Framework's ADR-0045 adds the rule the toolkit lacks entirely: approval requests left unanswered are rejected on the next run, because "a missing answer must never authorize tool execution" ([ADR-0045](https://github.com/microsoft/agent-framework/blob/main/docs/decisions/0045-dotnet-unanswered-tool-approvals.md)).

Translated to ADK, these become rules for adk-agent-security and adk-operational-guardrails:

- **Placement table.** Runner plugins apply to the whole tree; agent callbacks apply to one agent; tool callbacks apply per call, with 2.12 output filtering in `after_tool_callback`.
- **Parallel screening only for read-only agents.**
- **Approval keys.** Sticky approvals are keyed by agent and tool identity.
- **Unanswered confirmations.** A pending `ToolConfirmation` with no answer is resolved as rejected and recorded.

The server-side `INTERRUPT_RESUME_REQUIRED` in ag-ui-adk is the frontend counterpart. Strands' steering pattern maps to a `before_tool_callback` that reads a tool ledger and returns a dict to cancel and redirect a call ([steering](https://github.com/strands-agents/harness-sdk/blob/main/site/src/content/docs/user-guide/sdk/agents/interventions/steering.mdx)). The Claude cookbook's `decide()`/`escalate()` pair argues that "an agent that escalates everything is exhausting… an agent that escalates nothing is dangerous", which suggests escalation rate is a metric worth evaluating ([notebook](https://github.com/anthropics/claude-cookbooks/blob/main/managed_agents/CMA_gate_human_in_the_loop.ipynb)).

**Resume and durability** need a design fork the designer does not yet force. ADK resume is at-least-once: tools "may run more than once when resuming", and resuming from Web or CLI is unsupported ([adk.dev resume](https://adk.dev/runtime/resume/)). Diagrid, a vendor post, adds that "the caller is responsible for detecting failure and re-invoking" ([Diagrid](https://www.diagrid.io/blog/checkpoints-are-not-durable-execution-why-langgraph-crewai-google-adk-and-others-fall-short-for-production-agent-workflows)). LangGraph's "rules of interrupts" become an ADK resume checklist ([interrupts.mdx](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/interrupts.mdx)):

- a node re-runs from the beginning on resume;
- never wrap the pause in try/except;
- never reorder pause points;
- avoid `while True` loops around a pause.

Pydantic AI's "durability is not storage" frames the decision ([durable_execution](https://github.com/pydantic/pydantic-ai/blob/main/docs/durable_execution/overview.md)). Either use `ResumabilityConfig` with idempotent tools, or adopt an external engine when runs must survive crashes without a caller, or wait days for a human. The designer currently says only that session persistence "do[es] not supply durable execution guarantees" ([design-decisions.md](https://github.com/RuslanKhis/agentic-engineering-skills/blob/main/skills/adk-system-designer/references/design-decisions.md)).

Four engines appear in ADK's catalogue, and **none claims exactly-once external side effects**:

- **Temporal** (`temporalio-google-adk`, pre-release) runs each model call and tool as an Activity. It ships recorded-history `Replayer` tests for single-agent, multi-agent, graph-workflow and HITL cases. Its README warns that `factory_argument` values are "recorded in workflow history and, without a payload codec, visible in the web UI" ([README](https://github.com/temporalio/ai-integrations/blob/main/python/google_adk/README.md), [tests](https://github.com/temporalio/ai-integrations/tree/main/python/google_adk/tests)).
- **DBOS** needs only Postgres and makes compaction calls durable through `DBOSEventSummarizer` ([adk.dev DBOS](https://adk.dev/integrations/dbos/)). Its test asserts a tool's `call_count == 1` after fork-and-replay ([dbos-google-adk](https://github.com/dbos-inc/dbos-google-adk)).
- **Restate** supports only `LlmAgent` ([plugin.py](https://github.com/restatedev/sdk-python/blob/main/python/restate/ext/adk/plugin.py)).
- **Dapr** wraps the agent as a Dapr Workflow ([adk.dev Dapr](https://adk.dev/integrations/dapr/)).

Every engine checkpoints a step's *result*. A crash after the provider accepts a write but before the checkpoint re-executes the step, so safe-api-tool-calls' idempotency keys and uncertain-result reconciliation stay mandatory inside durable steps.

**Context and memory** have three sources of rules. MAF's ADR-0019 sets "atomic group preservation": a tool call and its results are kept or dropped together. It also names three compaction points: inside the run, before persisting, and as maintenance on stored history ([ADR-0019](https://github.com/microsoft/agent-framework/blob/main/docs/decisions/0019-python-context-compaction-strategy.md)). ADK 2.12's fix for orphaned function calls blocking compaction shows the failure is real.

Memory Bank revisions document consolidation semantics. New information creates a memory when nothing in scope covers it, updates an existing one when it is "duplicative, complementary, or contradictory", and deletes one it invalidates. `revision_labels` allow erasure and rollback by source, and `target_revision_id` restores a poisoned fact ([Memory revisions](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank/revisions)). Mem0's ADK sample is the contrast and the anti-pattern: its memory methods catch every exception and return empty results, which looks identical to "no memories" ([mem0 ADK guide](https://github.com/mem0ai/mem0/blob/main/docs/integrations/google-ai-adk.mdx)). Docling (MIT) is the open extractor that handles layout, tables, reading order and OCR, and it can feed the skill's `qualify_ingestion.py` ([docling](https://github.com/docling-project/docling)).

**Cost** has three items. ADK's GEPA optimizers should be used with a pinned `optimizer_model`, and each optimised instruction treated as a versioned release artefact. LiteLLM ships ADK spend fixtures for retries, streaming, swarms and failed-but-billed calls, outside its `enterprise/` directory ([litellm](https://github.com/BerriAI/litellm)). Anthropic's code-execution-with-MCP pattern cut "150,000 tokens to 2,000 tokens", but only behind sandboxing and monitoring ([Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)). It belongs in adk-tool-interface-design as an option gated on the security skill's executor controls. Finally, agents-shipgate's static diff of ADK tool bindings between commits is a cheap merge gate for "a coding agent changed what the production agent can do". Its ADK 2.x parsing still needs verifying on a fixture ([agents-shipgate](https://github.com/ThreeMoonsLab/agents-shipgate)).

## adk-system-designer needs a reference-patterns field and named companions

The ticket template already carries `primary_skill`, `supporting_skills`, `contracts`, A1–An acceptance items mapped to contracts, Verification, Evidence and "Run this ticket". It has no field for external patterns ([ticket-template.md](https://github.com/RuslanKhis/agentic-engineering-skills/blob/main/skills/adk-system-designer/assets/ticket-template.md)). The research converges on five small front-matter additions. `reference_patterns` names a source, the pattern, the ADK-native mechanism and the acceptance check it drives, so that adk-engineer implements the ADK version rather than porting another framework's API. `parallel_safe` and `touches` follow spec-kit's `[P]` marker, which means "different files, no dependencies" ([tasks-template](https://github.com/github/spec-kit/blob/main/templates/tasks-template.md)); they make frontier-based execution safe. `constraints` follows Superpowers' rule that every task "implicitly include[s]" a Global Constraints section ([writing-plans](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)). `docs` points at the official ADK Docs MCP ([coding-with-ai.md](https://github.com/google/adk-docs/blob/main/docs/tutorials/coding-with-ai.md)).

```yaml
parallel_safe: yes                        # spec-kit [P]; lets implement-spec give it its own worktree
touches: [app/agents/refund.py, app/tools/payments.py]   # inspected or proposed paths
constraints: AGENTS.md#constraints        # pinned google-adk, models, judge, invariants
docs: ADK Docs MCP (mcpdoc, adk.dev/llms.txt); verify against installed google-adk==<pin>
reference_patterns:                       # optional; external designs implemented ADK-natively
  - id: RP1
    source: microsoft/agent-framework docs/decisions/0045 (proposed 2026-10-02)
    pattern: an unanswered approval is rejected on the next run
    adk_native: pending ToolConfirmation resolved as rejected and recorded at next invocation
    drives: A3
    license: MIT; idea only, no code copied
  - id: RP2
    source: sierra-research/tau2-bench src/tau2/evaluator
    pattern: end-state comparison against gold replay; pass^k = C(c,k)/C(n,k)
    adk_native: fresh in-memory backends per trial; Runner with pinned model and judge
    drives: A1, A2
    license: MIT; formula restated
```

The body changes are equally small:

- **EARS wording for acceptance.** `WHEN <trigger> THE <app> SHALL …` for happy paths, `IF <failure> THEN … SHALL …` for recovery, and `… SHALL NOT …` for forbidden effects ([Kiro specs](https://kiro.dev/docs/specs/concepts)). Example: "A2 (C3) IF the booking API times out after the write was sent, THEN the agent SHALL report the outcome as unknown AND SHALL NOT retry."
- **Property statements for universal invariants**, such as owner isolation, verified with property-based tests ([Kiro correctness](https://kiro.dev/docs/specs/correctness/)).
- **Verification split** into `Automated:` commands and `Manual:` checks, after HumanLayer's plans ([humanlayer commands](https://github.com/humanlayer/humanlayer/tree/main/.claude/commands)).
- **Evidence requirements.** Each A-item records the command, its exit code, and the commit SHA and worktree. A `Rulings:` list (`what — why — cost if wrong`) records the implementer's decisions. Status `done` is allowed only when every A-item has fresh evidence. This follows Superpowers' rule "NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE" and its red-green revert check for regression tests ([verification-before-completion](https://github.com/obra/superpowers/blob/main/skills/verification-before-completion/SKILL.md), [subagent-driven-development](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)).
- **Maintenance changes (Journey B).** Record contracts as OpenSpec-style `ADDED/MODIFIED/REMOVED` deltas and merge them back into the architecture doc. A read-only "plan versus code" mode reports completeness, correctness and coherence as CRITICAL, WARNING or SUGGESTION ([OpenSpec verify](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/verify-change.ts)).
- **No new top-level documents.** Böckeler found spec-kit's markdown "repetitive and tedious to review", and Kiro turned a small bug into "four user stories and 16 acceptance criteria" ([martinfowler.com](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).

The designer should also propose a **G00 "project agent instructions" goal** that writes a project `AGENTS.md`. It should hold pinned versions and models, test and eval commands, the evidence directory, authority rules, the design's invariants and a 10–20-line skill index. Claude Code's docs say it "reads `CLAUDE.md`, not `AGENTS.md`", so pair it with a one-line `CLAUDE.md` containing `@AGENTS.md` and keep both under 200 lines ([Claude Code memory](https://code.claude.com/docs/en/memory?os=0)). Gemini CLI needs `context.fileName` set to read it ([gemini-md.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/gemini-md.md)). The skill index addresses the discovery failure the toolkit already cites, where skills went uninvoked in 56% of Vercel's cases ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). Whether it actually raises activation should be measured with `evals/activation.json`.

Companions belong in the "Run this ticket" prompt, one lead method per session. Superpowers bootstraps itself with `using-superpowers`, and Matt's collection has its own router, so co-running them risks conflicting process rules. Superpowers should therefore be offered as an alternative lead method, not an extra layer.

## Licences: share-alike, non-commercial and Elastic traps, and notices that must travel

The baseline is benign. Every Google repo whose licence was read is Apache-2.0, and none of the eleven key repos ships a root NOTICE file: adk-python, adk-recipes, adk-docs, mcp-toolbox, the BQAA SDK, agents-cli, google/skills, agent-sandbox, a2a-tck, generative-ai and A2UI ([adk-recipes root](https://github.com/google/adk-recipes)). Some individual recipes do carry their own LICENSE, such as `core/python/cross-session-memory`, so check per recipe before copying ([cross-session-memory](https://github.com/google/adk-recipes/tree/main/core/python/cross-session-memory)).

Apache-2.0 §4 requires three things of a copy: modified files must carry "prominent notices stating that You changed the files", copyright and attribution notices must be retained, and any upstream NOTICE must be reproduced ([adk-python LICENSE](https://github.com/google/adk-python/blob/main/LICENSE)). Apache material can then be combined into an MIT project ([FOSSA](https://fossa.com/resources/license-compliance-tools/license-compatibility-checker/apache-2-0-vs-mit/)). Strands' harness-sdk ships a NOTICE file beside its Apache licence, so any copied Strands code must carry it ([harness-sdk](https://github.com/strands-agents/harness-sdk)). The MCP project repos are "undergoing a licensing transition from the MIT License to the Apache License", so treat their new content as Apache-2.0 ([MCP LICENSE](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/HEAD/LICENSE)). MIT sources need only the copyright line kept.

**The packaging rule is the part that is easy to miss.** Skills install per folder, through `npx skills add` or `.agents/skills/<name>`, so a repo-root `THIRD_PARTY_NOTICES.md` does not travel with an installed skill. Every verbatim asset therefore needs its notice *inside the skill folder that ships it*. The likely candidates are Horizon evalset JSON, BQAA continuous-query SQL, Model Armor snippet code, ADK test helpers, a bundled AG-UI `schema.json` (MIT) and ATLAS or CoSAI ID tables (Apache). Place each under something like `assets/third_party/<origin>/` with:

- the original header;
- a "Modified by … on …" line;
- the Apache text, plus the upstream NOTICE where one exists;
- an entry in that skill's `provenance.md`, the pattern optimise-adk-on-google-cloud already uses.

A root file should serve only as an index. Paraphrasing a pattern with a link, which is the toolkit's existing practice, needs no licence action at all. Formulas such as pass^k are methods and can be restated freely.

The traps fall into four classes.

**Share-alike.** These sources must be linked and paraphrased, never vendored:

- BIRD mini_dev: a CC BY-SA 4.0 badge and no LICENSE file ([BIRD](https://github.com/bird-bench/mini_dev/blob/main/README.md)).
- The OWASP LLM and MCP Top 10 texts: CC BY-SA 4.0, so cite IDs and titles only ([OWASP MCP Top 10](https://github.com/OWASP/www-project-mcp-top-10)).
- 12-factor-agents: the content is CC BY-SA, though its code is Apache ([12-factor-agents](https://github.com/humanlayer/12-factor-agents)).

**Non-commercial.** These are unusable for commercial adopters of an MIT toolkit:

- LoCoMo (CC BY-NC 4.0) ([LoCoMo](https://github.com/snap-research/locomo)).
- WASP (CC BY-NC 4.0) ([wasp](https://github.com/facebookresearch/wasp)).
- The NirDiamant tutorial repos, whose licence prohibits commercial use "in whole or in part" ([LICENSE](https://github.com/NirDiamant/agents-towards-production/blob/main/LICENSE)).

**Source-available or restricted.**

- Arize Phoenix and `phoenix-evals` are under Elastic License 2.0 ([Phoenix LICENSE](https://github.com/Arize-ai/phoenix/blob/main/LICENSE)).
- Langfuse's `ee/` directories ([Langfuse LICENSE](https://github.com/langfuse/langfuse/blob/main/LICENSE)) and LiteLLM's `enterprise/` ([LiteLLM LICENSE](https://github.com/BerriAI/litellm/blob/main/LICENSE)) are carved out of their MIT licences.
- WrenAI's docs are CC BY 4.0, and the repo reserves future AGPL-3.0 modules ([WrenAI LICENSE](https://github.com/Canner/WrenAI/blob/main/LICENSE)).
- Prompt Guard 2 weights use the Llama 4 Community License.
- claude-task-master is MIT plus the Commons Clause ([LICENSE](https://github.com/eyaltoledano/claude-task-master/blob/main/LICENSE)).
- spec-workflow-mcp is GPL-3.0.
- The Reversec design-pattern samples ship no licence file, so default copyright applies and they can only be linked ([repo](https://github.com/ReversecLabs/design-patterns-for-securing-llm-agents-code-samples)).

**Service terms rather than licences.**

- Snyk Agent Scan's code is Apache-2.0, but running it means accepting Snyk's terms and uploading tool descriptions and skill content ([agent-scan](https://github.com/snyk/agent-scan)).
- deepeval's ADK tracing path requires a Confident AI key.
- AppWorld ships part of its code encrypted.

CoSAI WS4 is CC BY 4.0, so quoting with attribution is fine. None of this is legal advice, and the patent and trademark clauses (§6) were not analysed.

## What this research could not verify

**Popularity is unmeasured.** The GitHub API returned HTTP 403 for every repository in every research track, so **no star counts were collected**. Activity rests on HEAD commit dates from shallow clones, and "archived" status comes from README banners rather than the API flag. Third-party star figures, such as Superpowers at 298,135 or spec-kit at about 111K, are unverified. Registry versions are tag-based because PyPI and npm were unreachable.

**Nothing was executed against a live ADK application.** The MCP conformance suite, the A2A TCK, the Inspector, promptfoo, AgentDojo, agents-shipgate and the durable-engine tests are all claimed from documentation and source only. Five specific behaviours are untested:

- ADK 2.8.0 pins `mcp<2`, so `--requirements 2026-07-28` may fail wholesale, and `2025-11-25` may be the right default.
- The TCK's lack of an auth-header option was established by grep, so a pytest hook may yet work.
- Inspect's `agent_bridge` interception of ADK calls is unconfirmed.
- The OTel violation list was checked against ADK 2.11, not 2.12.
- Temporal's support for graph workflows with `rerun_on_resume` is unconfirmed.

Run a short spike before encoding any exit code into skill text.

**CVE-2026-4810 has two conflicting descriptions.** Aviatrix calls it CVSS 9.3, gives affected ranges of ">=1.7.0, <1.28.1, >=2.0.0a1, <2.0.0a2", and ties it to an agent-to-agent PR-injection chain ([Aviatrix](https://aviatrix.ai/threat-research-center/flaws-google-adk-python-agent-to-agent-attack-2026/)). The user's `sources.md` records it as an `adk web` flaw in 1.7.0–1.28.0, fixed in 1.28.1 ([sources.md](https://github.com/RuslanKhis/agentic-engineering-skills/blob/main/skills/adk-agent-security/references/sources.md)). Neither has been checked against the GHSA or OSV record.

**Several smaller conflicts remain open.**

- adk.dev dates ADK resumability to v1.16.0; Diagrid says v1.14.0.
- A September article claims Claude Code added an AGENTS.md fallback ([CryptoBriefing](https://cryptobriefing.com/anthropic-claude-code-agents-md-support/)); the official docs still say it reads only CLAUDE.md.
- Whether zero-trust-agents-2's "Semantic Governance Policies" and "Agent Anomaly Detection" are products or sample constructs is unknown.
- The Restate server licence and the third-party `gepa` package licence are unverified.

**Framings and figures carry their own caveats.** The `reference_patterns` field and the ticket deltas are proposals that have not been tested against the toolkit's activation corpus. The claims for Superpowers and Conductor are anecdotal. Every threshold in the acceptance templates is a placeholder.

## Conclusion

The toolkit's niche, deciding and then verifying, has become much cheaper to fill. All four protocol layers it touches (MCP, A2A, AG-UI and OpenTelemetry GenAI) now publish official conformance tooling, and two of them, MCP and OTel, ship explicit baselines or expected-violation lists. The leverage point is therefore not more prose in the specialists. It is a designer that emits pinned commands plus a reviewed baseline per ticket. Those baselines double as a drift detector: the MCP suite fails on a *stale* baseline entry, and the OTel scenario's expected violations turn an upstream change into a red CI signal rather than silent rot. That matters because drift, not missing repos, is the dominant risk. In the two weeks after the toolkit's early-October check, ADK shipped security-relevant 2.12 fixes and a new `adk eval` exit code on main, ag-ui-adk moved to the 1.0 protocol floor, and agents-cli made adk-recipes canonical. A week before that check, OpenInference had already raised its ADK floor above the toolkit's pin. Compatibility tables keyed by version and re-checked on a schedule are worth more than any single integration.

The research also shows the toolkit's surroundings changing shape. Google now ships skills inside its SDKs and repos: adk-python's `.agents/skills` and bundled BigQuery `SKILL.md` folders, an adk-recipes retail plugin whose `EVAL.yaml` halts below an 80% pass target, and agents-cli extensions that install skills. The TCK, ext-apps and CoSAI ship skills too. The 22 skills increasingly sit as a decision layer above operator skills from other publishers. `reference_patterns`, named companions and a Snyk-style scan of the toolkit's own `skills/` are how that position becomes explicit and safe. One invariant survives every repo examined: no durable engine, recipe or protocol promises exactly-once external side effects. ADK 2.9's failed-node rerun makes safe-api-tool-calls' idempotency and reconciliation rules more load-bearing, not less.
