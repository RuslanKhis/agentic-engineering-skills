# Ownership of contested topics

Read this when a request's words fit two specialists. Each row names the
owner (the primary skill) and the neighbours that defer to it, with the line
that separates them. A neighbour still joins as a supporting skill when the
change crosses into its part. Skill descriptions carry the same boundaries as
reciprocal "Do not activate" clauses, so a host choosing from descriptions
alone lands on the same owner.

| Topic | Owner | Neighbours that defer | Distinction |
| --- | --- | --- | --- |
| Human approval and confirmation | `adk-operational-guardrails` | `safe-api-tool-calls`, `adk-agent-security`, `adk-frontend-integration`, `adk-agent-interoperability` | Guardrails owns which actions wait, the durable review record and the confirmation-and-resume flow. Security decides which tools are dangerous enough to need it (tiering from the threat model). Safe-api owns the write side: a missing or rejected confirmation never runs the effect, and an approved write runs once. Frontend renders the approval state; interoperability only sets an MCP toolset's confirmation flag. |
| Replay and duplicate effects | `safe-api-tool-calls` | `adk-workflow-design`, `adk-memory-architecture`, `adk-agent-evaluation` | Safe-api owns idempotent replay of external writes, including a workflow node re-run on resume. Memory owns continuing a session and retrying a completed response without duplicating the turn; workflow owns resume semantics; evaluation's conformance replay is a test technique, not a runtime concern. |
| Ownership of the agent's sessions (list, resume, continue) | `adk-frontend-integration` | `adk-fastapi-backend`, `adk-tool-auth-and-secrets` | The run, stream and session endpoints belong to the agent-to-browser contract; they take the user from the backend's verified principal and never from the browser. |
| Another user's records through an HTTP route | `adk-fastapi-backend` | `adk-tool-auth-and-secrets`, `adk-frontend-integration` | The verified-principal dependency and owner filters in domain-route queries are the backend's. |
| Another user's data through an agent tool | `adk-tool-auth-and-secrets` | `adk-fastapi-backend`, `adk-agent-security` | At the tool hop the principal comes from trusted session state, never a model argument, and credential selection follows it. |
| Another user's memories or retrieved history | `adk-memory-architecture` | `adk-tool-auth-and-secrets` | Store scoping, consent, retention and erasure of what persists are memory's. |
| History and context trimming | `optimise-adk-on-google-cloud` | `adk-memory-architecture` | Optimise owns what each model request carries within a session (trimming, a summariser plugin, dangling function calls, cache misses), measured on latency and tokens. Memory owns what persists and is recalled across sessions. |
| Tool result size | `adk-tool-interface-design` | `optimise-adk-on-google-cloud` | Tool-interface shapes one tool's result for the model; optimise owns the measured request-level saving and hands the shaping back. |
| Prompt wording versus measurement | `adk-agent-instructions` | `adk-agent-evaluation` and every skill whose description says "adk-agent-instructions owns prompt wording" | Instructions writes and restructures the prompt; evaluation measures a prompt change on a labelled set and does not choose the wording. |
| Few-shot exemplars | `adk-agent-instructions` | `adk-agent-evaluation` | Instructions owns choice, count, order, format and storage as data. Evaluation guarantees leave-one-out selection on development cases and measures the change; its helper takes the count as a parameter. |
| Sub-agent routing | `adk-agent-instructions` | `adk-workflow-design`, `adk-tool-interface-design` | Instructions owns the descriptions a coordinator routes on; workflow owns the orchestration structure; tool-interface owns AgentTool versus sub-agents. |
| Eval gates in CI versus eval design | `adk-release-engineering` | `adk-agent-evaluation` | Release wires the gate into CI with thresholds, repeats, cost policy and pinned judge IDs. Evaluation writes the cases and graders, calibrates judges and decides what a gate can trust. |
| Production traces into eval cases | `adk-agent-observability` | `adk-agent-evaluation` | Observability samples, redacts and exports the sessions; evaluation curates them into cases. |
| Output, tool and SQL schemas | `adk-model-and-output-contracts` | `adk-tool-interface-design`, `adk-sql-agent-engineering` | Model contracts owns `output_schema`; tool-interface owns tool parameter schemas; the SQL agent owns its SQL wire schemas. |
| Model choice, escalation and deprecation | `adk-model-and-output-contracts` | `adk-agent-evaluation`, `adk-release-engineering`, `adk-portability-planning` | Model contracts chooses the model, settings and failover. Evaluation runs the measured comparison; release executes a migration (re-baseline, pins, rollback); portability covers other providers. |
| Cost and budgets | `adk-operational-guardrails` | `adk-agent-observability`, `optimise-adk-on-google-cloud`, `adk-release-engineering`, `adk-presenter` | Guardrails enforces budgets and staged shutdown. Observability accounts and attributes cost; optimise reduces it by a measured change; release sets eval-run cost policy; presenter reports cost per outcome. |
| Retries | `safe-api-tool-calls` | `adk-model-and-output-contracts`, `adk-operational-guardrails`, `adk-workflow-design`, `adk-agent-interoperability` | Safe-api owns one external call's retries, deadlines and idempotency. Model failover on 429s is model contracts; invocation limits and repeated-tool protection are guardrails; bounded loops are workflow; remote-agent and MCP timeouts are part of interoperability wiring. |
| Repeated or wrong tool calls | `adk-operational-guardrails` (repetition) | `adk-tool-interface-design` (wrong choice) | Guardrails stops a loop of identical or failing calls; tool-interface fixes why the model picks the wrong tool or arguments. |
| MCP security versus MCP wiring | `adk-agent-security` (threat model, allowlists, pinning policy) | `adk-agent-interoperability` (connection, lifecycle, filters, prefixes) | Security decides what may be trusted; interoperability connects what was approved. OAuth tokens for an MCP server are `adk-tool-auth-and-secrets`. |
| Prompt injection | `adk-agent-security` | `protect-adk-sensitive-data`, `adk-agent-instructions`, `adk-workflow-design` | Security owns the threat model and injection-resistant structure. Data protection operates screening products (Model Armor); instructions owns wording; workflow delimits documents inside drafts. |
| Where a screen runs (blocking or parallel, relative to the agent and tool dispatch) | `protect-adk-sensitive-data` | `adk-agent-security`, `adk-operational-guardrails` | Data protection operates the screens (Model Armor, a local Prompt Guard 2 classifier) and owns their placement: a screen that must prevent an effect runs blocking, before the agent acts, and a rejected output keeps its completed tool events. Security records screening as one layer in the threat model; guardrails supplies the static halt message that replaces rejected text. |
| Credential exposure | `adk-tool-auth-and-secrets` | `protect-adk-sensitive-data` | Tool-auth keeps tokens and keys out of state, events and logs by custody. Data protection screens content for PII and secrets that users paste or tools return. |
| Redaction controls versus governance papers | `protect-adk-sensitive-data` (controls) | `adk-governance-pack` (papers), `adk-agent-observability` (content-capture gates) | Data protection builds the controls; governance cites them in papers for reviewers; observability sets content capture to the data-protection policy. Which prompt content may leave through trace, completion-upload or analytics exporters is data protection's; the exporters and pipelines are observability's. |
| Security review versus security questionnaire | `adk-agent-security` | `adk-governance-pack` | Security hardens the agent; governance answers a client's questionnaire from that evidence. |
| Decision material versus proposals and memos | `adk-presenter` | `adk-system-designer`, `adk-governance-pack`, `adk-agent-evaluation` | Presenter writes decision decks, memos, the rollout pack and the monthly value report. The designer writes proposals, statements of work and change requests; governance writes the regulatory memo; evaluation audits the results the deck cites. |
| Monthly value report | `adk-presenter` | `adk-agent-observability` | Presenter writes the sponsor report and its stop, continue or scale call; observability supplies the cited measurements. |
| First deployment versus later releases | `deploy-adk-on-google-cloud` | `adk-release-engineering`, `optimise-adk-on-google-cloud`, `adk-fastapi-backend`, `adk-agent-observability` | Deploy owns hosting choice, packaging and the first rollout. Release owns later promotion, canary and rollback; optimise owns measured tuning; the backend owns the app's process shape; observability owns telemetry and alerts. |
| Choosing the use case versus designing the system | `adk-discovery` | `adk-system-designer` | Discovery picks the use case and its measure; the designer starts once both are chosen. |
| Agent memory versus the engineer's practice profile | `adk-memory-architecture` | `practice-profile` | Memory is inside the agent; the practice profile is the engineer's own context outside every repository. |
| Retries on the model's own 429 or quota errors | `adk-model-and-output-contracts` | `safe-api-tool-calls` | Model contracts owns `retry_options`, location and failover for model calls; safe-api owns retries of a tool's external API. |
| A new feature across several areas of an existing application | `adk-engineer` | `adk-system-designer` | The engineer plans and routes a feature in an application whose design is accepted; the designer is for a new application or a substantial redesign. |
| `{key}` placeholders after an `output_key` handoff | `adk-workflow-design` | `adk-agent-instructions` | Workflow owns whether the earlier agent wrote the key in time; instructions owns template syntax inside an instruction, such as optional `{key?}` and escaping. |
| Lock-in and exit plans | `adk-portability-planning` | `deploy-adk-on-google-cloud`, `adk-model-and-output-contracts`, `adk-agent-interoperability` | Portability writes a separate assessment; hosting, failover and cross-cloud wiring on the accepted design stay with their owners. |
