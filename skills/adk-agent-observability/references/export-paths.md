# Export paths by host

Read when choosing or auditing where telemetry goes. Source statements are google-adk 2.8.0 (`telemetry/setup.py`, `google_cloud.py`, `_agent_engine.py`, `_agent_engine_metric_exporter.py`, `cli/cli_deploy.py`) unless a version is named. Google Cloud statements are vendor guidance with their page dates.

## Rules that hold on every host

- `maybe_set_otel_providers(hooks, resource)` builds a `TracerProvider`, `MeterProvider` (`shutdown_on_exit=False`) and `LoggerProvider` only for signal types that have hooks, appends generic OTLP exporters for every `OTEL_EXPORTER_OTLP_*ENDPOINT` set, and does not override a provider that another component already set globally. One owner per signal; if the application or an instrumentor sets a provider first, ADK's exporters never attach.
- `get_gcp_exporters(enable_cloud_tracing, enable_cloud_metrics, enable_cloud_logging, google_auth)` returns hooks. Traces and metrics go by OTLP HTTP to `https://telemetry.googleapis.com/v1/traces` and `/v1/metrics` (mTLS endpoints when `GOOGLE_API_USE_CLIENT_CERTIFICATE` or `GOOGLE_API_USE_MTLS_ENDPOINT` select them) with an `AuthorizedSession` from Application Default Credentials. Logs in 2.8.0 use `CloudLoggingExporter` (package `opentelemetry-exporter-gcp-logging`) with log name `adk-otel` off Agent Runtime; 2.9.0 moves logs to OTLP at `telemetry.googleapis.com` (CHANGELOG).
- The project is resolved from ADC; with no project the function logs a warning and returns empty hooks, so a misconfigured identity fails silently into "no telemetry". Check the startup log for `Cannot determine GCP Project`.
- `get_gcp_resource` merges `gcp.project_id`, `OTEL_SERVICE_NAME` / `OTEL_RESOURCE_ATTRIBUTES` and, off Agent Runtime, the GCP resource detector (GCE, GKE, Cloud Run attributes; a warning when `opentelemetry-resourcedetector-gcp` is missing). On Agent Runtime it sets `cloud.platform=gcp.agent_engine`, `service.name` to the engine id, `service.version` to the runtime revision and `cloud.resource_id=//aiplatform.googleapis.com/projects/{p}/locations/{l}/reasoningEngines/{id}`.
- Flush deliberately: `BatchSpanProcessor` and `PeriodicExportingMetricReader` export on timers; call `force_flush` on each provider in the shutdown path with its own budget and inspect the boolean result (optimise-adk-on-google-cloud's `gke-serving.md` covers GKE drain budgets). In opentelemetry-sdk 1.42.1 `BatchSpanProcessor.force_flush` ignores its timeout and returns `True` once it has attempted the export, whether or not the export succeeded (`sdk/_shared_internal/__init__.py`, read 2026-10-25), so `True` means drained, not delivered: bound shutdown with `OTEL_EXPORTER_OTLP_TIMEOUT` and confirm delivery at the destination (checklist item 5).

## Agent Runtime (Vertex AI Agent Engine)

- Master switch: `GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true` in the deployment's environment (Agent Platform tracing page, 2026-10-01: replaces `enable_tracing`; needs the Telemetry API and Logging API). `adk deploy agent_engine --otel_to_cloud` sets it and, when `.env` lacks `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS`, sets that to `false`; when `.env` already carries the switch, the flag turns on automatically (`cli/cli_deploy.py`, 2.8.0). `agents-cli deploy` to Agent Runtime sets the same switch to `true` when `.env` lacks it, plus `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=NO_CONTENT` and `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false`, and its scaffolded `fast_api_app.py` passes `otel_to_cloud` to `get_fast_api_app` only when that switch reads `true` or `1` (Agents CLI 1.11.0, `src/google/agents/cli/deploy/agent_runtime.py` and `scaffold/agents/adk/app/fast_api_app.py`, read 22 October 2026).
- Optional: `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental` plus `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=EVENT_ONLY` adds prompts, responses and `user.id` to log records (vendor; content policy is protect-adk-sensitive-data's).
- Metrics: the runtime throttles CPU when a request ends, so a periodic reader starves. `_get_agent_engine_metrics_setup` (only when `GOOGLE_CLOUD_AGENT_ENGINE_ID` is set and no `MeterProvider` is already installed) builds `_RequestDrivenMetricReader` plus a span processor that collects on `generate_content` span starts, and `maybe_install_request_metrics_middleware(app, otel_to_cloud=True)` drives it from FastAPI request start and end. Constraints in source: collect only while serving; never closer than the floor (5 s default); at least once per period (60 s) under load. Documented residual loss: a request shorter than the floor that is the last before idle loses its points. Installing your own `MeterProvider` first disables this with a warning, and metrics may be dropped between requests.
- Traces and logs are force-flushed per request by the `AdkApp` host (source comment in `_agent_engine.py`), not by this middleware.
- Trace context: the runtime passes `Google-Agent-Engine-Traceparent`; `TopSpanProcessor` stamps a `supportID` attribute on the top span from the incoming `traceparent` baggage.
- Built-in metrics on monitored resource `aiplatform.googleapis.com/ReasoningEngine` (labels `resource_container`, `location`, `reasoning_engine_id`): `aiplatform.googleapis.com/reasoning_engine/request_count`, `request_latencies`, `cpu/allocation_time`, `memory/allocation_time`, with `response_code` and `response_code_class`; ADK 2.6.0 or later with telemetry on adds the GenAI metrics as user-defined metrics; an "Agent Runtime Overview" dashboard shows sessions, turns, invocations, tokens, p50 to p99 latency, errors, topology and MCP metrics (Agent Runtime monitoring page, 2026-10-01). Stdout lands in `reasoning_engine_stdout`, stderr and build logs beside it; child resources (Sessions, Memory Bank, Code Execution) are not logged (Agent Runtime logging page, fetched 2026-10-07).
- The host availability SLI, and the denominator of the "telemetry stopped" alert in [SLO and alerting](slo-and-alerting.md), come from that built-in counter in PromQL: `sum(rate(aiplatform_googleapis_com:reasoning_engine_request_count{resource_container="projects/{project}", response_code=~"5.."}[1h])) by (location, reasoning_engine_id)` over the same series without the response filter (Google's `google-cloud-slo-alert-configuration` skill, read 21 October 2026).

## Cloud Run

- Run `adk api_server --otel_to_cloud` (the CLI calls `get_gcp_exporters` and `maybe_set_otel_providers`) or call them from the application before constructing the `Runner`. `adk deploy cloud_run --otel_to_cloud` adds the flag to the generated `CMD` (`cli/cli_deploy.py`).
- Set `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false` explicitly; `adk deploy cloud_run` does not set it for you (adk-docs `integrations/cloud-trace.md`, fetched 2026-10-07). `agents-cli deploy` does, on Cloud Run, GKE and Agent Runtime alike, as a default that `.env` or `--env-vars` can override, and its Cloud Run and GKE scaffolds call `get_fast_api_app(otel_to_cloud=True)` unconditionally (Agents CLI 1.11.0, `src/google/agents/cli/deploy/cloud_run.py`, `gke.py`, read 22 October 2026). Verify the deployed revision's variables either way.
- Metrics use the periodic reader at `MIN_EXPORT_INTERVAL_MS` (5 s). Cloud Run also throttles CPU outside requests on request-based billing; test a quiet instance for dropped points, and consider always-allocated CPU or a flush in the request path if points go missing (this is an inference from the Agent Runtime design, not documented Cloud Run behaviour).
- Correlate logs: emit structured JSON with `logging.googleapis.com/trace` as `projects/{project}/traces/{trace_id}`, `logging.googleapis.com/spanId` and `logging.googleapis.com/trace_sampled` (Cloud Logging structured logging page). The `CloudLoggingExporter` path writes OTel log records; application `logging` output needs its own correlation fields. Cloud Run keeps the gateway's request record (status, latency, caller) in `log_id("run.googleapis.com/requests")` and the container's output in `run.googleapis.com/stdout` and `stderr`; the two join only on the `trace` field (Google's `cloud-logging-query-generation` skill, read 21 October 2026).
- Host-level signals beneath the agent SLIs, all `run.googleapis.com/` metrics queried in PromQL as `run_googleapis_com:` with `monitored_resource="cloud_run_revision"`: `request_count` by `response_code_class` for availability and 4xx surges, `request_latencies` for host latency, `container/instance_count{state="active"}` against the service's `max_instances` (warn at 80 percent, page at 95), `container/memory/utilizations` p95 at or above 0.90 before an OOM exit 137, `container/cpu/utilizations` p95 above 0.85 for throttling, `container/billable_instance_time` at a 5 m rate above three times the 1 h rate for runaway scaling, `container/startup_latencies` for cold starts. Guard every ratio with a minimum request rate so scale-to-zero does not page (Google's `cloud-run-alert-configuration` skill, read 21 October 2026). Saturation and memory pressure are the usual host causes of a long gap between spans ([debugging runbook](debugging-runbook.md)). When the deliverable is these policies, consult the installed Google skill `cloud-run-alert-configuration` (from google/skills); if it is not installed, adk-engineer explains how to get it.

## GKE

- Same programmatic setup as Cloud Run. The GCP resource detector supplies the `k8s_container` resource when the metadata server is reachable.
- Exporter allowlists, custom session spans and drain budgets are optimise-adk-on-google-cloud's (`references/gke-serving.md`, `assets/session_observation.py`); do not duplicate them. This skill owns which ADK signals exist and what they mean.
- A collector sidecar or DaemonSet receiving `OTEL_EXPORTER_OTLP_ENDPOINT` is the usual place for attribute processors; the collector then needs the writer roles above through Workload Identity.

## Agents CLI scaffolds (vendor guidance)

A project generated by Google's Agents CLI carries a second content path beside the span and log gates above. Read these facts from the installed skill before auditing such a project (Agents CLI 1.11.0, `google-agents-cli-observability` skill, read 22 October 2026):

- Prompt-response logging is a completion upload, not a span attribute: `OTEL_INSTRUMENTATION_GENAI_COMPLETION_HOOK=upload`, `OTEL_INSTRUMENTATION_GENAI_UPLOAD_BASE_PATH=gs://<bucket>/completions`, `OTEL_INSTRUMENTATION_GENAI_UPLOAD_FORMAT=jsonl`, `LOGS_BUCKET_NAME` and `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental`, set by the generated `service.tf` (Terraform deploys only; a bare `agents-cli deploy` does not create the bucket). The skill states that these uploads "do **not** honor `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`", so `NO_CONTENT` on the span and event tier leaves full prompts and responses in GCS and BigQuery; removing the upload block is the only off switch. The capture policy is protect-adk-sensitive-data's; this skill records which path is live.
- The generated `telemetry.tf` creates a `<project>_telemetry` dataset, a sink with filter `labels."event.name"="gen_ai.client.inference.operation.details"`, an external table `completions` over the bucket and a `completions_view` (with a `service_version` column since 1.9.0). The sink table is named after the log id and differs by host: `gen_ai_client_inference_operation_details` on Cloud Run and GKE, `aiplatform_googleapis_com_reasoning_engine_stdout` on Agent Runtime, where GenAI log records arrive through stdout.
- `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` is the four-mode enum in ADK Python but a boolean in ADK Go (`1` or `true` captures, anything else elides); in a mixed fleet the same value means different things.
- When the deliverable is that bucket, dataset, sink or view, consult the installed `google-agents-cli-observability` skill; if it is not installed, adk-engineer explains how to get it. This skill still decides which signals, gates and SLIs the agent needs.

## OTLP third parties

When a collector's Prometheus exporter feeds the dashboards, the metric and
attribute names on the dashboard are the exporter's, not ADK's: it normalises
names to Prometheus rules (special characters, including dots, become `_`)
and by default appends type and unit suffixes (`add_metric_suffixes: true`,
deprecated in favour of `translation_strategy`, whose
`UnderscoreEscapingWithSuffixes` keeps the suffixes and
`UnderscoreEscapingWithoutSuffixes` drops them; open-telemetry/opentelemetry-collector-contrib
`exporter/prometheusexporter/README.md`, read 2026-10-23; vendor
documentation). So `gen_ai.client.operation.duration` appears as
`gen_ai_client_operation_duration_seconds_bucket` or without the unit suffix
depending on the collector's configuration; read the collector's `/metrics`
once and pin the dashboard to what it serves, and keep the dashboard lint in
the drift check keyed on the registry names before translation.

| Destination | Mechanism in adk-docs (fetched 2026-10-07) | Duplicate-span check |
| --- | --- | --- |
| Langfuse, Phoenix, Arize AX | `openinference-instrumentation-google-adk` `GoogleADKInstrumentor().instrument()` | Runs beside ADK's native spans; verify one `invoke_agent` per invocation in the destination. Version-gated: 1.0.0 (2026-09-29) requires `google-adk>=2.10` (breaking change, #3858), so a 2.8.0 project stays on the 0.1.x line (last 0.1.28, 2026-09-15); 1.0.3 (2026-10-08) forwards ADK 2.x `invoke_workflow` and `invoke_node` spans (#3846), closing the earlier report that the instrumentor suppressed them (#3844); 1.0.4 (2026-10-09) is current on PyPI. Earlier reports of orphan or duplicate spans after a partial patch (Arize community thread 2026-02-20) and an `instrument()` failure on ADK 2.10 fixed 2026-09-29 (#3857) remain symptoms to test for (package CHANGELOG, read 2026-10-22) |
| Weave, MLflow Tracing, Grafana Cloud, Datadog, Cloud Trace | OTLP exporter and a global `TracerProvider` set before ADK, or `maybe_set_otel_providers` with hooks | ADK attaches to the existing provider; no second instrumentor |
| Langfuse masking | `mask_otel_spans` applies only to Langfuse's exporter (Langfuse masking page, vendor) | Other exporters in the same process still receive unmasked attributes |

Pin `openinference-instrumentation-google-adk` to a version tested with the pinned ADK: below 1.0 for google-adk 2.8.0 and 2.9.x, 1.0 or later from 2.10. `opentelemetry-instrumentation-google-genai` now lives in the open-telemetry/opentelemetry-python-genai repository (PyPI 1.2b0, 2026-09-24, supporting `google-genai>=1.32.0`); the copy left in opentelemetry-python-contrib "only receive[s] security patches and will be removed" (contrib `instrumentation-genai/README.md`, read 2026-10-22), so cite and pin the new home. Below `1.0b0` it drops `user.id` (issue #6361, community, open). Run the agent with `run_async`; Langfuse documents that synchronous `runner.run()` executes on a thread that loses OTel context (vendor).

Keeping evaluation traces in-house with these backends (read 2026-10-25):

- MLflow (commit 77f1aff): OTLP ingestion needs a SQL backend store and the `x-mlflow-experiment-id` header. Client and server telemetry is on unless `MLFLOW_DISABLE_TELEMETRY=true` or `DO_NOT_TRACK=true`; it is also off when CI variables are present, which include Cloud Run jobs' `CLOUD_RUN_EXECUTION` and pytest's `PYTEST_CURRENT_TEST` but nothing a Cloud Run service sets (`mlflow/telemetry/utils.py`), so a pytest run cannot prove the egress behaviour. In an offline run on 2026-10-25 (mlflow 3.17.2) the server's workers also fetched LiteLLM's model cost map from `raw.githubusercontent.com` until `LITELLM_LOCAL_MODEL_COST_MAP=True` was set; with the three switches set, neither client nor server attempted any connection.
- Opik (comet-ml/opik commit 763a2ec, Apache-2.0): the SDK points at Comet's cloud and starts Sentry error reporting by default; self-host with `OPIK_URL_OVERRIDE` and set `OPIK_SENTRY_ENABLE=false`, `OPIK_ANALYTICS_ENABLE=false` and `OPIK_ENABLE_LITELLM_MODELS_MONITORING=false` (its own ADK CI sets all three, `.github/workflows/lib-adk-tests.yml`), and `OPIK_USAGE_REPORT_ENABLED=false` on the server. Its ADK integration patches ADK's global tracer and `LlmResponse.create` for the whole process and appends its callbacks after existing ones, so a guard callback that short-circuits may hide blocked calls from it (read, not run).
- deepeval: no supported self-hosted sink (`adk-agent-evaluation`'s provider compatibility).

## Flush and shutdown checklist

1. Which component owns each provider, and does anything set one earlier?
2. Is `force_flush` called on traces, metrics and logs in the shutdown handler with a budget, and is its result logged?
3. On Agent Runtime, is the metrics middleware installed (`otel_to_cloud=True` path) and is no other `MeterProvider` created?
4. Does the startup log show the project resolved and the exporter packages present (`opentelemetry-exporter-otlp-proto-http`, `opentelemetry-exporter-gcp-logging`, `opentelemetry-resourcedetector-gcp`)?
5. Does one synthetic invocation produce the expected spans in the destination within the batch delay, and one metric point within the export interval?
