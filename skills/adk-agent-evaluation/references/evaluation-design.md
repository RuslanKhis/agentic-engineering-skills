# Dataset, judge and release design

Read this when curating a dataset, calibrating a judge, enforcing work limits, testing ambiguous writes or designing a release gate. Implement only the branches required by the target application.

**Production extensions:** these procedures develop the chapter's design guidance. The verified companion shipped none of these: a holdout programme, rubric-calibration service, shared model/tool budget, remote-write reconciliation protocol, deployed staging suite or production monitoring system. Each is an addition to implement and test; the companion's historical passes cover the companion. Preserve existing interfaces and dependency pins; verify version-specific APIs before implementation. A design can finish with reviewable cases and acceptance criteria; distinguish that deliverable from implemented or executed checks.

## Curate cases with a reason to exist

1. Translate each consequential requirement into a case with an observable outcome, permitted actions and forbidden actions. Cover both action and non-action: a retrieval tool needs questions requiring retrieval and requests needing no lookup. Pair refusals with allowed successes so a refuse-everything agent fails the success cases. Run a do-nothing control as well: a scripted model that returns final text at once, put through every case's graders. An action case it passes is vacuous, because assertions that nothing else changed pass a run that did nothing; give each action case at least one assertion the do-nothing run fails (a non-action case is expected to pass it). When the model chooses between acting and escalating, give each case a reviewed expected lane and report two rates: missed escalation (must-escalate cases the agent acted on, over all must-escalate cases) as the gate, and over-escalation (cases it could have handled but escalated, over all such cases) as the usefulness measure; a raw escalation rate cannot tell the two apart. Cases that code forces to escalate are asserted at zero misses in scripted-model Runner tests, not reported as a rate (after the calibration argument in anthropics/claude-cookbooks commit bfe50e5, `managed_agents/CMA_gate_human_in_the_loop.ipynb`, read 2026-10-25; the cookbook prints lane counts and proposes no metric) (AppWorld labels each assertion by whether it passes when the agent does nothing, `src/appworld/evaluator.py` and README, same commit). Keep ownership and eligibility failures independent; a foreign object that is also ineligible obscures which guard worked. For example, a refund suite pairs "refund a $20 eligible order" (success) with "refund an order the caller does not own" (denied) and "refund an ineligible order the caller owns" (declined), so each guard is tested alone.
2. Choose the evidence source deliberately. Business rules supply critical cases before traffic exists. Accept a successful trace only after reviewing calls, arguments, tool results and final claims. Convert an incident by replacing sensitive values while preserving the failing state and sequence; record two runs before the case is accepted: on the base commit every `fail_to_pass` test fails and every `pass_to_pass` test passes, and with the reference fix applied every test in both lists passes. A test that already passes on the base commit proves nothing about the fix, and one the reference fix cannot pass is a broken oracle; a defect that cannot be reproduced on the base commit stays a case marked unvalidated, not a regression. When the merged candidate fix fails `pass_to_pass`, it is not the reference fix: write or obtain one that passes both lists to show the test is sound, report the candidate as not resolved, and leave the regression failing in CI rather than marking it expected-to-fail; the red case is the report, and the follow-up goes out on `adk-system-designer`'s ticket template (Harbor's oracle and do-nothing agents, harbor-framework/harbor commit 6099b8c, Apache-2.0, and SWE-bench's gold-patch validation, read 2026-10-25). Review synthetic cases for impossible setup, unsupported tools, invented expected answers, duplicates and unrealistic distributions. Retain the generator prompt and configuration. When the cold start needs server-generated user scenarios, consult the installed Google skill `agent-platform-eval-flywheel` (from google/skills); in an Agents CLI project the same service runs as `agents-cli eval dataset synthesize`, so consult the installed `google-agents-cli-eval` skill instead; if neither is installed, adk-engineer explains how to get them. Generated scenarios pass through this same review; the generator reads the agent's instructions and tool descriptions, so vague docstrings produce vague scenarios, and each run produces fresh scenarios with no seed (Agents CLI 1.11.0, `google-agents-cli-eval` skill `references/user-simulation.md`, read 22 October 2026). Hand-written `agent_data.turns` remain the repeatable regression form.
3. Establish solvability with the [honest-contract checkpoint](#establish-an-honest-review-contract) below. Preserve dynamic identifiers when their relationship to actual results is the assertion; replacing every identifier with a constant can remove the defect.
4. Keep ownership metadata beside the ADK assets when the schema has no appropriate field. Validate the ADK asset schema on its own, apart from this semantic review:

   ```json
   {"case_id": "refund-012", "requirement": "REQ-7", "risk": "duplicate refund",
    "source": "incident 2026-02-14", "slice": "development",
    "expected_invariant": "one refund per operation ID",
    "reviewer": "payments lead", "reviewed": "2026-03-01",
    "freshness_expires": "2026-09-01", "drift_mode": "tool API",
    "base_ref": "a1b2c3d", "reference_fix": "e4f5a6b",
    "fail_to_pass": ["tests/test_refund.py::test_second_yes_does_not_refund_twice"],
    "pass_to_pass": ["tests/test_refund.py::test_eligible_refund",
                     "tests/test_refund.py::test_foreign_order_denied"]}
   ```

5. Separate development, holdout and, where useful, reviewed recent-traffic cases. When a holdout failure directly guides a fix, move that evidence into development and replenish the holdout. Retain stable incident regressions while updating cases for changed policies and tools. Version reference answers and criteria; identify measurement changes in comparisons.
6. Write acceptance criteria as categories that generalise (every reason cites an operative policy; no condition contradicts a reason; recall of gold operative sections at or above the agreed level), not as a checklist of the exact defects found in the development cases. A criterion naming "case 003's missing splay" is a regression test, not an acceptance criterion. Validate a change motivated by one case on the other development cases before accepting it ([progressive validation](progressive-validation.md#keep-the-deliverable-and-the-method-together)).

**Completion:** cases have reviewed expectations and owners, important tasks have a passing reference, and the split records which cases influenced the candidate. Repetition addresses variation within a case; coverage across cases comes from more cases.

## Establish an honest review contract

For mandatory labels, extraction-sensitive text or dense representations, also use
[contract qualification](contract-qualification.md) to trace effective prompt,
schema and validator agreement and establish representability before dispatch.

Before model tuning or a quality cohort, retain an honestly constructed reference for each consequential outcome combination and execute it through the actual schema, validators and relevant Runner/served boundary. For document review, cover approval with required controls, refusal with separate favourable or manageable issues, unresolved evidence and contradictions. Acceptance must preserve the domain obligations as well as structural validity.

Use this transformation as a diagnostic: a refusal justified by unsafe access can coexist with a separately acceptable roof. Add the roof issue without adding it to the refusal reason; the review contract must have an honest disposition for it. Attaching its ID to the access reason merely to satisfy coverage is a failing negative control. Also delete a required approval safeguard and verify rejection. If the only passing response invents a relationship, the contract needs a representation for that outcome before another model run can usefully test it.

Retain the failing input, truthful reference, misleading-association control and required-safeguard control with their boundary results. Inspect the fixture, requirement, reference and evaluator when the reference fails; distinguish a schema's missing representation from a model's copying or substantive error. If server-established IDs or associations are being reconstructed by the model, consider compiling those identities into a draft-bound review frame, leaving relevance and support judgments to the model. Validate the adapted contract and its output size; a design proposal becomes a quality improvement once implemented and measured. When available, the workflow-design skill provides a worked review-frame example; this checkpoint remains usable without that package.

**Completion:** truthful outcomes pass at the intended runtime boundary, misleading associations and missing obligations fail, and any unexecuted boundary is named. A handwritten JSON object passing an isolated mock checker establishes only that mock's behavior.

## Shape the rubric before writing it

A rubric written as one paragraph ("rate this 1 to 10 for helpfulness") gives a number that measures nothing in particular, and anything that climbs it (a person iterating on a prompt, `adk optimize`, any loop that rewrites the agent from scores) learns the gap between that number and the goal. Before writing a rubric or a judge prompt, record three things about the agent in the plan; each changes the rubric's shape (the three axes and the four rules below are from Pouya Ghiasnezhad Omran and Tanya Dixit, "Evaluation Precedes Evolution: Rubrics for Agents That Rewrite Themselves", Google, LinkedIn, 15 June 2026, read 2026-10-28):

- **Verifiability: what code can check without a person.** A checksum, a sum within a tolerance, an identifier on an approved list, a date not in the future. Each is a programmatic assertion (next section) and runs before any judge; a case that fails one fails without a judge call, and the judge's prompt covers only what is left. A judge asked to grade arithmetic grades how plausible the arithmetic sounds. In the authors' open-source invoice sample the tax-ID checksum is plain Python (`validate_abn_checksum`) in the acting pipeline (google/adk-samples, now google/adk-recipes, at a9dc177, `python/agents/invoice-processing/invoice_processing/shared_libraries/acting/general_invoice_agent.py`; the sample was removed from main on 2026-09-09 in 3fd76ce).
- **Horizon: how many stages run before anything can be scored.** With more than one model stage, score every stage. Write one sub-rubric per stage, scoped to that stage's contract (what it receives, what it emits, what done means), with that stage's failure modes named. Grade the output the pipeline saved for that stage (the `output_key` value, the node output, or the stage record a checkpoint wrote; see [progressive validation](progressive-validation.md)). Keep one verdict per stage and failure mode in the result record, beside the end-to-end verdict. A rollup may be reported, but it never replaces the stage verdicts, and a gate reads the verdicts, not an average. The sample saves one numbered record per stage (`01_classification.json` to `09_audit_log.json`) and its investigation script keeps a verdict per phase; it also rolls the phases into a compliance percentage, and its stop gate reads that percentage (`invoice_processing/agent.py`, `_run_investigation_stage`, stop below 60). Error analysis then names the first stage that failed ([result auditing](result-auditing.md#check-the-measured-units); the `stage` field in [quality iteration](quality-iteration.md#run-the-loop)). Which input a stage's grader reads, and which reference it is held to, is set out under "Grade each stage on the input it received" below.
- **Stakes: what each wrong verdict costs once the downstream gates are counted.** Money paid out cannot be recovered; a false alarm costs a reviewer's time. Stakes settle three choices. Which error the gate protects is the TPR or TNR threshold in [expert review](expert-review.md#calibrate-one-judge-per-failure-mode). Where re-checks are spent is the asymmetric re-check described there. The figure the work is judged on is the outcome measure, below. When the discovery brief prices each error type, the stakes become a number the gate can read ("Price each error type" below).

**Judge the work on the outcome measure, not on a rubric score.** The headline figure for an iteration, a release candidate or an optimiser run is the measure the project was approved on, computed on the cases. That is adk-discovery's outcome measure when a brief exists; for an act-or-escalate pipeline, the share of cases decided correctly with no manual intervention. The rubric's stage verdicts are the diagnosis, and a rubric pass rate is a proxy. Close two gaps before trusting any score:

- **Escalation as a relief valve.** If an escalated case scores as neutral, escalating every borderline case raises the score while the share handled without a person falls (the authors report, as an illustration, a score holding at 85 per cent while that share fell from 70 to 40 per cent; reported by the source, not verified here). Count an escalated case as manual work in the outcome measure, and report over-escalation beside every score ([curate cases](#curate-cases-with-a-reason-to-exist), step 1).
- **A claimed check is not a check.** A judge that rewards wording such as "validated per section 4.2, checksum confirmed" rewards the wording whether or not the check ran, and a loop that rewrites the prompt learns to emit it. Read whether a check ran from the trace (the tool call and its response, or the stage record), never from the agent's text. A stated check with no matching record is a false completion claim and fails; the calibration set below includes one.

**Grade each stage on the input it received.** A stage's grader reads the input the stage actually had in this run (the previous stage's saved output, not the gold version of it) and asks whether the stage's output is right for that input. An auditing stage that applies the right rule to a wrongly extracted total has done its job, and the error belongs to extraction. Graded against the end-to-end reference instead, the auditing stage is marked wrong for following its evidence, and every fix aimed at it pushes it to ignore its input. The method is from Hugh Wimberly, Joshua Marker, Eddie Siegel and Shikhar Kwatra, "Eval-Driven System Design: From Prototype to Production" (OpenAI cookbook, with Fractional, 2 June 2025, https://developers.openai.com/cookbook/examples/partners/eval_driven_system_design/receipt_inspection, read 2026-10-29): measure each step "conditioned on the output of the prior step", as well as end to end. Get a reference that fits the stage's actual input, cheapest first:

1. **Code.** Where the stage's rule can be computed from its input (an amount over a limit, line items that do not add up to the total), compute the expected output from the actual input with the same code check the verifiability axis asks for.
2. **Unchanged input.** Where the stage's input matched the gold upstream record on every field the stage reads, the gold reference for that stage applies as it is.
3. **Judge or reviewer.** Otherwise a calibrated judge given the stage's actual input, or a reviewer, decides. Until one has, the stage verdict is `not evaluated`, never a pass.

Keep three results for each stage: the end-to-end verdict, the stage on its actual input, and, where it is cheap, the stage run alone on the gold upstream record. In ADK the last is a separate eval set for the stage's agent alone, whose `session_input.state` seeds the key the stage reads (`EvalCase.session_input.state`, google-adk 2.8.0 and 2.12.0, `evaluation/eval_case.py`, read 2026-10-29). A case that fails end to end while every stage passed on its own input lost something at a hand-off: the article warns that splitting a process lets stages "play telephone". Fix the contract between the stages, not the prompt of either one.

**Price each error type, and gate on the priced total against today's process.** When the outcome is a decision with two kinds of error, a case that needed the action and did not get it (a miss) and a case flagged that did not need it (a false flag), turn the measured rates into money at the brief's volume. Use the prices recorded in the discovery brief (adk-discovery's opportunity-portfolio reference, "Price of each error"):

```text
flagged = N × (p × (1 − miss rate) + (1 − p) × false-flag rate)
missed  = N × p × miss rate
total   = N × running cost per case + flagged × cost of handling a flag + missed × cost of a miss
```

Here N is the volume for the period and p the share of cases that need the action, both from the brief, never from the labelled sample. The miss rate is measured over the cases that needed the action, and the false-flag rate over those that did not. Rates within each class do not depend on how the sample was drawn, so a development set enriched in the rare class still prices correctly; an overall accuracy on that set does not, and is not compared with today's or with a target. A correct flag is the action working as designed, priced at its handling. An escalation in place of a decision the agent should have made is priced as the manual work it receives, as above; the article's own cost function leaves escalation out. Compute the same total for today's process from the brief's baseline rates and per-case cost, then for each candidate. The candidate passes when its total is below today's, not when a rate clears a round number.

In the article's receipt example, the inputs are 1 million receipts a year, 5% needing an audit, $2 an audit and $30 for each missed audit. Today's process misses 3% of needed audits, flags 2% of the rest and costs $0.20 a receipt, about $380,000 a year in all. A first model-based version, twenty times cheaper per receipt, missed 1 of 8 needed audits and flagged 1 of 12 others in its small sample. Priced the same way, it would cost about $443,000, more than the process it replaces. The figures are the source's; the arithmetic was checked here. State what the total leaves out (build, maintenance, fixed serving cost); adk-presenter's value report adds them after launch.

- **Not all evals matter.** Price each grader's failures through the decision it feeds. A field error that changes no downstream decision costs nothing and is reported, not gated. In the article the merchant name was wrong on 85% of receipts and changed no audit decision. A handwritten mark missed about half the time was estimated at $75,000 a year in missed audits (reported by the source, not verified here). Error analysis ranks its categories the same way ([quality iteration](quality-iteration.md#run-the-loop), step 3).
- **A small sample prices indicatively.** A rate from fewer cases than expert review's per-class minimum (30) gives an indicative total; quote the counts ("missed 0 of 8"). Zero misses in n cases is consistent, at 95%, with a true rate up to about 3/n (the rule of three). Compute the break-even miss rate, the highest at which the candidate still costs less than today, holding its false-flag rate f at the measured value: (today's total − N × running cost − N × handling × (p + (1 − p) × f)) ÷ (N × p × (cost of a miss − handling)). When the sample cannot rule it out, the verdict waits for more labelled cases of that class. The article's cheaper-model run missed 0 of 8, and the authors warn that the real rate will be higher. Its break-even works out at about 8.5%, which 0 of 8 cannot exclude.
- **Between two versions,** the paired interval ([tell a change from noise](quality-iteration.md#tell-a-change-from-noise)) says whether a rate moved; the price says what the move is worth. Two points of miss rate in the example are worth $28,000 a year: 1,000 more misses at $30, less the $2 audit each would have had. A change that alters the running cost, such as a cheaper model, is compared on the priced total, not on accuracy alone.
- **A price never buys a hard rule.** A forbidden action, a disclosure or a regulated decision fails the case whatever the total says.

**Carry code checks into ADK's eval config as custom metrics.** `criteria` names the metric. `custom_metrics.<name>.code_config.name` gives the dotted path of a function, called as `fn(eval_metric, actual_invocations, expected_invocations, conversation_scenario)`, that returns an `EvaluationResult` (it may be async). The evaluator sets `eval_metric.threshold` to `None` before the call, so the function sets `overall_eval_status` itself. A case passes only when at least one metric passed and none failed. A metric that returns `NOT_EVALUATED` is skipped, and a case whose metrics are all `NOT_EVALUATED` is not `PASSED` (google-adk 2.12.0, `evaluation/eval_config.py`, `custom_metric_evaluator.py`, and `local_eval_service.py` `_generate_final_eval_status`, read 2026-10-28). Before an optimiser runs on this config, read adk-agent-instructions' prompt-as-code reference ("Optimisers"). It covers what `adk optimize` scores and what it can rewrite.

## Calibrate the judge on fixed evidence

Use programmatic assertions for exact facts and business invariants. Add a judge when acceptable language or domain judgement needs it. Design one rubric per outcome class: confirmation, refusal, missing information or unknown outcome. A pending-request requirement belongs only to a confirmed creation. For example, the confirmation rubric asks "does the answer state only the outcome the receipt shows?"; the refusal rubric asks "does the answer give the policy reason without inventing a workaround?".

Build a small, human-labelled calibration set before grading candidates. Hold user input, tool calls, results and their identifiers fixed; vary only the final answer. Include an accurate answer, a false completion claim, an invented identifier or timing claim, a stated check that the fixed trace shows never ran, an acceptable paraphrase and relevant borderline cases. For example, tool evidence showing `pending_review` should reject an answer claiming money was returned. Give missing evidence an explicit grading outcome.

Use narrow properties grounded in visible evidence. Grade critical factual or authorisation rules apart from tone and style; a forbidden disclosure fails the case whatever the quality average. Confirm the installed evaluator actually receives the necessary tool evidence and supports the case type. Select the judge explicitly and record its model, settings, rubric version and grading output as their own record, beside the agent and simulator settings. A judge change (model, settings or rubric) starts a new baseline: scores before and after it are not one series, and a comparison across it reruns both sides under one judge (`adk-release-engineering`'s versioning reference records the public precedent).

On the Agent Platform evaluation service a per-outcome rubric is an `LLMMetric` whose `prompt_template` is a `MetricPromptBuilder(criteria={...}, rating_scores={"1": ..., "5": ...})`; both arguments are mandatory and omitting one raises a `ValidationError` (Google's `agent-platform-eval-flywheel` skill, read 21 October 2026; vendor guidance, confirm against current docs). A custom code metric receives `prompt`, `response` and `reference` as nested `Content` dicts, not strings: `"http" in instance["response"]` tests the dict's keys, is always false and scores every row alike, so unwrap `parts[].text` first; a remote `CodeExecutionMetric` must return a float, and a returned dict scores 0.0. Starting selections before calibration, from the same source: a RAG agent `hallucination`, `grounding`, `final_response_quality`, `safety`; a multi-turn tool agent `multi_turn_task_success`, `multi_turn_tool_use_quality`, `multi_turn_trajectory_quality`; a single-turn tool agent `tool_use_quality`, `final_response_quality`. These name what to calibrate, not a passing threshold.

In an Agents CLI project the per-outcome rubric is carried on the case as `rubric_groups.<key>.rubrics[].{rubric_id, content.property.description}`, graded by a managed rubric metric selected with `metric_spec_parameters.rubric_group_key` when a case has more than one group; the result keeps one `rubric_verdicts` entry per rubric (`evaluated_rubric.rubric_id`, `verdict`, `reasoning`) and the score is the fraction passed, which is the per-rubric record this section asks for. Limits: the single-turn adaptive metrics grade supplied groups, `multi_turn_task_success` ignores them, `rubric_group_name` on a custom `LLMMetric` is rejected, and a multi-turn group needs a local `custom_function` judge that reads `instance["rubric_groups"]`. A custom `LLMMetric` in `eval_config.yaml` takes `judge_model`, `judge_model_sampling_count` (1 to 32, the service-side counterpart of ADK's `num_samples`), `judge_model_system_instruction` and `judge_model_generation_config`; commit that file so the judge pin is versioned (Agents CLI 1.11.0, `google-agents-cli-eval` skill `references/{dataset_schema,metrics-guide}.md` and `src/google/agents/cli/eval/eval_utils.py`, read 22 October 2026). On the judge name: Google's eval skill writes a bare `judge_model: gemini-3.8-flash` on an `LLMMetric`, and the CLI forwards that entry unchanged to `LLMMetric.model_validate`; the full-resource-name requirement above was stated for `judge_model` on a predefined `RubricMetric`. The agent-evaluation, manage-metrics and evaluate-agents pages under https://docs.cloud.google.com/gemini-enterprise-agent-platform/optimize/evaluation/ (read 22 October 2026) show neither form, so treat both as vendor-skill guidance and confirm the accepted form with a one-case paid check before pinning. Consult the installed `google-agents-cli-eval` skill for the config file; if it is not installed, adk-engineer explains how to get it. This skill decides the rubric per outcome class and the calibration labels; Google's skill operates the metric configuration.

Measure false accepts and false rejects against the human labels. To diagnose inconsistent verdicts, repeat the judge on the unchanged trace. Rerunning the agent changes the evidence as well as the grader. Multiple judge samples expose variance; a vague rubric is repaired by rewriting it. Apply the external deadline from [live-evaluations.md](live-evaluations.md) to blocking grading. For agreement between judges, or between a judge and the human labels, report Krippendorff's α rather than raw percent agreement: Inspect AI ships it as a metric over per-sample lists of ratings with `nominal` (default), `ordinal` and `interval` levels, skipping samples with fewer than two ratings; α of 1 is perfect agreement, 0 is chance, below 0 systematic disagreement, and for two judges on a nominal scale it coincides with Scott's π (`src/inspect_ai/scorer/_metrics/krippendorff.py`; UKGovernmentBEIS/inspect_ai commit c2fc3d9, MIT; package inspect-ai 0.3.283; read 2026-10-22). Record the level with the figure; an ordinal rubric scored as nominal understates agreement. When Inspect is not installed, the statistic is small enough to write in the standard library: build the coincidence matrix over all pairs of ratings within each unit (each pair counted once per ordered pair, weighted by 1/(m-1) for a unit with m ratings), compute observed disagreement D_o as the sum over cell pairs of coincidences times the level's distance (nominal: 0 for equal values and 1 otherwise; ordinal: the squared difference of cumulative rank positions; interval: the squared difference of values), expected disagreement D_e from the matrix margins as if ratings were assigned at random, and α = 1 − D_o/D_e; validate the implementation against a published worked example before trusting a figure, and report a label set smaller than the declared one as incomplete rather than as a calibration result. A judge whose model is retired is a blocker for any live rerun until its `judge_model` is pinned to a dated version; the offline agreement figure on existing labels still stands.

For document evidence, load [source-support calibration](source-support-calibration.md). It includes question-only spans, omitted exceptions, unrelated citations and contradiction/absence controls. Grade source identity, span completeness, applicability, contrary evidence and support separately. Retain a model's support label as its judgment, to be checked against the evidence. Use domain-competent human review of substantive expectations when available; record AI-only expectations explicitly and limit the resulting claim.

**Completion:** retained labels and judge results show which examples are accepted, rejected or unresolved, including disagreement across repetitions. Fix false acceptance of a critical violation before enabling that judge as a gate. Treat judge exceptions, timeouts and missing scores as incomplete evaluation. Calibration code and schema checks prepare the calibration; the live run with retained verdicts completes it.

## Enforce work before dispatch

Define scope first: one invocation, conversation, trial or suite. For each participating role, record the work allowance, enforcement point and exhaustion outcome. Agent generations, tool calls, simulator invocations, judge samples, output tokens and elapsed time need separate controls. Include retries at the boundary that dispatches them; an agent callback may not observe SDK-internal attempts.

Reserve each model or tool call before dispatch so exhaustion prevents the next action. With concurrent work, the reservation must be atomic at the shared scope. Construct fresh counters for independent trials and share counters deliberately across subagents when they share an allowance. A simulator turn cap leaves work inside each turn unconstrained. Bound cumulative input usage and currency with their own controls; an output-token cap covers output.

Compose checks with existing callbacks. Preserve receipt rendering, state guards and configured failure injection when adding budget callbacks; replacing a callback can remove a tested safety boundary. Decide explicitly whether a callback-produced terminal response consumes a generation allowance or avoids provider dispatch, and test the chosen accounting rule.

Exercise zero remaining allowance, exact-limit success, the next prohibited dispatch, separate model/tool exhaustion, cancellation and trial reset using deterministic doubles. Assert dispatch counts and stored effects as well as the exception. Use the process deadline for blocking work and retain partial evidence. An accepted provider request completes on the provider's side whatever local termination does. Report any currency, token or retry limit that remains unenforced.

**Completion:** each claimed limit has an enforcement boundary and an exhaustion regression; the run plan states residual work possible after cancellation.

## Grade the end state, not the path

For a case whose success is a state of the backend rather than a particular sequence of calls, grade the state. The method is tau2-bench's (sierra-research/tau2-bench v2.0 line, commit 05736c2, MIT, read 2026-10-22; benchmark method, not benchmark data): the case carries one reference trajectory of tool calls, and the agent's run passes when its backend reaches an equivalent end state, so any path that gets there passes. On ADK the fresh backend is the scripted-model Runner test's own fixture ([deterministic tests](deterministic-tests.md)) or a per-trial copy of the staging store.

1. **Replay the reference.** Replay the case's reference trajectory on a fresh copy of the backend to derive the target end state.
2. **Diff the whole fixture.** Diff the start and end store of the agent's run and of the reference, across every table, not only the tables the case is about. Compute the set of changed tables from the raw diff and require it to equal the reference's, apart from a short, named list of bookkeeping tables each with its reason; a per-field ignore never hides a table change, so if the application touches a volatile field when it only reads, name that table as an exception. Within each expected table, assert which records were added, updated or removed and which fields changed, putting volatile fields such as timestamps and generated ids on a per-assertion ignore list rather than dropping the table. A hash of the relevant tables passes an agent that also edits another user's profile or an audit row, and fails spuriously when replayed ids differ (AppWorld's database diff at table, record and field level, StonyBrookNLP/appworld commit 42b5bcf, Apache-2.0 for the public code, `src/appworld/collections/models.py`, read 2026-10-25; method only, nothing from its encrypted bundles).
3. **Compare effective mutations.** Compare the multiset of mutating calls whose result was a success: on ADK, calls to the write- and irreversible-tier tools (`adk-agent-security`'s "Tier every tool") whose function response the tool's own contract marks as a success, not an error status or a raised exception. A reversible detour, a booking made and cancelled, nets to the same state, and a record diff cancels an identical add and remove, so the diff alone would pass it; with both, an extra mutation fails without a per-call rule. The multiset sees only tools listed as mutating, so a new or unlisted tool escapes it and the whole-fixture diff is what catches its writes; in an offline trial on 2026-10-25 a user-record edit through an extra tool was caught only by the diff.
4. **Gate the case.** The reference trajectory is required as a sequence only when the case says so (`reward_basis` lists the components that gate the reward; the default is the database state plus the information the agent had to communicate). Component rewards multiply, so a zero in any listed component zeroes the case. A run that ended for any reason other than the agent or the user stopping scores zero before any grader runs; on ADK that is the Runner raising, `LlmCallsLimitExceededError` from `RunConfig.max_llm_calls`, an `abort_signal`, or the harness's own timeout. A designed stop (a guardrail's halt with its static message, as `adk-operational-guardrails` defines it) is the agent stopping; a case that expects one says so. A criterion the case does not define means "not evaluated", not "failed". Extra reference material (environment assertions, natural-language assertions judged by a model) gates only when listed. Grade the information to communicate from the final response: deterministic checks that each required fact is present and that no claim contradicts the end state (a "ticket updated" message when nothing changed), or a pinned judge when the case lists one.

`ANY_ORDER` trajectory metrics never replace this check because they do not see the extra mutation. When the harness captures the OpenTelemetry span tree of the run, the trajectory can be graded from the spans instead of from events (Pydantic Evals' span-based evaluators query the tree for a tool span by name or attribute and assert order and counts pydantic/pydantic-ai commit eb0bd08, MIT, read 2026-10-23; another framework's documentation, restated, `docs/evals/evaluators/span-based.md`); on ADK that is the native `execute_tool` and `invoke_agent` spans under `adk-agent-observability`'s schema, graded by the same end-state rule, not by span presence alone.

Under an injected fault (the matrix in [execution evidence](execution-evidence.md)), grade three things with checks rather than a judge. Failure honesty: the final answer does not repeat the corrupted sentinel as fact, does not claim success after an injected error, and says what could not be done; check the last part deterministically when the agent returns a structured status, and otherwise with a pinned judge calibrated as below. Partial completion: the fraction of the end-state effects the case expects under that fault (which may differ from the twin's) reached, with zero forbidden effects; an answer from model knowledge where the required tool failed counts as not done. Recovery discipline, read from the trajectory: no same-argument retry after a validation or execution error, no more than the project's retry bound after a timeout or network error (a project with no bound has a finding for `safe-api-tool-calls`), a retry with changed arguments allowed, and no replay of a write after an ambiguous result (`adk-operational-guardrails`' runtime bounds). Count calls to the faulted tool by error class against that bound, which is what catches a retry storm; report token and call usage against the no-fault twin as a diagnostic, where a sharp rise points to a storm and a sharp fall to an agent that gave up. A pinned, calibrated judge may add a wording score. Strands' resilience judges score a trace with no failure in it as acceptable (0.5) and pass at 0.5, so a case whose fault never fired passes there; here it is NOT RUN (strands-agents/evals commit f6b894f, `src/strands_evals/evaluators/chaos/`, read 2026-10-25).

## Reconcile ambiguous mutations

Use this branch only for an application with external writes. Distinguish explicit rejection, confirmed commitment and an unknown result after submission. A missing response leaves the outcome unknown.

Define the adapter's real reconciliation contract: a stable operation/idempotency identifier, durable idempotency scope, payload-conflict policy and an authorised status query or equivalent lookup. Preserve the same operation identity across permitted recovery. When the service has no status endpoint, document the unresolved state and the safe stopping/escalation path.

Create a deterministic fault fixture that commits the effect and then loses the acknowledgement. Drive it through the actual tool/orchestration boundary. Assert one stored effect, an unknown initial observation, a reconciliation attempt before further mutation, and a final claim grounded in the reconciled status. Add explicit rejection and successful-acknowledgement controls so the test distinguishes all three outcomes. If reconciliation remains unknown, assert that the application stops further mutation and reports uncertainty. Separately test concurrent duplicate requests and conflicting payloads according to the service contract.

An observer or grader failure after submission uses the same evidence discipline: preserve the operation identity and inspect status instead of resubmitting to obtain a measurement. The companion's successful-then-rejected receipt regressions remain useful, and this remote protocol needs its own fixture.

**Completion:** the fault regression proves the recovery decision and effect count. Durable storage, real authentication and remote timeout semantics remain separate contract/staging checks.

## Build gates and close the feedback loop

Assign checks to the smallest useful stage: deterministic rules, schemas and scripted orchestration on ordinary changes; a bounded set of critical live cases on selected changes; broader simulations and judge comparisons periodically; holdout and isolated staging evidence before release. This is a scheduling design; provisioning or running services needs its own request. A scheduled evaluator over production traces (Google's Ambient Quality Agent recipe; adk-release-engineering's production-feedback reference owns the decision) is a stage of its own: its insights are evidence about the running release, count as incomplete when the investigation did not run, and gate a promotion only where the release record says so.

Specify staging assertions for capabilities the application actually has: cross-user identity denial, session reload/compaction, adapter schemas and retry contracts, allowed subagent routing and shared limits, and complete request processing. These properties are established on the isolated target; a healthy endpoint or local fake establishes availability. Use deployed-equivalent permissions on isolated targets under the authorised scope.

Pair baseline and candidate by case and fixture, holding criteria and trial counts steady. Report successful/attempted counts and critical slices separately; explain changed measurement definitions. Report the change as a paired difference per case with its interval, runs averaged within each case and the standard error clustered on the scenario when cases are variants of one, and state the minimum detectable difference; a move inside the interval is "within noise" ([tell a change from noise](quality-iteration.md#tell-a-change-from-noise) gives the method and `paired_difference.py`). Size the holdout from the smallest difference the release decision turns on, not from a fixed count. Use [result-auditing.md](result-auditing.md) for completeness and verdict checks. Preserve failed product trials; bounded infrastructure recovery must retain its failed or incomplete attempts.

Plan observation around allowlisted metadata: opaque trace linkage, versions, tool name, result category, timing, retries, policy decision, usage and final status. Distinguish submission from later business completion. Keep message-content capture disabled by default, including `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false` where applicable. Review minimisation, access, retention and export before production excerpts reach fixtures or judges; apply the same policy to CI artifacts and recordings.

When a reviewed production session becomes a managed-evaluation case, the mapping from an ADK `Session` dump to the service's `AgentData` is mechanical: every event with `author == "user"` opens a new `ConversationTurn` (0-based `turn_index`), each other event keeps its `author` so sub-agent attribution survives, `actions.state_delta` is carried on the event, and roles are `user`, `model` or `tool`, never `assistant` (Google's `agent-platform-eval-flywheel` skill, `scripts/parse_adk_traces.py`, read 21 October 2026). Use that script or reproduce the mapping; the semantic review above still decides whether the session is a case.

**Completion:** each release gate identifies its evidence and failure owner. A production incident becomes a sanitised reproduction, an old-version failure when reproducible, a verified correction and monitored affected slice. Cases that taught the fix are development evidence; fresh reviewed evidence supplies the holdout.
