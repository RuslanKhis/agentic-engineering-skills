# Delivery profiles: size the design to the people and time available

Read during the scope gate, before choosing components, and again when writing
the plan. Real people build these systems inside fixed hours. The same product
idea needs a different design when one person has five hours for a demo than
when six engineers have four months for a regulated launch. This reference
turns the constraint answers into a delivery profile, decides which concerns
are built now, kept minimal or deferred, checks the plan against capacity, and
splits it into phases that ship first and continue later.

## Ask for capacity, not only scope

Ask only what the request has not answered, with a default the user can accept
in one word. Group the questions in one turn; they are the scope gate.

| Question | Default | Why it changes the design |
| --- | --- | --- |
| When must the first useful version exist, and what happens after it (thrown away, continued, launched)? | No deadline; continued | Sets phase 1 and whether phase 1 code must be reusable |
| Who builds it: how many people, hours each per week, familiarity with ADK and GCP? Who runs it afterwards? | One developer, part time, new to ADK | Converts the deadline into person-hours and setup cost |
| What spend is available for models and cloud? | Small personal allowance | Model tier, hosted services, evaluation repeats |
| Who uses or judges it: the builder, a demo audience, employees, external customers? What will the judge read? | The user, reading the design | Identity, frontend, availability, documents |
| What data does it touch (synthetic, internal, personal, regulated) and what can it change (nothing, drafts, reversible writes, money, messages to real people)? | Synthetic data, read only | Sets the floor and the security depth |

The last row decides the risk, whatever label the user gives. A "POC" that
sends email to real customers from a real inbox carries production risk;
plan it as a POC with that risk removed (see the floor below), not as a POC
that ignores it.

## Choose the profile

| Profile | Purpose | Done means | Design and plan size |
| --- | --- | --- | --- |
| Proof of concept or exploration | Show the core idea works, to the builder or a demo audience | The core journey runs end to end on sample inputs, and someone saw it | One page of design, three to six goals, a "later" list |
| Time-boxed assignment judged on output | Produce good results under a fixed time | Measured quality on labelled cases and the deliverable regenerated by the final method | One page; see the [proportionality rule](design-decisions.md#size-the-first-slice-to-the-judge) |
| Internal tool | Useful daily work for known colleagues | Colleagues use it with their own identity on real internal data | Two to four pages; access control and data scoping are first-class |
| MVP or pilot | First external users, learning what they need | Real users complete the journey safely; the team can see failures and cost | Two to four pages per phase; phase 1 fits the deadline, phase 2 is written |
| Production service | Reliable operation at agreed targets | Agreed SLOs, release gates and recovery are in place and tested | As long as its decisions require |

Say which profile you chose and why in one line, and let the user correct it.
A profile can change at a phase boundary: a POC that will become an MVP gets a
phase 2 that graduates it.

## Decide the depth per concern

Use this as the default emphasis; adjust to the journey and say why.
**Build** means a goal implements and tests it now. **Minimal** means the
cheapest form that keeps the floor, usually a configuration line or a test.
**Defer** means a "later" goal with a trigger.

| Concern | POC | Internal tool | MVP or pilot | Production |
| --- | --- | --- | --- | --- |
| Core judgment end to end, measured | Build, on sample inputs with a handful of checked cases | Build, with a small regression set | Build, with an evaluation set | Build, with gated evaluation |
| User identity and per-user data scope | Defer when single user and synthetic data | Build: existing SSO, users see their own records | Build | Build |
| Secrets and credentials | Minimal: environment or Secret Manager, never in code or prompts | Build: workload identity, least privilege | Build | Build, with rotation |
| External writes and effects | Minimal: fake or staging targets, or a human sends | Build: confirmation for writes | Build: idempotent writes for money and orders | Build: full replay and reconciliation |
| Sensitive data | Defer with synthetic or anonymised data; otherwise Minimal | Minimal: scoped access and no content in logs | Build | Build |
| Prompt injection and agency | Minimal: break the untrusted-input-plus-write combination | Build: per-agent exposure check | Build | Build: threat model and adversarial suite |
| Budgets and loop limits | Minimal: `max_llm_calls` and a spend cap | Minimal | Build: per-user allowance | Build: shared budgets and approval |
| Memory and retrieval | Only what the journey needs; in-memory sessions | Build what the journey needs | Build | Build |
| Frontend | `adk web` or the simplest page | A simple authenticated page or an existing tool | Build | Build |
| Hosting | Local, or one Cloud Run service | Cloud Run behind IAP or the existing platform | Chosen host with a rollback | Chosen host with recovery and cleanup |
| Observability | Defer: console logs | Minimal: structured logs and model cost | Build: traces and token cost | Build: SLOs and alerts |
| Release engineering | Minimal: pinned model ID | Minimal: pinned versions and unit tests in CI | Build: evaluation in CI | Build: canary and joint rollback |
| Performance and cost tuning | Defer | Defer until measured | Defer until measured | Build where targets need it |

Keep the depth visible in the design's scope block as a short table: concern,
depth now, and the trigger that raises it. A concern the journey does not touch
is left out with a word, not a row per missing feature.

## Keep the floor at every profile

These cost minutes, not days, and their absence causes harm that a demo cannot
undo. They hold even when the user says security can wait; that instruction
lowers the depth, never the floor.

- No secrets in source, prompts, logs or shared documents.
- A spend stop: `RunConfig.max_llm_calls` where the application owns the
  Runner, and a model-spend cap the user set. When a demo runs through
  `adk web` or another host you do not configure, put the cap on the model
  project instead (a quota or budget alert).
- Nothing irreversible or visible to a real outside person (money moved, a
  message sent, a record changed) happens without a human approving it, unless
  the user explicitly accepts that risk after hearing it in one sentence.
- Real personal data enters a POC only when the user chose it, scoped to what
  the journey needs and kept out of logs.
- The model ID is pinned, so the demo behaves as it did yesterday.

When a floor item conflicts with the request, propose the cheapest design that
keeps it and still shows the idea: drafts a human sends instead of automatic
replies, a staging API instead of the real one, the anonymised sample instead
of the live inbox. Record the user's choice. If they accept a risk, write it in
the design as an accepted risk with its owner and the condition that ends it.

Mark a POC or internal tool with who may use it and on what data. Write the
**graduation conditions**: what must be built before it reaches more users,
real data or outside people. Those conditions become the next phase's goals.

## Check the plan fits the people

Estimate each goal as a range of focused hours for the team's stated
familiarity, and label the estimates as assumptions. Compare phase 1 with the
capacity:

- Capacity is people × available hours × a focus factor. Use about 0.6 for
  part-time or interrupted people and about 0.8 for a dedicated block such as
  a single afternoon.
- First use of ADK, GCP or a new provider costs setup time: an hour for a local
  agent with an API key, half a day or more for a GCP project with IAM.
- Keep 20 to 30 percent in reserve for demo preparation, setup surprises and
  the final run.

Phase 1 fits when the high end of its estimate range is within capacity minus
the reserve. If only the low end fits, say so and name the goals that move to
phase 2 when the work runs high. Abuse and spend limits, such as a per-user
allowance on a public service, are part of the floor, not scope to cut.

If phase 1 does not fit, cut scope, not the floor: simplify a goal, move it to
the next phase, or replace a build with a minimal form. Show the user the cut
line ("fits: G01 to G04, about 4 hours of 5; next phase: G05 to G08") and ask
them to confirm or move it. When someone may work alone, name the order in which
goals stay useful if time runs out early.

## Split the plan into phases

Write all phases in one plan so another session can continue "when things are
quieter" without a new design conversation.

1. **Phase 1, ship:** the goals that fit the capacity and deliver the profile's
   "done". Each is end to end and demonstrable on its own.
2. **Phase 2, harden or graduate:** the graduation conditions and the deferred
   controls the next audience needs, written as goals with skills and
   acceptance. Leave them coarser than phase 1 when phase 1's results could
   change them, but give each at least its primary skill, an estimate range
   and one observable acceptance check, so a later session can start it.
3. **Later:** the remaining deferred items, one line each with the trigger that
   brings it forward (more users, real data, a measured latency, an incident,
   a model retirement date) and the risk accepted while it waits.

Say whether phase 1 code is meant to be kept. A throwaway demo can hard-code
what a kept slice would configure; a kept slice puts the same choice where
phase 2 can change it. Most POCs that impress get continued, so prefer the kept
form when it costs little more.

## Compact form for short work

A proof of concept or a time-boxed assignment gets one file of about 1,200
words: the design and plan together. Its reader has minutes and the builder
has hours; a document longer than the work it plans has failed its profile.
Use these sections and leave the rest of the design template out, rather than
marking each section not applicable:

1. **Constraints and profile:** the scope-gate table, with assumed answers
   folded in as one line each (answer and what depends on it).
2. **Journey and shape:** the journey in three sentences, what the model
   decides and what code controls, a small diagram only if it saves words.
3. **Decisions:** at most six, one line each in the requirement, choice,
   tradeoff, check order.
4. **Floor, depth and deferred:** one table of concern, depth now, trigger.
   Graduation conditions as a short list.
5. **Plan:** phase 1 goals of four to six lines each (outcome, estimate,
   primary skill, acceptance, run prompt), the capacity sum and cut line,
   phase 2 goals of one to three lines each, and the later list.
6. **Open decisions and next prompt.**

Failure tables, data-authority tables and observability sections appear only
when the journey actually holds that risk, and then as two or three rows.

## Examples

**Five hours, one developer, demo tomorrow, 50 anonymised emails.** POC.
Capacity about 5 × 0.8 = 4 hours, so roughly 3 hours of goals after reserve.
Phase 1: a local agent that classifies an email and drafts a reply for a human
(1.5 hours), a script that runs the 50 samples into a reviewable table and a
handful of checked labels (1 hour), `adk web` for the demo with a pinned model
and a call cap (0.5 hour). Floor: no sending; drafts only; sample data only.
Phase 2, if the demo lands: real inbox access with scoped credentials, sending
behind approval, an evaluation set, Cloud Run behind IAP. Later: SLOs, CI
evaluation gate, cost tuning, each with its trigger.

**Two engineers at half time for three weeks, 40 finance colleagues, Google
Workspace sign-in.** Internal tool. Capacity about 2 × 0.5 × 15 days × 6 hours
× 0.6 ≈ 54 focused hours. Identity and "employees see only their own claims"
are built in phase 1, enforced in code from the verified user, with
cross-user denial tests. A canary, SLOs and an adversarial suite are deferred
with triggers, because the users are known colleagues and the tool only reads.

**Three people, two weeks to an MVP, customers can place orders.** MVP. Order
placement is money: idempotent order creation and explicit confirmation are in
phase 1 even though it delays recommendations polish. Evaluation in CI,
per-user budgets and traces follow in phase 2; tuning waits for measured traffic.
