# Delivery profiles: size the design to the people and time available

Read during the scope gate, before choosing components, and again when writing
the plan. Real people build these systems inside fixed hours. The same product
idea needs a different design when one person has five hours for a demo than
when six engineers have four months for a regulated launch. This reference
turns the constraint answers into a delivery profile, decides which concerns
are built now, kept minimal or deferred, checks the plan against capacity, and
splits it into phases that ship first and continue later.

## Ask for capacity, not only scope

Ask only what the request has not answered, with a default the user can accept
in one word. Group the questions in one turn; they are the scope gate.

| Question | Default | Why it changes the design |
| --- | --- | --- |
| When must the first useful version exist, and what happens after it (thrown away, continued, launched)? | No deadline; continued | Sets phase 1 and whether phase 1 code must be reusable |
| Who builds it: how many people, hours each per week, familiarity with ADK and GCP? Who runs it afterwards? | One developer, part time, new to ADK | Converts the deadline into person-hours and setup cost |
| What spend is available for models and cloud? | Small personal allowance | Model tier, hosted services, evaluation repeats |
| Who uses or judges it: the builder, a demo audience, employees, external customers? What will the judge read? | The user, reading the design | Identity, frontend, availability, documents |
| Does it need its own web interface, who can reach its URL, and will other developers continue it? | `adk web` for the builder only; not handed over | Frontend depth, identity, the handover fundamentals in [web application defaults](web-app-defaults.md) and the [security baseline](security-baseline.md) tier |
| What data does it touch (synthetic, internal, personal, regulated) and what can it change (nothing, drafts, reversible writes, money, messages to real people)? | Synthetic data, read only | Sets the floor and the security depth |
| Which reviews need a presentation, for whom and when: before the proof of concept is built, after it to decide on production, after the production build? | All three, business audience, dates to confirm | Presentation goals at the phase boundaries and the decision waits the next phase depends on |

The data row decides the risk, whatever label the user gives. A "POC" that
sends email to real customers from a real inbox carries production risk;
plan it as a POC with that risk removed (see the floor below), not as a POC
that ignores it.

## Choose the profile

| Profile | Purpose | Done means | Design and plan size |
| --- | --- | --- | --- |
| Proof of concept or exploration | Show the core idea works, to the builder or a demo audience | The core journey runs end to end on sample inputs, and someone saw it | One page of design, three to six goals, a "later" list |
| Time-boxed assignment judged on output | Produce good results under a fixed time | Measured quality on labelled cases and the deliverable regenerated by the final method | One page; see the [proportionality rule](design-decisions.md#size-the-first-slice-to-the-judge) |
| Internal tool | Useful daily work for known colleagues | Colleagues use it with their own identity on real internal data | Two to four pages; access control and data scoping are first-class |
| MVP or pilot | First external users, learning what they need | Real users complete the journey safely; the team can see failures and cost | Two to four pages per phase; phase 1 fits the deadline, phase 2 is written |
| Production service | Reliable operation at agreed targets | Agreed SLOs, release gates and recovery are in place and tested | As long as its decisions require |

Say which profile you chose and why in one line, and let the user correct it.
A profile can change at a phase boundary: a POC that will become an MVP gets a
phase 2 that graduates it.

## Decide the depth per concern

Use this as the default emphasis; adjust to the journey and say why.
**Build** means a goal implements and tests it now. **Minimal** means the
cheapest form that keeps the floor, usually a configuration line or a test.
**Defer** means a "later" goal with a trigger.

| Concern | POC | Internal tool | MVP or pilot | Production |
| --- | --- | --- | --- | --- |
| Core judgment end to end, measured | Build, on sample inputs with a handful of checked cases | Build, with a small regression set | Build, with an evaluation set | Build, with gated evaluation |
| User identity and per-user data scope | Defer for a builder-only local demo. Minimal when reachable at a URL: managed sign-in with an allowlist, principal from the token (SB02) | Build: existing SSO, users see their own records | Build | Build |
| Secrets and credentials | Minimal: environment or Secret Manager, never in code or prompts | Build: workload identity, least privilege | Build | Build, with rotation |
| External writes and effects | Minimal: fake or staging targets, or a human sends | Build: confirmation for writes | Build: idempotent writes for money and orders | Build: full replay and reconciliation |
| Sensitive data | Defer with synthetic or anonymised data; otherwise Minimal | Minimal: scoped access and no content in logs | Build | Build |
| Prompt injection and agency | Minimal: break the untrusted-input-plus-write combination | Build: per-agent exposure check | Build | Build: threat model and adversarial suite |
| Budgets and loop limits | Minimal: `max_llm_calls` and a spend cap | Minimal | Build: per-user allowance; a cost contract with a stop | Build: shared budgets and approval; the cost contract, labels and a cost review |
| Memory and retrieval | Only what the journey needs; in-memory sessions | Build what the journey needs | Build | Build |
| Frontend | `adk web` on loopback for a builder-only demo. Otherwise Build: the baseline single-page app from web application defaults, one browser journey | Build | Build | Build |
| API contract and typed client | Build when handed over: generated client and drift check | Build | Build, with a breaking-change check | Build, with a breaking-change gate |
| Web security baseline | Tiers 1–2; also tier 3 when reachable at a URL or handed over | Tiers 1–4 | Tiers 1–5 | Tiers 1–6 |
| Hosting | Local, or one Cloud Run service | Cloud Run behind IAP or the existing platform | Chosen host with a rollback | Chosen host with recovery and cleanup |
| Observability | Defer: console logs | Minimal: structured logs and model cost | Build: traces and token cost | Build: SLOs and alerts |
| Release engineering | Minimal: pinned model ID | Minimal: pinned versions and unit tests in CI | Build: evaluation in CI | Build: canary and joint rollback |
| Performance and cost tuning | Defer | Defer until measured | Defer until measured | Build where targets need it |

Keep the depth visible in the design's scope block as a short table: concern,
depth now, and the trigger that raises it. A concern the journey does not touch
is left out with a word, not a row per missing feature.

The contract set follows the same depth. A read-only proof of concept needs
three to five contracts (who may ask, what data is in scope, grounded answers,
what failure looks like) plus the floor. A tool that writes adds confirmation
and authority contracts; money, orders or publishing add idempotency, inventory
or rights, and recovery contracts. A deferred control removes or weakens a
contract only by saying so: its Evidence reads `deferred: <trigger>`.

## Keep the floor at every profile

These cost minutes, not days, and their absence causes harm that a demo cannot
undo. They hold even when the user says security can wait; that instruction
lowers the depth, never the floor.

- No secrets in source, prompts, logs or shared documents.
- A spend stop: `RunConfig.max_llm_calls` where the application owns the
  Runner, and a model-spend cap the user set. When a demo runs through
  `adk web` or another host you do not configure, put the cap on the model
  project instead: a quota stops calls, while a budget alert only warns
  someone who must then act.
- A resource that charges while provisioned (a database instance, a deployed
  vector index, a managed RAG database, minimum instances, a reservation, a
  load balancer) is created only after the goal records its idle cost at the
  chosen configuration with the pricing date, its cleanup command and how its
  absence is verified; a POC's plan ends with a teardown goal that runs them.
  The [resource cost ledger](resource-costs.md) says which resources these are.
- Nothing irreversible or visible to a real outside person (money moved, a
  message sent, a record changed) happens without a human approving it, unless
  the user explicitly accepts that risk after hearing it in one sentence.
- Real personal data enters a POC only when the user chose it, scoped to what
  the journey needs and kept out of logs.
- Nothing reachable at a URL without sign-in: ADK's own server routes are
  never exposed, and the application's routes fail closed when no verifier
  is configured.
- The model ID is pinned, so the demo behaves as it did yesterday.

When a floor item conflicts with the request, propose the cheapest design that
keeps it and still shows the idea: drafts a human sends instead of automatic
replies, a staging API instead of the real one, the anonymised sample instead
of the live inbox. Record the user's choice. If they accept a risk, write it in
the design as an accepted risk with its owner and the condition that ends it.

Mark a POC or internal tool with who may use it and on what data. Write the
**graduation conditions**: what must be built before it reaches more users,
real data or outside people. Those conditions become the next phase's goals.

## Check the plan fits the people

### Estimate human effort per goal

An estimate is the person-hours of human effort for a developer working with a
coding agent and these skills. It is not the agent's run time, and not the time
to type the code by hand. Give every goal and ticket a range in two parts:

- **Hands-on:** reading the goal, the decisions only a person can make,
  accounts, keys, GCP projects, IAM and OAuth clients, gathering or labelling
  data, judging model output on real inputs, demo preparation, conversations
  with stakeholders.
- **Review and verify:** reading the agent's change, running the tests and the
  application, checking the acceptance cases by hand, fixing what review finds.

Round to quarter hours for a proof of concept and whole hours above it; finer
splits suggest a precision the estimate does not have. Size review to the
change, not by a fixed ratio: an authorization boundary,
a write to money or a security control needs a careful read and adversarial
checks; a template, a configuration line or a test fixture needs a glance.

A coding agent shortens code writing. It does not shorten console setup,
labelling, judging output quality, debugging a live integration or waiting for
someone's decision, so a goal made mostly of those costs nearly as much as
it would without an agent.

A wait that is requested on day 1 runs in parallel with the work. Give it its
own schedule entry (for example `W1` with `total: 0` and `wait_days`, no
owner) and make the goals that need it depend on it, rather than adding the
wait to the end of a goal.

Record **calendar waits** separately, not as hours: a security review,
an IAM grant from another team, provider app verification (Google's
verification of restricted Gmail scopes takes weeks), a DPIA sign-off. A wait
blocks a goal's start or finish; it does not consume capacity. Put it on the
goal and start it early.

Starting points for an experienced ADK developer, agent-assisted, hands-on
plus review. Label them as assumptions and adjust to the project:

| Slice | Human hours |
| --- | --- |
| Local `LlmAgent` with one or two function tools and offline tests | 1–2 |
| A tool against a real API, with confirmation and actionable error results | 2–4 |
| Retrieval over a small document set, checked against a few gold questions | 3–6 |
| Per-user identity through existing SSO, with cross-user denial tests | 4–8 |
| Delegated per-user OAuth with consent, refresh and disconnect | 8–16, plus provider verification wait |
| Evaluation set of 20 to 50 labelled cases with a runner (mostly labelling) | 4–8 |
| First Cloud Run deployment with a service account and secrets | 3–6 |
| Evaluation gate in CI | 3–6 |
| Stakeholder presentation for one audience: outline from plan evidence, narrative, questions, one rehearsal (`adk-presenter`) | 3–6, plus the review date as a wait |

For a team new to ADK, multiply by about 1.5. State the multiplier once in
the plan and apply it to every implementation goal, hands-on and review
alike, rather than to some; presentation, labelling and stakeholder goals
are not ADK work and keep their own estimates. For a team new to GCP, add a day for the first project, billing, IAM
and deployment, on the first goal that needs them. A range whose high end is more than twice its low end hides an
unresolved question: make that question a short discovery goal.

Keep the numbers consistent. The plan's goal entry is the only source of each
estimate and calendar wait: the phase total is the sum of its goals, each
ticket copies its goal's figures and acceptance cases but links to the plan
for the route and rationale instead of repeating them, and prose elsewhere refers to the goal ID
instead of restating a number. With several people, assign goals to people and
compare each person's load with their own hours. The phase cannot finish
before its longest chain of dependent goals, nor before the busiest person
works through their own goals in order; name whichever is longer, high end
included, and compare it with the calendar.

For one person on a proof of concept, add the goals by hand in the plan; the
chain is the sum. With several people or several weeks, do not do this
arithmetic in your head. Write the phase's goals into the
plan's `yaml` schedule block (see the [plan template](../assets/implementation-plan-template.md)),
then run the helper with the team's focused hours per day and the working days
available:

```bash
python3 "$SKILL_DIR/scripts/check_schedule.py" --plan docs/plans/<topic>.md \
  --tickets docs/tickets/<topic>/ --days <working days> \
  --design docs/architecture/<topic>.md \
  --reserve 0.25 --person "Dev A=3.6" --person "Dev B=3.6"
```

Give each person's full focused hours per day; `--reserve` holds the same
share back on the calendar as on the hours, so the reserve is not spent twice.

With `--design` it also checks that every coverage-grid cell cites an
acceptance item, that every contract in the design is cited by a goal or
marked `gap:` or `deferred:`, and that every security rule at Build or
Minimal depth is cited by a goal or marked `n/a:` or `deferred:`. It adds up the phase, compares every ticket with
the plan, and reports each
person's load, the longest dependent chain and a finish range in working days
that respects dependencies, one goal at a time per person and calendar waits
(`wait_days`). Exit status 1 means something does not fit or disagrees. Quote
its figures in the plan instead of your own, including any comparison such as
"half the capacity", and fix the plan or the cut line until the result is what
you tell the user.

When a run fails, change the plan only in ways that are true of the work: cut
or move scope, add people, or extend the date. Do not remove a dependency,
shorten a wait or drop a review to make the numbers fit. A wait that depends on
someone else stays at its real length until they confirm otherwise; add a goal
or first step that requests it today. When a review or check moves to another
goal, its hours and calendar time move with it. List in the plan what you
changed after a failing run and why; a passing run checks the arithmetic, not
the assumptions. Run every remedy you offer for a slip (another person, more
hours from a reviewer, a moved goal, a cut) as a what-if with the helper and
quote the finish it gives; offer only remedies that close the gap. A negative
claim ("more people would not help", "only a later date works") needs the same
what-ifs: try splitting the goals on the longest chain and adding hours to the
busiest person before saying it. State the assumptions a fallback depends on.

The reserve is for overruns and surprises, not for planned work: a rehearsal,
a demo dry run or a handoff between people is a goal or part of one, with its
own hours. When work passes from one person to another, add the handoff hours
to the receiving goal and record them as `handoff: <hours>` on its schedule
entry; the helper lists every cross-person dependency that has none.

The schedule block is the plan as it will run. Anything the text says about
who does or reviews a goal, what a goal needs first, or which approval it
waits for appears there as an owner, a dependency or a wait entry, so the
helper's figures describe the plan the reader is told about. The helper reads
each goal's prose (its plan section and ticket) and lists for review every
other goal it names that is neither before nor after it, and every outside
approval it names (sign-off, DPIA, pen test, legal or security review, quota,
budget or change approval, access request) with no wait for it scheduled
before. The list does not fail the run, so there is nothing to gain by
avoiding it: name goals by their ID in prose. Settle each item by asking both
directions (does this goal need the other, or does the other need this one?),
then add the dependency or wait entry, or list it under `mentions_only` (goal
IDs, or `wait`) when the text only refers to it. The helper prints every
settled mention for a reviewer. If Python 3.11 or later is not
available, say the schedule was not checked.

### Compare with capacity

Compare phase 1 with the capacity:

- Capacity is people × available hours × a focus factor. Use about 0.6 for
  part-time or interrupted people and about 0.8 for a dedicated block such as
  a single afternoon.
- First use of ADK, GCP or a new provider costs setup time: an hour for a local
  agent with an API key, half a day or more for a GCP project with IAM. In an
  organisation-managed account the project, billing link and policy
  exceptions are an administrator's calendar wait rather than team hours; the
  foundation section of [GCP decisions](gcp-decisions.md#project-foundation-the-first-goal-needs)
  says how to tell and what to ask.
- Keep 20 to 30 percent in reserve for demo preparation, setup surprises and
  the final run.

Phase 1 fits when the high end of its estimate range is within capacity minus
the reserve. If only the low end fits, say so and name the goals that move to
phase 2 when the work runs high. Abuse and spend limits, such as a per-user
allowance on a public service, are part of the floor, not scope to cut.

If phase 1 does not fit, cut scope, not the floor: simplify a goal, move it to
the next phase, or replace a build with a minimal form. Show the user the cut
line ("fits: G01 to G04, about 4 hours of 5; next phase: G05 to G08") and ask
them to confirm or move it. When someone may work alone, name the order in which
goals stay useful if time runs out early.

## Split the plan into phases

Write all phases in one plan so another session can continue "when things are
quieter" without a new design conversation.

1. **Phase 1, ship:** the goals that fit the capacity and deliver the profile's
   "done". Each is end to end and demonstrable on its own.
2. **Phase 2, harden or graduate:** the graduation conditions and the deferred
   controls the next audience needs, written as goals with skills and
   acceptance. Keep them to three or four lines each, because phase 1's
   results will change them, but give each at least its primary skill, an
   estimate range and one observable acceptance check, so a later session can
   start it.
3. **Later:** the remaining deferred items, one line each with the trigger that
   brings it forward (more users, real data, a measured latency, an incident,
   a model retirement date) and the risk accepted while it waits.

A phase boundary that needs someone's decision gets a presentation goal
(`adk-presenter`) before it and the decision date as a calendar wait after
it; the goals that need the decision depend on that wait, not on the deck.

A phase whose resources are not carried into the next one ends with a
**teardown goal**: a POC after its review, a pilot that is not continued, a
disposable environment. It runs each cleanup command recorded on the goals
that created a while-provisioned resource, deletes dependants before owners,
checks the dependent resources and retention the ledger names, inspects the
resource list, and reads the billing report once it has caught up. Its
acceptance is "absent" per resource or "retained" with a reason and an
owner, never "the delete command returned". It follows the review goal, so
the demo still exists when the decision is made, and its hours count against
the phase's capacity even though they fall after the demo. Estimate it like
any goal; the deploy skill's historical teardown took as long as the setup.

Say whether phase 1 code is meant to be kept. A throwaway demo can hard-code
what a kept slice would configure; a kept slice puts the same choice where
phase 2 can change it. Most POCs that impress get continued, so prefer the kept
form when it costs little more.

## Compact form for short work

A proof of concept or a time-boxed assignment gets one file of about 1,200
words: the design and plan together (about 1,600 when the journey writes to
an external system or provisions a resource that charges while idle, because
the failure grid or the resources rows and teardown goal are kept). Its reader has minutes and the builder
has hours; a document longer than the work it plans has failed its profile.
Use these sections and leave the rest of the design template out, rather than
marking each section not applicable:

1. **Constraints and profile:** the scope-gate table, with assumed answers
   folded in as one line each (answer and what depends on it).
2. **Journey and shape:** the journey in three sentences, what the model
   decides and what code controls, a small diagram only if it saves words.
3. **Contracts and decisions:** three to five contracts, one line each (ID,
   invariant with its scope, enforced where, check), including the floor
   items the journey touches; then at most six decisions, one line each in
   the requirement, contract, choice, tradeoff, check order.
4. **Floor, depth and deferred:** one table of concern, depth now, trigger.
   Graduation conditions as a short list.
5. **Plan:** phase 1 goals of four to six lines each (outcome, contracts,
   estimate, primary skill, acceptance, run prompt, and an empty **Status
   and evidence** line that `adk-engineer` fills with one line per contract
   proved, and numbered measurement records `M1`, `M2` and incident records
   `I1`, `I2` for a pilot or production run, each with value, baseline,
   window, sample, method, owner and build), a one-line **Resources created**
   entry on any goal that provisions something that charges while idle, the
   teardown goal that closes phase 1 after the demo, the capacity sum and cut line, phase 2
   goals of one to three lines each, and the later list. The estimates a
   review decides on (hours, spend, cost per unit) stay in the plan so the
   next review measures against them.
6. **Open decisions and next prompt.**

If the user asks for tickets, each stays under about 120 words of body (front
matter not counted): outcome, acceptance, an empty Evidence section and the
run prompt, linking to the design for everything else.

For a web application, section 4 gains one security line: the tiers applied,
the rules marked `n/a` with a reason, and the deferred rules with triggers.
Each phase 1 goal gains one line naming its companion skills and rule IDs.
Allow about 250 more words: about 1,450 in total, or 1,850 with the failure
grid. A ticket may add a one-line Constraints section of about 30 words.
The compact form has no companion table: goals name companions only, and the
first goal writes the table from web application defaults, with the pins it
resolves, into the project's `AGENTS.md`.
Estimates are in quarter hours. With one person, add them by hand; no schedule block or helper run. When several people share the work, add the schedule block anyway and run the helper: by hand, cross-person chains, loads and part sums go wrong (a two-developer trial on 23 October 2026 showed all three).

Failure tables, data-authority tables and observability sections appear only
when the journey actually holds that risk, and then as two or three rows. A
proof of concept that writes to an external system keeps a three-column
failure grid (unavailable or slow, rejects the request, write outcome
unknown), one row per external system touched, each cell a few words citing
an acceptance item.

## Write each fact once, at the depth it is known

Long plans drift: a figure or goal ID restated in three places is updated in
one, and the reader acts on another. Length should come from decisions, not
from repetition.

- **Summary first.** Open the plan with a summary of at most one page for the
  person who decides: profile, what phase 1 delivers, the finish range and
  whether it fits, the three largest risks, and the decisions needed from
  them. A manager should not need to read further to act.
- **One home per fact.** Requirements, contracts, decisions and their
  rationale live in the design, with R, C and D IDs. Goals and tickets cite
  contracts by ID and record evidence against them.
  Estimates, owners, dependencies and waits live in the plan's schedule block.
  Capacity, finish range and the largest risks live in the plan's summary;
  the design points to it instead of restating them. Each goal's scope,
  route and acceptance have one home: the ticket when tickets are written,
  with the plan's goals table linking to it in place of a full goal entry;
  otherwise the plan's goal entry. Everywhere else refers to the ID ("see
  D4", "G07") instead of restating it. Change lists and what-if results are
  tables of one row each, not paragraphs.
- **Detail follows certainty.** Phase 1 goals are complete. Phase 2 goals are
  three or four lines each: outcome, primary skill, estimate and one
  acceptance check. The later list is one line per item. Write tickets only
  for phase 1 unless the user asks for more, because phase 2 will change once
  phase 1 has run.
- **Cut waste, never substance.** Do not set a word count for larger
  profiles: in testing, a number made the model cut a kill switch and a
  staging test while keeping filler. Remove instead: facts restated outside
  their home (a contract's invariant repeated in decision rationale, goal
  outcomes or failure rows instead of its ID), run-history and change logs
  beyond one row per change, pasted
  helper output (quote the four figures that matter), tables that only point
  elsewhere, later-list items repeated from the depth table, and phase 2
  detail. Keep every floor item, failure row, test, acceptance case, wait and
  handoff. Write the design at the profile's depth: an internal tool does not
  need a production service's contract and failure tables for paths it
  does not have.

## Examples

**Five hours, one developer, demo tomorrow, 50 anonymised emails.** POC.
Capacity about 5 × 0.8 = 4 hours, so roughly 3 hours of goals after reserve.
Phase 1: a local agent that classifies an email and drafts a reply for a human
(1.5 hours), a script that runs the 50 samples into a reviewable table and a
handful of checked labels (1 hour), `adk web` for the demo with a pinned model
and a call cap (0.5 hour). Floor: no sending; drafts only; sample data only.
Phase 2, if the demo lands: real inbox access with scoped credentials, sending
behind approval, an evaluation set, Cloud Run behind IAP. Later: SLOs, CI
evaluation gate, cost tuning, each with its trigger.

**Two engineers at half time for three weeks, 40 finance colleagues, Google
Workspace sign-in.** Internal tool. Capacity about 2 × 0.5 × 15 days × 6 hours
× 0.6 ≈ 54 focused hours. Identity and "employees see only their own claims"
are built in phase 1, enforced in code from the verified user, with
cross-user denial tests. A canary, SLOs and an adversarial suite are deferred
with triggers, because the users are known colleagues and the tool only reads.

**Three people, two weeks to an MVP, customers can place orders.** MVP. Order
placement is money: idempotent order creation and explicit confirmation are in
phase 1 even though it delays recommendations polish. Evaluation in CI,
per-user budgets and traces follow in phase 2; tuning waits for measured traffic.
